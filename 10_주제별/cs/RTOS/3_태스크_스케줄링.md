## 1. 멀티스레드 프로그램이 실제로 실행되는 방식

우리가 multi-threaded program을 작성할 때는 보통 `main`에서 setup을 수행하고, 필요한 thread나 task를 만든다. 코드 관점에서는 각 task가 독립적인 `while (forever)` loop처럼 보이고, 동시에 실행되는 것처럼 느껴진다.

Microcontroller에서는 여기에 hardware interrupt도 함께 붙을 수 있다. 예를 들어 timer overflow, pin change, message transmit 같은 event를 interrupt service routine(ISR)에서 처리할 수 있다.

하지만 single-core processor에서는 실제로 여러 task가 물리적으로 동시에 실행되지 않는다. CPU core가 하나뿐이라면 processor는 시간을 잘게 나누어 여러 task에 배분한다. RTOS scheduler는 이 배분을 담당한다.

## 2. Tick과 Time Slicing

많은 RTOS는 **time slicing** 방식을 사용한다. Hardware timer가 일정한 간격으로 processor에 interrupt를 걸고, RTOS는 그 시점마다 scheduler를 실행한다.

FreeRTOS에서는 흔히 **1 millisecond** time slice를 볼 수 있다. 강의에서 사용하는 ESP32 예제도 1ms 간격으로 scheduler가 동작한다. 이 주기적인 scheduler 호출 간격을 **tick**이라고 부른다.

Scheduler는 매 tick마다 다음에 어떤 task를 실행할지 판단한다. 판단 기준은 단순히 "아무 task나 순서대로"가 아니라, **ready 상태인 task 중 가장 높은 priority를 가진 task**를 선택하는 것이다.

- **Tick:** scheduler가 주기적으로 실행되는 시간 기준 단위
- **Time slice:** 한 task가 다음 scheduler 판단 전까지 CPU를 사용할 수 있는 시간 조각
- **Scheduler:** ready task 목록과 priority를 보고 다음 running task를 고르는 RTOS 구성 요소

## 3. Priority 기반 선택과 Round-Robin

Task마다 priority가 있고, scheduler는 ready 상태인 task 중 가장 높은 priority를 먼저 실행한다.

예를 들어 task A의 priority가 0이고, task B와 task C의 priority가 1이라면, A보다 B와 C가 먼저 선택된다. A가 아직 끝나지 않았더라도, B와 C가 ready 상태가 되면 다음 tick에서 scheduler는 더 높은 priority인 B 또는 C를 실행한다.

같은 priority의 task가 여러 개 ready 상태라면 scheduler는 이들을 번갈아 실행한다. 이를 **round-robin** 방식이라고 한다. 강의 예시에서는 B와 C가 모두 priority 1이므로, 둘이 차례대로 CPU 시간을 나누어 가진다.

이처럼 낮은 priority task가 실행 중이더라도 높은 priority task가 ready 상태가 되면 CPU 시간이 빼앗길 수 있다. 이런 방식을 **preemptive scheduling**이라고 한다.

> **주의**
> 높은 priority task가 ready 상태가 되었다고 해서 항상 즉시 실행되는 것은 아니다. 강의의 단순화된 timeline에서는 B와 C가 tick 중간에 ready 상태가 되어도 다음 tick까지 기다린 뒤 scheduler에 의해 선택된다.

## 4. `vTaskDelay`와 Blocked State

Task가 계속 CPU를 써야 하는 것은 아니다. 실행 중인 task는 API를 호출해 자신을 **blocked state**로 보낼 수 있다.

대표적인 API가 `vTaskDelay`다. 예를 들어 task A가 실행 중 `vTaskDelay(2)`를 호출하면, task A는 2 ticks 동안 blocked 상태에 들어간다. Blocked 상태의 task는 CPU에서 실행되지 않고, scheduler도 running state로 선택할 수 없다.

Delay가 끝나면 task는 자동으로 ready state로 돌아간다. 그 후 scheduler가 priority와 ready task 목록을 보고 다시 실행 여부를 결정한다.

Blocked state는 delay뿐 아니라 queue나 semaphore를 기다릴 때도 사용된다. 예를 들어 어떤 task가 queue message를 기다리거나 semaphore release를 기다리는 동안에는 CPU를 쓰지 않고 blocked 상태에 머무를 수 있다.

- `vTaskDelay`: 지정한 tick 수만큼 task를 blocked 상태로 보냄
- Queue wait: message가 들어올 때까지 blocked
- Semaphore wait: semaphore가 release될 때까지 blocked

## 5. Task State: Ready, Running, Blocked, Suspended

FreeRTOS scheduler는 각 task가 어떤 state에 있는지 기록한다.

### Ready State

Task가 생성되면 자동으로 ready state에 들어간다. Ready state는 "언제든 실행될 준비가 되어 있다"는 뜻이다.

다만 ready state에 있다고 해서 반드시 바로 실행되는 것은 아니다. 더 높은 priority task가 ready 상태라면 그 task가 먼저 실행된다. 같은 priority task가 여러 개라면 scheduler의 round-robin 정책에 따라 차례를 기다릴 수 있다.

### Running State

Scheduler가 task를 선택하면 해당 task는 running state가 된다. Running state는 processor를 실제로 사용하고 있는 상태다.

Single-core processor에서는 한 순간에 running state인 task가 하나뿐이다. Multi-core processor라면 core 수에 따라 여러 task가 동시에 running state가 될 수 있다.

### Blocked State

Task가 `vTaskDelay`, queue wait, semaphore wait 같은 API를 호출하면 blocked state로 갈 수 있다. Blocked state의 task는 CPU를 사용하지 않으며, unblock event가 발생해야 ready state로 돌아간다.

Unblock event는 delay timer expiration, semaphore release, queue receive 가능 상태 등이 될 수 있다.

### Suspended State

FreeRTOS에는 `vTaskSuspend` API가 있다. 이 API를 사용하면 task를 suspended state로 보낼 수 있다. Suspended state의 task도 blocked state처럼 scheduler에 의해 실행 대상으로 선택되지 않는다.

차이는 복귀 조건이다. Blocked state는 delay 만료나 semaphore release 같은 event로 ready state에 돌아올 수 있지만, suspended state는 명시적으로 `vTaskResume`이 호출되어야 ready state로 돌아온다.

따라서 `vTaskSuspend`와 `vTaskResume`은 timer에 의존하지 않고 task를 잠시 재워 두고 싶을 때 사용할 수 있다.

## 6. Hardware Interrupt와 RTOS Scheduler의 관계

지금까지의 scheduling 설명은 software task 사이의 CPU 배분이다. Hardware interrupt는 별개의 우선순위 체계로 동작한다.

특별히 interrupt를 비활성화하지 않는 한, hardware interrupt는 일반 task code보다 높은 우선순위를 가진다. 어떤 task가 실행 중이더라도 hardware interrupt가 발생하면 processor는 task 실행을 멈추고 ISR을 수행한다.

ISR이 끝나면 execution은 원래 실행 중이던 task로 돌아간다. 이후 scheduler가 다시 실행될 때 task priority와 state에 따라 다음 task가 결정된다.

Hardware interrupt가 다른 hardware interrupt를 preempt할 수 있는지는 hardware와 설정에 따라 달라진다. 이를 **nested interrupt**라고 한다. 강의에서는 nested interrupt를 깊게 다루지 않고, 우선은 한 번에 하나의 ISR만 실행하고 ISR을 최대한 짧게 유지하라고 권장한다.

> **주의**
> RTOS task priority와 hardware interrupt priority를 같은 층위로 생각하면 안 된다. Hardware interrupt는 일반 task scheduling보다 우선하며, ISR은 짧게 작성해야 전체 system latency를 관리하기 쉽다.

## 7. Multi-Core Scheduler와 ESP32

Single-core 시스템에서는 한 순간에 하나의 task만 running state에 있을 수 있다. 하지만 multi-core 시스템에서는 scheduler가 task를 여러 core에 배치할 수 있다.

ESP32는 multi-core 환경을 제공한다. ESP-IDF scheduler에 task allocation을 맡기면 task B와 task C가 서로 다른 core에서 실제로 동시에 실행될 수 있다.

다만 강의 예제에서는 scheduling 개념을 단순하게 보여주기 위해 하나의 core만 사용한다. Multi-core scheduling은 task가 어느 core에서 실행되는지, shared resource를 어떻게 보호하는지까지 고려해야 하므로 예제가 복잡해진다.

## 8. Context Switching

Scheduler가 한 task에서 다른 task로 전환하려면, 현재 task가 어디까지 실행되었는지 기억해야 한다. Program instruction의 위치, CPU register 값, RAM에 있는 working variable 등 task의 실행 문맥 전체를 보존해야 한다.

이 실행 문맥을 **context**라고 하고, 한 task의 context를 저장한 뒤 다른 task의 context를 복원하는 과정을 **context switching**이라고 한다.

Context에는 다음 정보가 포함될 수 있다.

- Program counter처럼 다음에 실행할 instruction 위치
- CPU register 값
- Stack에 저장된 함수 호출 정보와 지역 변수
- Task가 사용 중이던 working memory 상태

FreeRTOS에서는 task를 만들 때 stack 크기를 지정해야 한다. 이 stack은 함수 호출과 지역 변수뿐 아니라 context 저장에도 사용된다. 그래서 task stack을 너무 작게 잡으면 context switching이나 task 실행 중 문제가 생길 수 있다.

강의에서는 FreeRTOS documentation의 context switching 설명과 AVR microcontroller 예제를 참고하라고 권한다. 해당 문서는 context switch가 어떤 단계로 수행되는지 자세히 보여준다.

## 9. Arduino ESP32 예제: Task Preemption 관찰

강의에서는 Arduino 환경의 ESP32 예제로 task preemption을 관찰한다. 설정은 하나의 core만 사용하도록 맞춘다.

예제에는 세 가지 흐름이 있다.

첫 번째 task는 문자열을 한 글자씩 serial terminal에 출력한다. `Serial.print`로 문자열 전체를 한 번에 출력하면 Arduino serial buffer에 문자열이 한꺼번에 복사되어 preemption이 눈에 잘 보이지 않는다. 그래서 문자열을 loop로 돌며 character 단위로 출력한다. 출력이 끝나면 `vTaskDelay`로 1초 동안 blocked state에 들어간다.

두 번째 task는 100 milliseconds마다 asterisk(`*`) 한 글자를 출력한다. 이 task는 첫 번째 task보다 높은 priority를 가진다. 따라서 실행 준비가 되면 첫 번째 task의 문자열 출력 중간을 preempt할 수 있다.

세 번째 task는 다른 두 task를 제어하는 역할을 한다. 강의에서는 task handle을 사용해 두 번째 task를 suspend/resume하고, 몇 번 반복한 뒤 첫 번째 task를 `vTaskDelete`로 삭제한다.

Setup에서는 serial baud rate를 매우 느린 **300 baud**로 설정한다. 그래야 문자열 출력이 한 tick 안에 모두 끝나지 않고, preemption이 눈으로 보인다. ESP32에서는 serial monitor 연결 시간을 주기 위해 약 1초 delay를 추가하는 것도 권장한다.

예제 실행 결과는 다음을 보여준다.

- `setup`과 `loop`도 자체 task 안에서 실행된다.
- 문자열 출력 task는 priority 1로 동작한다.
- Asterisk 출력 task는 priority 2로 동작한다.
- Asterisk task를 suspend/resume하면 별표 출력이 멈췄다가 다시 시작된다.
- Priority가 더 높은 asterisk task가 문자열 출력 task를 preempt하면 문장 중간에 `*`가 끼어든다.
- 첫 번째 task가 삭제된 뒤에는 asterisk task만 계속 실행된다.

> **주의**
> `vTaskDelete`를 호출할 때는 task handle이 `NULL`이 아닌지 확인하고, 삭제 직후 handle을 `NULL`로 설정하는 것이 좋다. 존재하지 않는 task에 대해 `vTaskDelete`를 호출하면 memory overwrite나 processor crash/reset 같은 문제가 생길 수 있다.

## 10. 실습 Challenge: LED Blink 속도 제어

강의의 challenge는 두 개의 task로 LED blink 속도를 제어하는 프로그램을 만드는 것이다.

첫 번째 task는 LED를 blink한다. 두 번째 task는 serial terminal input을 듣는다. 사용자가 숫자를 입력하면 그 숫자를 LED blink delay time으로 반영한다.

이 구조의 핵심은 user interface와 hardware control이 독립적으로 실행된다는 점이다. Serial input을 기다리는 동안에도 LED 제어 task는 계속 동작할 수 있고, LED blink가 진행되는 동안에도 input task는 사용자의 새 delay 값을 받을 준비를 할 수 있다.

이 challenge를 풀 때는 shared variable을 어떻게 안전하게 갱신할지 생각해야 한다. 강의 Part 3에서는 아직 semaphore나 mutex를 깊게 다루지 않았지만, 이후 shared resource 관리 주제와 자연스럽게 연결된다.

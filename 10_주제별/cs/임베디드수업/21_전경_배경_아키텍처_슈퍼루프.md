# 전경-배경 아키텍처 — Super Loop와 Main+Interrupts

**원본 강의:** [#21 Foreground-Background Architecture ("Superloop") (YouTube)](https://www.youtube.com/watch?v=AoLLKbvEY8Q)

전경-배경(foreground/background) 아키텍처는 작은 임베디드 시스템에서 널리 쓰이는 기본 소프트웨어 구조다. `main()`의 끝없는 loop가 **배경(background)** 을 이루고, 이 loop를 언제든 선점(preempt)하는 interrupt handler(ISR)가 **전경(foreground)** 을 이룬다. 이를 `super-loop`, `main + ISRs`라고도 부른다. 이 구조는 이후 RTOS와 다른 임베디드 아키텍처를 이해하는 출발점이다.

---

## 1. 구조의 핵심 — Background loop와 Foreground ISR

가장 단순한 Blinky program도 전경-배경 구조를 가진다. `main()`은 LED를 켜고 끄는 일을 계속 반복하고, SysTick interrupt는 정해진 주기로 발생해 tick counter를 증가시킨다.

```c
int main(void) {
    BSP_init();

    while (1) {                 // background
        BSP_ledGreenOn();
        BSP_delay(BSP_TICKS_PER_SEC / 4U);
        BSP_ledGreenOff();
        BSP_delay(3U * BSP_TICKS_PER_SEC / 4U);
    }
}

void SysTick_Handler(void) {    // foreground
    ++l_tickCtr;
}
```

실행 중 interrupt가 발생하면 CPU는 background loop의 현재 instruction을 마친 뒤 ISR을 실행한다. ISR은 끝나면 **선점했던 바로 그 지점**으로 복귀한다. 따라서 foreground가 background보다 우선하지만, 별도의 scheduler가 background 작업을 교체하는 구조는 아니다.

> 전경-배경은 "주 프로그램 + 예외 처리"라는 가장 작은 동시성 모델이다. Background는 계속 돌고, 시간·입력·통신 같은 비동기 사건은 interrupt가 먼저 처리한다.

- **Background:** `main()` 내부의 무한 loop. 일반 application logic와 상대적으로 시간 제약이 느슨한 작업을 수행한다.
- **Foreground:** SysTick, GPIO, UART 등 interrupt source의 ISR. Background를 비동기적으로 선점한다.
- **Super loop:** `while (1)` 또는 빈 제어식의 `for (;;)`로 구성한 background loop를 가리키는 관용적 이름이다.
- **Main + ISRs:** foreground/background를 구현 관점에서 부르는 다른 이름이다.

> **이미지 필요**
> Background의 무한 loop를 SysTick ISR이 선점했다가 원래 instruction으로 복귀하는 전경-배경 타임라인
> - 출처: 강의 07:47~08:18
> - 대체안: `main()` loop와 `SysTick_Handler()`를 두 lane으로 그려 preemption/return 화살표를 표시

## 2. ISR과 Background 사이의 공유 데이터 — `volatile`과 critical section

두 실행 맥락은 공유 변수로 통신한다. 강의의 `l_tickCtr`는 SysTick ISR에서 증가하고, background의 `BSP_delay()` 및 `BSP_tickCtr()`에서 읽는다.

```c
static volatile uint32_t l_tickCtr;

void SysTick_Handler(void) {
    ++l_tickCtr;
}

uint32_t BSP_tickCtr(void) {
    uint32_t tickCtr;
    QF_INT_DISABLE();
    tickCtr = l_tickCtr;
    QF_INT_ENABLE();
    return tickCtr;
}
```

`volatile`은 compiler에게 이 값이 현재 code 흐름 밖에서 예기치 않게 바뀔 수 있으니, register에 캐시하거나 읽기를 제거하지 말고 실제 memory access를 유지하라고 알린다. ISR이 값을 바꿀 수 있는 변수에 필요한 qualifier다.

그러나 `volatile`만으로 race condition이 해결되지는 않는다. Background가 공유 값을 읽거나 read-modify-write 하는 도중 ISR이 끼어들 수 있기 때문이다. 강의의 규칙은 **background에서 공유 변수에 접근할 때 interrupt를 잠깐 disable한 critical section으로 보호**하는 것이다. ISR은 이미 interrupt context에서 실행되므로 같은 방식으로 자신을 보호하지 않는다.

```text
background: tick counter 읽기 시작
        ↓ (중간에 interrupt 발생)
ISR:     counter 갱신
        ↓
background: 일관되지 않거나 오래된 값으로 처리할 위험
```

`BSP_delay()`는 먼저 시작 tick을 저장하고, 이후 현재 tick과의 차이를 polling한다.

```c
void BSP_delay(uint32_t ticks) {
    uint32_t const start = BSP_tickCtr();

    while ((BSP_tickCtr() - start) < ticks) {
        /* tick timeout을 polling */
    }
}
```

Unsigned 2's complement arithmetic를 사용하므로 counter가 `0xFFFFFFFF`에서 `0`으로 wraparound해도, 두 tick의 간격이 counter 전체 범위를 넘지 않는 한 뺄셈 결과로 경과 시간을 올바르게 판단할 수 있다.

> **주의**
> `volatile`은 compiler 최적화에 관한 약속일 뿐 atomicity나 상호 배제를 제공하지 않는다. ISR과 background가 공유하는 값의 일관성은 critical section, atomic access, 또는 더 높은 수준의 동기화 설계로 따로 보장해야 한다.

## 3. SysTick 기반 BSP delay와 busy-wait의 비용

기존의 단순 delay loop는 compiler가 생성한 instruction 속도에 영향을 받지만, `BSP_delay()`는 SysTick interrupt를 이용해 시간을 센다. 예를 들어 `BSP_TICKS_PER_SEC`가 `100`이면 SysTick은 초당 100회 발생하며, ISR이 `l_tickCtr`를 1씩 증가시킨다. Timing 기준이 CPU instruction loop가 아니라 SysTick이므로 더 정밀하다.

하지만 delay가 정밀해졌다고 CPU를 효율적으로 쓰는 것은 아니다. `BSP_delay()`의 `while`은 timeout까지 tick counter만 반복해서 확인한다. 즉 CPU가 timeout을 기다리는 동안 다른 application 일을 하지 못하고 cycle을 소모한다.

디버거로 실행 중인 Blinky를 멈추면 대개 다음 call stack에서 멈춘다.

```text
main()
  └─ BSP_delay()
       └─ BSP_tickCtr()
```

이는 program 실행 시간 대부분이 delay의 polling loop에 있다는 뜻이다. Flowchart에서 control flow가 뒤로 돌아가는 굵은 화살표가 바로 이 polling loop다.

- **정밀도 향상:** SysTick 주기로 delay를 재므로 compiler-generated delay loop보다 timing 기준이 안정적이다.
- **CPU 낭비:** timeout 동안 계속 polling하므로 CPU cycle을 모두 사용한다.
- **구조적 한계:** delay 중 background는 다음 작업·새 event를 처리할 수 없다.

## 4. Blocking·sequential 방식 — 읽기 쉽지만 기다리는 동안 멈춘다

LED를 켠 뒤 1/4초를 기다리고, 끈 뒤 3/4초를 기다리는 code는 **blocking**이며 **sequential**하다.

```text
LED on → 1/4초 timeout 대기 → LED off → 3/4초 timeout 대기 → 반복
```

Blocking이라는 말은 event(여기서는 timeout)를 inline으로 기다리며, event가 도착하기 전까지 code가 다음 단계로 진행하지 못한다는 뜻이다. 대신 timeout이 도착한 뒤에 실행될 code가 바로 아래에 있으므로, 그 event를 어떻게 처리할지는 source code의 순서 안에 이미 명확히 들어 있다.

Sequential이라는 말도 같은 특징을 다른 각도에서 설명한다. Program이 받아들일 event의 순서가 instruction 순서에 hard-code되어 있다. 이 Blinky는 LED를 켠 뒤의 1/4초 timeout, LED를 끈 뒤의 3/4초 timeout 순서만 기대한다.

- **장점:** 순서대로 읽히므로 간단한 절차를 구현하기 쉽고, 다음 처리의 context가 call stack과 바로 뒤 code에 남는다.
- **단점:** 기다리는 동안 다른 event를 처리할 수 없고, polling loop가 CPU를 점유한다.
- **적합한 경우:** 처리할 일이 하나뿐이거나, 기다리는 동안 놓치면 안 되는 다른 event가 없고 CPU 낭비가 허용되는 매우 단순한 system.

## 5. Non-blocking·event-driven 방식 — polling state machine

같은 LED를 blocking delay 없이 구현할 수 있다. 핵심은 현재 상태와 deadline을 저장하고, main loop 한 번마다 "지금 timeout이 되었는가?"만 짧게 검사하는 것이다.

```c
enum BlinkyState {
    LED_ON_STATE,
    LED_OFF_STATE
};

int main(void) {
    enum BlinkyState state = LED_OFF_STATE;
    uint32_t timeout = BSP_tickCtr();

    BSP_init();
    BSP_ledGreenOn();
    state = LED_ON_STATE;
    timeout += BSP_TICKS_PER_SEC / 4U;

    while (1) {
        uint32_t const now = BSP_tickCtr();

        if ((int32_t)(now - timeout) >= 0) {
            if (state == LED_ON_STATE) {
                BSP_ledGreenOff();
                state = LED_OFF_STATE;
                timeout += 3U * BSP_TICKS_PER_SEC / 4U;
            }
            else {
                BSP_ledGreenOn();
                state = LED_ON_STATE;
                timeout += BSP_TICKS_PER_SEC / 4U;
            }
        }

        /* 다른 event와 작업을 여기에서 계속 처리할 수 있다. */
    }
}
```

위 code의 핵심은 `while (1)` 안에서 기다리지 않는다는 점이다. 각 pass는 앞으로만 진행하고 즉시 loop의 시작점으로 돌아온다. 따라서 main loop는 초당 한 번이 아니라 수십만 번 이상 돌 수 있으며, event가 도착하면 **도착한 순서대로** 빠르게 처리할 기회를 얻는다. 이를 **event-driven**이라고 부른다.

강의의 non-blocking 구현은 **polling state machine** 형태다. Timeout event의 순서는 더 이상 instruction의 나열에 고정되어 있지 않고, `state`와 deadline 같은 data가 현재 context를 보존한다. 이 flexibility와 responsiveness가 복잡도 증가의 대가다.

```text
Blocking / sequential
  상태와 다음 행동이 call stack·instruction 순서에 암묵적으로 존재

Non-blocking / event-driven
  상태와 다음 행동을 state variable·deadline으로 명시적으로 보존
```

> **주의**
> Non-blocking code를 상태기계로 구조화하지 않으면, 여러 global variable을 기준으로 깊게 중첩된 `if-then-else`를 쌓기 쉽다. 이런 "spaghetti code" 또는 "big ball of mud"는 event 순서가 늘어날수록 수정과 검증이 어려워진다.

## 6. Timing 제약은 어디에서 처리할까

Background loop에서 호출되는 함수의 실행 시점은 일정하지 않다. 한 loop pass의 시간이 conditional branch, 다른 작업의 처리량, 그리고 ISR 실행 시간에 따라 계속 달라지기 때문이다. 따라서 strict timing constraint가 있는 동작을 background에 두면 deadline을 보장하기 어렵다.

그런 작업은 foreground ISR로 옮겨야 한다. ISR은 interrupt source의 timing에 맞춰 실행되므로 background보다 deadline을 예측하기 쉽다. 다만 ISR을 길게 만들면 새로운 문제가 생긴다.

```text
긴 ISR
  ├─ background를 오래 멈춤
  └─ 다른 interrupt의 응답을 지연시킬 수 있음
```

- **Background에 둘 일:** deadline이 느슨한 application logic, 상태 전이 검사, 짧은 polling 작업.
- **Foreground ISR에 둘 일:** 정밀한 순간 대응이 필요한 최소 작업, 시간 기준을 만드는 tick 갱신, hardware event 포착.
- **실무 원칙:** ISR은 가능한 짧게 끝내고, 긴 처리는 flag/event를 통해 background 또는 이후의 task로 넘긴다.

전경-배경 구조는 단순해 consumer electronics, home appliances, toys, remote controller 등 대량 생산 소형 embedded application에서 여전히 많이 쓰인다. 반면 ISR이 길어지고 background 일이 여러 개로 늘어나 event-driven state machine만으로 관리하기 어려워지면, 다음 단계인 RTOS와 다른 architecture를 검토할 이유가 생긴다.

## 7. BSP로 WHAT과 HOW 분리하기

Board Support Package(BSP)는 application code가 board-specific detail을 직접 알지 않도록 하는 계층이다. Blinky의 초기화, LED pin 번호, MCU header, LED on/off register 조작은 모두 board에 종속적이므로 `bsp.c`로 옮긴다.

```c
/* main.c: 무엇을 할지(WHAT)만 표현 */
int main(void) {
    BSP_init();
    while (1) {
        BSP_ledGreenOn();
        /* ... */
        BSP_ledGreenOff();
    }
}

/* bsp.c: 해당 board에서 어떻게 할지(HOW)를 구현 */
void BSP_init(void) { /* clock, GPIO 초기화 */ }
void BSP_ledGreenOn(void) { /* 해당 pin 제어 */ }
void BSP_ledGreenOff(void) { /* 해당 pin 제어 */ }
```

이 분리는 `main()`을 작고 self-explanatory하게 만들며, board나 toolchain이 바뀌어도 BSP implementation만 교체하면 application code를 그대로 재사용할 수 있게 한다. 같은 main application을 desktop PC에서 실행하는 BSP를 제공하는 것도 가능하다.

| 구분 | Application / `main.c` | BSP / `bsp.c`, `bsp.h` |
| --- | --- | --- |
| 관심사 | 무엇을 할 것인가 | 해당 board에서 어떻게 할 것인가 |
| 포함 내용 | LED를 켜고 끄는 업무 흐름 | MCU header, pin 번호, register, clock/GPIO 초기화 |
| board 교체 시 | 가능한 한 변경하지 않음 | 새 board에 맞춰 implementation 교체 |

Arduino도 이 architecture를 library 안에 감춰 사용한다. Arduino runtime의 `main()`은 초기화와 `setup()` 1회 호출 뒤 `for (;;)`에서 `loop()`를 반복한다. 여기에 system tick ISR 등 foreground interrupt handler가 결합된다. 익숙한 Arduino `delay()` 역시 tick을 polling하는 blocking delay라는 점에서 같은 구조다.

## 8. 설계 선택 요약 — 단순성, 응답성, 확장성의 trade-off

| 방식 | 강점 | 한계 | 구현 단서 |
| --- | --- | --- | --- |
| Blocking sequential super loop | 가장 직관적이고 code 순서가 곧 event 순서 | 기다리는 동안 CPU 낭비, 다른 event 대응 지연 | `BSP_delay()`처럼 polling loop 안에서 대기 |
| Non-blocking event-driven super loop | main loop가 자주 돌아 새 event에 빠르게 대응 | 상태를 명시적으로 관리해야 해 code가 복잡해짐 | state variable, deadline, polling state machine |
| ISR 중심 처리 | strict timing 대응 가능 | ISR이 길어지면 background·다른 ISR을 방해 | ISR은 짧게, 긴 일은 밖으로 전달 |
| RTOS | 복수 작업과 scheduling을 체계적으로 관리 | 추가 복잡도와 resource overhead | super loop의 한계가 실제 문제일 때 검토 |

전경-배경 architecture 자체가 나쁜 설계인 것은 아니다. 작은 system에서는 낮은 memory/CPU overhead와 단순성이 큰 장점이다. 중요한 것은 현재 workload가 blocking을 허용하는지, event의 deadline이 어느 정도인지, 그리고 증가할 state와 interrupt 복잡도를 이 구조가 감당할 수 있는지 판단하는 것이다.

## 면접 답변 (30초 분량)

> `/easy-quiz` 실행 시 이 섹션이 정답 카드로 사용됩니다.

- **한 줄 정의:** 전경-배경 architecture는 `main()`의 무한 background loop와 이를 선점하는 foreground ISR로 구성된, super loop 또는 main+ISRs라고도 하는 기본 임베디드 구조다.
- **왜 필요:** 작은 system은 RTOS의 scheduling overhead 없이도 background에서 일반 logic을 반복하고, timer·입력처럼 즉시 반응해야 하는 event는 interrupt로 처리할 수 있다.
- **동작:** ISR은 background를 선점한 뒤 원래 지점으로 복귀하며, 두 영역은 `volatile` 공유 변수로 통신한다. Background의 공유 데이터 접근은 race condition을 막기 위해 짧은 critical section으로 보호한다. Blocking delay 대신 state와 deadline을 두면 non-blocking event-driven loop로 전환할 수 있다.
- **비교:** Blocking sequential loop는 event 순서가 code 순서에 고정되어 읽기 쉽지만 기다리는 동안 CPU를 점유한다. Non-blocking event-driven loop는 event 대응이 빠른 대신 state machine으로 context를 명시적으로 관리해야 한다.
- **30초 통합 답변:** 전경-배경 architecture는 `main()`의 무한 loop가 background로 일반 application logic을 수행하고, SysTick·GPIO 같은 ISR이 foreground에서 이를 선점해 긴급 event를 처리하는 구조입니다. 두 영역은 `volatile` 공유 변수로 통신하지만 `volatile`만으로 race condition이 해결되지는 않으므로 background 접근은 짧은 critical section으로 보호합니다. `BSP_delay()`처럼 기다리는 blocking super loop는 단순하지만 CPU를 낭비하고 다른 event 대응이 늦습니다. 상태와 deadline을 저장하는 non-blocking state machine으로 바꾸면 event-driven하게 동작하며, timing이 엄격한 최소 작업은 ISR에 두고 ISR이 길어지면 RTOS 같은 다음 architecture를 검토합니다.

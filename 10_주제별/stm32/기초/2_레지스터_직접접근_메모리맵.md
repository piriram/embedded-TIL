# STM32 입문 #3 — 레지스터 직접 접근 (메모리 맵 · 포인터 · 구조체)

**주제:** CMSIS 헤더가 해 주는 일을 직접 손으로 — 메모리 맵에서 레지스터 주소를 찾아 포인터로 캐스팅해 접근하고, 더 깔끔하게 구조체로 매핑하기
**타겟 MCU:** STM32F767VIT6
**원본 강의:** [(210) STM32 입문 강의 몰아보기 | ARM, GPIO, ADC, UART (YouTube)](https://www.youtube.com/watch?v=XOsyrZGZtR8)

> 지난 편(GPIO 출력)에서는 CMSIS 헤더에 미리 선언된 `GPIOD`, `RCC`를 가져다 썼다. 이번엔 그 헤더가 내부적으로 무엇을 하는지, **포인터로 메모리 주소에 직접 접근**해 똑같이 동작시켜 본다.

---

## 1. 메모리 맵 — 주소로 주변 장치에 접근한다

STM32F767의 **메모리 맵(Memory Map)** 은 `0x0000_0000`부터 `0xFFFF_FFFF`까지의 주소 공간을 SRAM, 주변 장치(Peripherals) 등 섹터별로 할당한 표다.

- 주변 장치(Peripherals)는 **`0x4000_0000` 번지부터** 매핑된다.
- 이 영역은 다시 **APB1, APB2, AHB** 버스별로 펼쳐진다.
- 각 버스에 주소가 할당돼 있어서, **그 주소로 레지스터에 접근**할 수 있다.

예: APB1의 시작 주소는 `0x4000_0000`이고, 거기에 타이머 2가 연결돼 있다 — 이런 식으로 표에서 확인한다.

핵심 아이디어: **레지스터는 결국 특정 메모리 주소다.** 그 주소를 알면 C 포인터로 직접 읽고 쓸 수 있다.

---

## 2. 베이스 주소 정의

GPIO D를 직접 다뤄 보자. 메모리 맵에서 GPIO D는 `0x4002_0C00`에서 시작한다. RCC도 함께 정의한다.

```c
#define GPIOD_BASE   0x40020C00
#define RCC_BASE     0x40023800   // RCC 시작 주소
```

> `(volatile unsigned long *)` 같은 리터럴 캐스팅으로 "이 숫자는 주소다"라고 컴파일러에 알려 준다.

---

## 3. 오프셋 — 베이스에서 얼마나 떨어져 있나

레퍼런스 매뉴얼의 **GPIO register map** 표를 보면 각 레지스터의 **offset**이 나온다. 오프셋은 베이스 주소에서 떨어진 거리다.

| 레지스터 | offset | 의미 |
| --- | --- | --- |
| `MODER`  | `0x00` | 시작 주소 그 자리 |
| `OTYPER` | `0x04` | 32비트(4바이트) 떨어짐 |
| `OSPEEDR`| `0x08` | 또 4바이트 떨어짐 |
| `ODR`    | `0x14` | … |

레지스터가 32비트(4바이트)라서 연속된 레지스터는 **4바이트씩** 떨어져 매핑돼 있다.

```c
#define GPIO_MODER_OFFSET    0x00
#define GPIO_OTYPER_OFFSET   0x04
#define GPIO_OSPEEDR_OFFSET  0x08
// RCC AHB1ENR 오프셋은 RCC 베이스에서 0x30
#define RCC_AHB1ENR_OFFSET   0x30
```

---

## 4. 포인터 캐스팅으로 레지스터 만들기

레지스터의 실제 주소 = **베이스 + 오프셋**. 이 값을 **포인터로 캐스팅**하고, **역참조(`*`)** 하면 그 주소의 값에 접근한다.

```c
#define GPIOD_MODER  (*(volatile unsigned long *)(GPIOD_BASE + GPIO_MODER_OFFSET))
#define GPIOD_ODR    (*(volatile unsigned long *)(GPIOD_BASE + 0x14))
```

해석:
1. `GPIOD_BASE + offset` → 레지스터의 주소(숫자)
2. `(volatile unsigned long *)` → 그 숫자를 **주소(포인터)** 로 타입 변환
3. 맨 앞 `*` → 포인터를 **역참조**해 그 주소의 **값**에 접근

이제 GPIO 출력 편과 똑같이 비트 연산으로 설정한다.

```c
GPIOD_MODER |= (1 << 6);   // MODER 6번 비트 SET → PD3 출력 모드(01)
GPIOD_ODR   |= (1 << 3);   // PD3 = High
```

- `1 << 6`은 1을 왼쪽으로 6칸 시프트한 값. 초기값 0인 레지스터와 OR 연산하면 **6번 비트만 1로 세팅**된다.
- 같은 GPIO D의 레지스터들은 **베이스가 같고 오프셋만 다르다.**

---

## 5. 구조체로 깔끔하게 — CMSIS가 쓰는 방식

> **주의**
> 위처럼 매 레지스터를 일일이 포인터 캐스팅하면 지저분하고, 복사-붙여넣기 중 실수하기 쉽다. 실제 프로젝트는 설정할 게 많아서 더 위험하다.

더 나은 방법은 **구조체**다. GPIO 레지스터들은 메모리에 **4바이트씩 연속 배치**돼 있다는 점을 이용한다. 구조체 멤버를 순서대로 선언하면, 각 멤버의 주소가 자동으로 4바이트씩 차이 나서 **오프셋과 정확히 일치**한다.

```c
typedef struct {
    volatile unsigned long MODER;     // +0x00
    volatile unsigned long OTYPER;    // +0x04
    volatile unsigned long OSPEEDR;   // +0x08
    volatile unsigned long PUPDR;     // +0x0C
    volatile unsigned long IDR;       // +0x10
    volatile unsigned long ODR;       // +0x14
    // ...
} GPIO_TypeDef;

#define GPIOD  ((GPIO_TypeDef *)GPIOD_BASE)
```

`GPIOD`는 베이스 주소를 가리키는 구조체 포인터다. `GPIOD->MODER`는 시작 주소(+0x00), `GPIOD->ODR`은 +0x14를 자동으로 가리킨다.

```c
GPIOD->MODER |= (1 << 6);   // 지난 편과 완전히 동일한 코드
```

> 이렇게 하면 GPIO 출력 편에서 쓴 `GPIOD->MODER` 문법이 **어디서 나온 것인지** 완전히 이해된다.

---

## 6. 결론 — CMSIS 헤더가 이걸 다 해 준다

이 모든 베이스 주소·오프셋·구조체 정의는 **CMSIS 헤더(`stm32f767xx.h`)에 이미 다 들어 있다.** 그래서 앞으로 실습에서는 직접 만들지 않고, 헤더에 정의된 `GPIOD`, `RCC` 등을 가져다 쓴다.

- 특히 헤더의 구조체들은 이 강의에서 본 것처럼 **메모리 레이아웃에 정확히 맞게** 설계돼 있다.
- 우리가 한 일은 "헤더가 내부적으로 무엇을 하는가"를 손으로 재현해 본 것.

- **한 줄 정의:** 레지스터 직접 접근은 메모리 맵에서 베이스 주소+오프셋으로 레지스터 주소를 구해, 포인터로 캐스팅·역참조해 읽고 쓰는 기법이다.
- **왜 필요:** 모든 레지스터는 특정 메모리 주소다. 주소만 알면 라이브러리 없이도 하드웨어를 직접 제어할 수 있고, CMSIS 헤더의 동작 원리를 이해할 수 있다.
- **동작:** 주변 장치는 0x4000_0000부터 버스별로 매핑된다. 레지스터는 32비트라 4바이트씩 연속 배치되고, (베이스+오프셋)을 `volatile unsigned long *`로 캐스팅한 뒤 `*`로 역참조해 접근한다.
- **비교:** 일일이 포인터 캐스팅하면 실수가 잦아, 연속 배치 특성을 이용한 구조체 매핑이 더 안전·간결하다. CMSIS 헤더가 바로 이 구조체 방식을 쓴다.
- **30초 통합 답변:**
  > STM32의 모든 레지스터는 메모리 맵상의 특정 주소입니다. 주변 장치는 0x4000_0000부터 AHB·APB 버스별로 매핑되고, 레퍼런스 매뉴얼의 레지스터 맵에서 각 레지스터의 오프셋을 알 수 있습니다. 레지스터가 32비트라 4바이트씩 연속 배치되므로, 베이스 주소에 오프셋을 더한 값을 volatile 포인터로 캐스팅하고 역참조하면 직접 읽고 쓸 수 있습니다. 다만 매번 캐스팅하면 지저분하고 실수가 잦아서, 연속 배치 특성을 이용해 멤버를 순서대로 선언한 구조체로 매핑하면 GPIOD->MODER 같은 깔끔한 문법으로 접근할 수 있습니다. CMSIS 헤더가 정확히 이 구조체 방식으로 모든 레지스터를 정의해 둔 것이고, 그래서 평소엔 헤더만 포함하면 됩니다.

벤더 제공 헤더 파일은 **MCU 제조사가 레지스터 주소, 비트 필드, 주변장치 매크로를 미리 정의해 둔 `.h` 파일**입니다. 주로 사용자가 레지스터 주소 매크로를 직접 작성하지 않고, 데이터시트와 대응되는 공식 이름을 그대로 쓰기 위해 사용합니다. 내부적으로는 `#include "lm4f120h5qr.h"`처럼 큰따옴표 include로 헤더 내용을 현재 `.c` 파일에 포함시키고, 그 안에 정의된 `GPIO_PORTF_DATA_R` 같은 매크로를 전처리 단계에서 치환하는 방식으로 동작합니다. 직접 만든 매크로와 비교하면 주소 정의를 반복해서 작성할 필요가 없고, 벤더가 제공한 표준 이름을 쓰므로 실수 가능성이 줄어듭니다. 실제로는 MCU 레지스터를 직접 제어하는 bare-metal embedded C 코드에서 특히 중요합니다.

## 한 줄 정의

벤더 제공 헤더 파일은 **MCU 제조사가 해당 칩의 레지스터와 비트 정의를 미리 매크로로 제공하는 헤더 파일**이다.

핵심 특성은 **사용자가 레지스터 주소 매크로를 직접 만들 필요를 줄여준다는 것**이다.

## 왜 필요한가

MCU의 레지스터 주소를 직접 매크로로 정의할 수도 있다.

```c
#define GPIOF_BASE       0x40025000
#define GPIO_PORTF_DATA  (*((unsigned int *)(GPIOF_BASE + 0x3FC)))
#define GPIO_PORTF_DIR   (*((unsigned int *)(GPIOF_BASE + 0x400)))
#define GPIO_PORTF_DEN   (*((unsigned int *)(GPIOF_BASE + 0x51C)))
```

하지만 실제 MCU에는 GPIO뿐 아니라 UART, Timer, ADC, PWM, Interrupt Controller 등 많은 주변장치가 있고, 각 주변장치마다 여러 레지스터가 있다. 이것을 사용자가 전부 직접 작성하면 다음 문제가 생긴다.

- 주소 오타 가능성이 높다.
- 데이터시트와 코드 이름이 불일치할 수 있다.
- 프로젝트마다 동일한 매크로를 반복 작성하게 된다.
- `volatile` 같은 중요한 타입 한정자를 빠뜨릴 수 있다.

그래서 벤더는 칩별 헤더 파일을 제공한다. 강의 노트의 예시는 Stellaris Launchpad 보드의 칩인 `LM4F120H5QR`에 대응하는 `lm4f120h5qr.h`이다.

## 동작 원리

헤더 파일은 `.c` 파일에 직접 컴파일되는 파일이라기보다, `#include`를 통해 다른 C 소스 파일 안으로 포함되도록 설계된 파일이다.

사용 예:

```c
#include "lm4f120h5qr.h"
```

여기서 큰따옴표 `"..."`는 보통 **프로젝트 내부 또는 지정된 include path에서 헤더를 찾으라**는 의미로 사용된다. 반대로 표준 라이브러리 헤더는 보통 꺾쇠괄호 `<...>`를 쓴다.

```c
#include <stdint.h>
```

전처리 단계에서 `#include "lm4f120h5qr.h"`는 해당 헤더 파일의 내용을 현재 위치에 텍스트로 포함시킨다. 그 결과, 헤더 안에 정의된 매크로를 현재 `.c` 파일에서 바로 사용할 수 있다.

예:

```c
#include "lm4f120h5qr.h"

GPIO_PORTF_DATA_R = 0x02;
```

개념적으로는 `lm4f120h5qr.h` 안에 이미 다음과 같은 매크로가 정의되어 있는 것과 같다.

```c
#define GPIO_PORTF_DATA_R  (*((volatile unsigned long *)0x400253FC))
```

따라서 사용자는 직접 주소를 계산하거나 매크로를 작성하지 않아도 된다.

## 언제 쓰는가 / 언제 피하는가

- **쓰는 경우:** 특정 MCU의 레지스터를 직접 제어하는 bare-metal C 코드에서는 보통 벤더 제공 헤더를 사용한다.

```c
#include "lm4f120h5qr.h"

SYSCTL_RCGCGPIO_R |= 0x20;
GPIO_PORTF_DIR_R  |= 0x0E;
GPIO_PORTF_DEN_R  |= 0x0E;
GPIO_PORTF_DATA_R  = 0x02;
```

- **피하는 경우:** 다른 MCU로 쉽게 옮겨야 하는 상위 레벨 로직에서는 벤더 헤더 이름과 레지스터 매크로에 직접 의존하는 코드를 넓게 퍼뜨리지 않는 편이 좋다. 이런 경우에는 하드웨어 의존 코드를 드라이버 계층에 모으고, 나머지 코드는 추상화된 API를 사용하게 만든다.

예:

```c
led_on(LED_RED);
led_off(LED_RED);
```

이런 함수 내부에서만 `GPIO_PORTF_DATA_R` 같은 벤더 매크로를 쓰면 이식성이 좋아진다.

## 대표 예시

직접 작성한 매크로:

```c
#define MY_GPIO_PORTF_DATA  (*((unsigned int *)0x400253FC))
```

벤더 헤더 파일 사용:

```c
#include "lm4f120h5qr.h"

GPIO_PORTF_DATA_R = 0x02;
```

벤더 헤더 안의 매크로는 보통 다음과 같은 형태다.

```c
#define GPIO_PORTF_DATA_R  (*((volatile unsigned long *)0x400253FC))
```

직접 만든 매크로와 비교했을 때 중요한 차이는 다음 두 가지다.

```c
// 직접 작성
#define MY_REG  (*((unsigned int *)0x40025000))

// 벤더 헤더
#define HW_REG  (*((volatile unsigned long *)0x40025000))
```

1. `unsigned int` 대신 `unsigned long`을 쓸 수 있다.
2. 더 중요한 차이는 `volatile`이 붙어 있다는 점이다.

MMIO 레지스터는 하드웨어 이벤트로 값이 바뀔 수 있으므로, 컴파일러가 값을 캐싱하거나 접근을 제거하면 안 된다. 그래서 벤더 헤더의 레지스터 매크로에는 보통 `volatile`이 포함된다.

## 비교 / 대안

| 비교 대상 | 핵심 차이 |
|----------|-----------|
| 직접 작성 매크로 | 학습에는 좋지만 주소 오타, 타입 누락, `volatile` 누락 위험이 있다. |
| 벤더 제공 헤더 파일 | 칩 제조사가 제공한 레지스터 이름과 주소 정의를 그대로 사용한다. |
| CMSIS 헤더 | ARM Cortex 계열에서 더 표준화된 코어/디바이스 접근 방식을 제공하는 경우가 있다. |
| 드라이버 라이브러리 | 레지스터를 직접 만지지 않고 함수 API로 주변장치를 제어한다. 편하지만 내부 동작이 덜 직접적으로 보일 수 있다. |

## 꼬리질문 예상

- **Q:** 왜 `#include "lm4f120h5qr.h"`에서 큰따옴표를 쓰나요?
  **A:** 이 헤더는 표준 라이브러리 헤더가 아니라 프로젝트에 추가한 칩 전용 헤더이기 때문이다. 큰따옴표 include는 보통 현재 프로젝트나 지정된 include path에서 파일을 찾을 때 사용한다.

- **Q:** 벤더 헤더를 쓰면 직접 매크로를 아예 몰라도 되나요?
  **A:** 사용은 쉬워지지만 원리는 알아야 한다. 벤더 헤더도 결국 `#define` 매크로로 레지스터 주소를 정의하고, 전처리 단계에서 치환된다.

- **Q:** 벤더 헤더의 레지스터 매크로에는 왜 `volatile`이 붙나요?
  **A:** MMIO 레지스터는 프로그램 명령 없이도 하드웨어에 의해 값이 바뀔 수 있기 때문이다. `volatile`은 컴파일러가 해당 접근을 캐싱하거나 제거하지 못하게 한다.

- **Q:** `GPIO_PORTF_DATA_R` 같은 이름은 어디서 오나요?
  **A:** 벤더가 데이터시트의 레지스터 이름과 주소 정보를 기반으로 헤더 파일에 정의해 둔 이름이다.

## 자주 하는 오해

- **오해:** 벤더 헤더 파일은 특별한 컴파일러 기능이다.
  - **정확히는:** 헤더 파일 자체는 일반 텍스트 파일이고, `#include`가 전처리 단계에서 그 내용을 현재 소스 파일에 포함시킨다. 그 안의 레지스터 이름들도 대부분 매크로 정의다.

- **오해:** 벤더 헤더를 쓰면 런타임에 헤더 파일을 불러온다.
  - **정확히는:** `#include`는 컴파일 전에 처리된다. 런타임에는 헤더 파일을 읽는 일이 없다.

- **오해:** 큰따옴표 include와 꺾쇠괄호 include는 완전히 같은 의미다.
  - **정확히는:** 둘 다 헤더를 포함하지만, 일반적으로 큰따옴표는 프로젝트/사용자 헤더, 꺾쇠괄호는 표준 또는 시스템 헤더에 사용한다. 실제 검색 경로의 세부 동작은 컴파일러 설정에 의존할 수 있다.

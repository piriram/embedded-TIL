# `volatile` 키워드

> 출처: `붙여넣은 마크다운(1)(7).md`
> 최종 갱신: 확인 불가

---

## 30초 통합 답변

> 면접 직전 이것만 소리내어 읽는다. 입에 붙을 때까지.

`volatile`은 **이 객체의 값이 프로그램 명령과 무관하게 자발적으로 바뀔 수 있다고 컴파일러에 알리는 C 타입 한정자**입니다. 주로 IO 레지스터, 인터럽트 핸들러가 갱신하는 변수, busy-wait delay loop처럼 컴파일러 최적화가 실제 동작을 깨뜨릴 수 있는 대상을 위해 사용합니다. 내부적으로는 해당 객체에 대한 읽기와 쓰기를 소스 코드에 적힌 대로 실제 메모리 접근 명령으로 남기도록 강제합니다. 일반 변수와 비교하면 일반 변수는 컴파일러가 CPU 레지스터에 캐싱하거나 불필요한 접근을 제거할 수 있지만, `volatile` 객체는 그런 캐싱·재배치·제거 최적화가 제한됩니다. 실제로는 GPIO 입력 레지스터처럼 스위치나 인터럽트에 의해 값이 바뀌는 MMIO 레지스터에서 특히 중요합니다.

## 한 줄 정의

`volatile`은 **객체의 값이 프로그램 흐름 밖에서 바뀔 수 있음을 컴파일러에 알리는 타입 한정자**이다.

핵심 특성은 **소스 코드의 읽기·쓰기를 실제 메모리 접근으로 유지하게 만든다는 것**이다.

## 왜 필요한가

컴파일러는 일반 변수에 대해 공격적인 최적화를 할 수 있다.

예를 들어 컴파일러는 다음과 같이 판단할 수 있다.

- "이 변수는 코드상 바뀌지 않는다."
- "이 값을 매번 메모리에서 다시 읽을 필요가 없다."
- "이 루프는 결과에 영향을 주지 않으니 제거해도 된다."
- "메모리 접근 대신 CPU 레지스터에 보관해도 된다."

일반 메모리 변수라면 이런 최적화가 대부분 안전하다. 그러나 IO 레지스터나 인터럽트 관련 변수에서는 안전하지 않을 수 있다.

예를 들어 GPIO 입력 레지스터는 프로그램이 대입하지 않아도, 사용자가 스위치를 누르면 하드웨어가 값을 바꾼다. 컴파일러가 이 값을 한 번만 읽고 CPU 레지스터에 캐싱하면, 이후 스위치 상태 변화를 보지 못할 수 있다.

따라서 이런 객체에는 `volatile`을 붙여 컴파일러에게 다음 사실을 알려야 한다.

```text
이 값은 네가 보기에 코드상 그대로여도,
외부 하드웨어나 인터럽트에 의해 언제든 바뀔 수 있다.
```

## 동작 원리

`volatile`이 붙은 객체에 대해 컴파일러는 소스 코드에 적힌 읽기와 쓰기를 함부로 생략하거나 재사용하면 안 된다.

예:

```c
#define GPIO_PORTF_DATA_R  (*((volatile unsigned long *)0x400253FC))
```

사용 코드:

```c
unsigned long value;

value = GPIO_PORTF_DATA_R;
value = GPIO_PORTF_DATA_R;
```

`volatile`이 없으면 컴파일러는 두 번째 읽기가 첫 번째와 같다고 판단해 메모리 접근을 줄일 수 있다. 하지만 `volatile`이 있으면 두 줄은 각각 실제 메모리 읽기로 남아야 한다.

개념적으로는 다음 차이다.

| 구분 | 컴파일러가 할 수 있는 일 |
|------|--------------------------|
| 일반 객체 | 값을 CPU 레지스터에 캐싱하거나, 중복 읽기·쓰기를 제거할 수 있다. |
| `volatile` 객체 | 소스 코드의 각 읽기·쓰기를 실제 접근으로 유지해야 한다. |

다만 `volatile`은 CPU 캐시 전체를 끄거나, 원자성을 보장하거나, 멀티스레드 동기화를 완성하는 기능은 아니다. 정확한 의미는 **컴파일러 최적화에 대한 제약**이다.

## IO 레지스터에 필수인 이유

MMIO 레지스터는 메모리 주소처럼 접근하지만, 실제로는 하드웨어 장치와 연결되어 있다.

예를 들어 GPIO 입력 레지스터의 특정 비트가 보드의 스위치와 연결되어 있다면 다음 일이 가능하다.

```text
사용자가 스위치를 누름
-> 하드웨어가 GPIO 입력 레지스터의 비트를 변경
-> 프로그램 명령 없이도 레지스터 값이 바뀜
```

이 변화는 C 코드의 대입문으로 발생하지 않는다. 컴파일러 입장에서는 "아무도 이 값을 바꾸지 않았다"고 오해할 수 있다.

따라서 IO 레지스터 매크로는 보통 다음처럼 `volatile` 포인터 역참조 형태로 정의된다.

```c
#define GPIO_PORTF_DATA_R  (*((volatile unsigned long *)0x400253FC))
```

이 정의는 컴파일러에게 다음을 강제한다.

- 레지스터를 읽으라고 쓰인 곳에서는 실제 load 명령을 만든다.
- 레지스터에 쓰라고 쓰인 곳에서는 실제 store 명령을 만든다.
- 이전에 읽은 값을 재사용하지 않는다.
- "겉보기에는 불필요한 접근"이라고 제거하지 않는다.

## delay loop 제거 사례

`volatile`은 IO 레지스터뿐 아니라 일반 변수에도 필요할 수 있다. 대표적인 예가 busy-wait delay loop다.

```c
unsigned int counter;

for (counter = 0; counter < 1000000; ++counter) {
}
```

이 루프는 사람 입장에서는 시간을 지연시키기 위한 코드다. 하지만 컴파일러 입장에서는 루프 안에서 의미 있는 결과가 만들어지지 않는다.

`counter`의 값이 이후 사용되지 않는다면 컴파일러는 다음처럼 판단할 수 있다.

```text
이 루프는 최종 프로그램 결과에 영향이 없다.
따라서 제거해도 된다.
```

최적화 레벨을 올리면 실제로 delay loop가 제거될 수 있다. 강의 노트의 사례에서는 LED ON/OFF 사이의 delay loop가 사라져 LED가 기대한 방식으로 깜빡이지 않는다.

해결 방법:

```c
volatile unsigned int counter;

for (counter = 0; counter < 1000000; ++counter) {
}
```

또는 같은 의미로 다음처럼 쓸 수 있다.

```c
unsigned int volatile counter;
```

이제 `counter`의 증가와 비교는 실제 메모리 접근을 동반해야 하므로, 컴파일러가 루프를 통째로 제거하기 어렵다.

## 언제 쓰는가 / 언제 피하는가

- **쓰는 경우:** MMIO 레지스터, GPIO, UART, Timer, ADC 같은 peripheral register, 인터럽트 서비스 루틴이 변경하는 변수, 하드웨어 상태 플래그, busy-wait delay loop의 counter, 컴파일러가 보기에는 불필요하지만 실제 시간 지연이나 하드웨어 접근 의미가 있는 코드에 사용한다.

```c
volatile unsigned int counter;
```

```c
#define UART0_FR_R  (*((volatile unsigned long *)0x4000C018))
```

- **피하는 경우:** 일반 지역 변수, 단순 계산용 변수, 최적화를 막을 필요가 없는 데이터, 멀티스레드 동기화를 `volatile`만으로 해결하려는 경우에는 피한다.

`volatile`을 남발하면 컴파일러가 가능한 최적화를 하지 못한다. 또한 `volatile`은 atomic operation, mutex, memory barrier를 대체하지 않는다.

## 대표 예시

### 1. IO 레지스터 읽기

```c
#define GPIO_PORTF_DATA_R  (*((volatile unsigned long *)0x400253FC))

if (GPIO_PORTF_DATA_R & 0x10) {
    // switch input is high
}
```

여기서 `GPIO_PORTF_DATA_R`는 하드웨어 입력에 따라 바뀔 수 있다. 따라서 매번 실제 레지스터를 읽어야 한다.

### 2. IO 레지스터 쓰기

```c
GPIO_PORTF_DATA_R = 0x02;
```

이 코드는 단순 변수 대입처럼 보이지만, 실제로는 특정 하드웨어 주소에 store 명령을 보내 LED나 GPIO 출력 상태를 바꾸는 동작이다.

### 3. delay loop

```c
volatile unsigned int counter;

for (counter = 0; counter < 1000000; ++counter) {
}
```

이 루프는 계산 결과가 아니라 시간 지연 자체가 목적이다. `volatile`이 없으면 최적화 과정에서 제거될 수 있다.

## 비교 / 대안

| 비교 대상 | 핵심 차이 |
|----------|-----------|
| 일반 변수 | 컴파일러가 값을 캐싱하거나, 중복 접근을 제거하거나, 루프를 제거할 수 있다. |
| `volatile` 변수 | 소스 코드의 읽기·쓰기를 실제 메모리 접근으로 유지해야 한다. |
| `const` | 값을 수정하지 않겠다는 의미다. 외부에서 값이 바뀔 수 있다는 의미가 아니다. |
| `atomic` | 동시성에서 원자적 연산과 메모리 순서를 다룬다. `volatile`과 목적이 다르다. |
| memory barrier | CPU/컴파일러 재정렬을 더 강하게 제어하는 동기화 장치다. `volatile`만으로 대체할 수 없다. |

## 꼬리질문 예상

- **Q:** `volatile`은 무엇을 컴파일러에 알려주나요?
  **A:** 이 객체의 값이 프로그램 명령과 무관하게 외부 요인으로 바뀔 수 있음을 알려준다.

- **Q:** IO 레지스터에 왜 `volatile`이 필요한가요?
  **A:** GPIO 입력, 스위치, 인터럽트, 하드웨어 상태 변화는 C 코드의 대입문 없이도 레지스터 값을 바꿀 수 있기 때문이다. 컴파일러가 값을 캐싱하면 실제 하드웨어 상태를 놓칠 수 있다.

- **Q:** `volatile`이 붙으면 정확히 무엇이 강제되나요?
  **A:** 소스 코드에 나타난 각 읽기·쓰기가 실제 메모리 접근으로 남아야 한다. 컴파일러가 해당 접근을 임의로 캐싱·제거·재사용하기 어렵다.

- **Q:** delay loop는 왜 사라질 수 있나요?
  **A:** 컴파일러가 보기에 루프의 계산 결과가 프로그램의 관찰 가능한 결과에 영향을 주지 않으면, 최적화 과정에서 제거할 수 있기 때문이다.

- **Q:** `volatile`은 멀티스레드 동기화에 충분한가요?
  **A:** 아니다. `volatile`은 주로 컴파일러 최적화를 제한하는 장치다. 원자성이나 스레드 간 happens-before 관계를 보장하려면 atomic, mutex, memory barrier 같은 별도 동기화가 필요하다.

## 자주 하는 오해

- **오해:** `volatile`은 변수를 빠르게 만든다.
  - **정확히는:** 오히려 최적화를 제한하므로 성능이 낮아질 수 있다. 목적은 속도가 아니라 정확성이다.

- **오해:** `volatile`을 붙이면 값이 절대 사라지지 않는다.
  - **정확히는:** 컴파일러가 해당 접근을 함부로 제거하거나 캐싱하지 못하게 할 뿐이다. 하드웨어 값 자체의 안정성이나 원자성을 보장하지는 않는다.

- **오해:** `volatile`은 인터럽트와 멀티스레드 문제를 모두 해결한다.
  - **정확히는:** 인터럽트가 변경하는 단순 플래그를 컴파일러가 캐싱하지 못하게 하는 데는 필요할 수 있다. 하지만 복합 연산의 원자성, 경쟁 상태, 메모리 순서까지 해결하지는 않는다.

- **오해:** delay loop는 C 코드에 있으니 반드시 실행된다.
  - **정확히는:** 컴파일러가 루프의 결과가 관찰 가능하지 않다고 판단하면 제거할 수 있다. 지연 자체가 목적이면 `volatile` counter 또는 하드웨어 timer 같은 더 명확한 방법이 필요하다.

## 자주 놓치는 정확 표현

| 모호한 말 | 정확한 용어 |
|----------|-------------|
| 값이 갑자기 바뀐다 | 프로그램 명령과 무관하게 외부 요인으로 값이 바뀔 수 있다 |
| 최적화를 못 하게 한다 | 해당 객체의 읽기·쓰기에 대한 캐싱·제거·재사용을 제한한다 |
| 메모리에 항상 있다 | 소스 코드의 volatile 접근을 실제 메모리 접근으로 유지해야 한다 |
| 인터럽트 변수에는 volatile | 인터럽트 핸들러와 main context가 공유하고, 컴파일러 캐싱 문제가 있는 객체에는 volatile이 필요할 수 있다 |
| delay loop를 살린다 | 루프 counter 접근을 관찰 가능한 volatile 접근으로 만들어 제거를 막는다 |
| volatile이면 thread-safe | volatile은 원자성이나 동기화를 보장하지 않는다 |

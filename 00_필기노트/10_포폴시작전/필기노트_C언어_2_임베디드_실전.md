# C언어 심화 2 — 임베디드 실전

용도: A4 세로 반 접기 2열 손필기

규칙:

- 내용이 길면 다음 페이지로 넘김
- 들여쓰기 없음
- 파랑: 제목, 번호, 핵심 키워드
- 검정: 설명, 예시, cf
- 빨강: 면접 주의, 헷갈리는 점

## 1페이지: 고정폭 타입·비트 연산

<span style="color:#1d4ed8">주제: C 코드를 하드웨어 bit와 안전하게 연결하기</span><br>
<span style="color:#1d4ed8">1. 고정폭 정수 타입</span><br>
<span style="color:#111827">a. #include &lt;stdint.h&gt;의 uint8_t, int16_t, uint32_t 등</span><br>
<span style="color:#111827">b. 타입 이름에 bit 폭과 signed/unsigned 의도가 드러남</span><br>
<span style="color:#111827">c. 레지스터, 통신 payload, 파일 형식처럼 폭이 중요한 곳에 우선</span><br>
<span style="color:#111827">d. size_t는 객체 크기·배열 인덱스에 맞는 unsigned 타입</span><br>
<span style="color:#dc2626">※ int의 크기는 환경 의존적; 프로토콜/레지스터에는 int라고 가정하지 않음</span><br>
<br>
<span style="color:#1d4ed8">2. literal과 shift의 기본</span><br>
<span style="color:#111827">a. 1U, 0x20U처럼 unsigned suffix를 써서 의도를 명확히 함</span><br>
<span style="color:#111827">b. 1U &lt;&lt; n은 n번 bit mask를 만드는 기본 표현</span><br>
<span style="color:#111827">c. shift 수는 음수이거나 타입 폭 이상이면 안 됨</span><br>
<span style="color:#111827">d. signed 값의 left shift와 overflow는 피하고 unsigned mask를 사용</span><br>
<span style="color:#dc2626">※ bit 연산 전에 대상 레지스터의 폭과 bit 번호를 데이터시트로 확인</span><br>
<br>
<span style="color:#1d4ed8">3. mask로 bit 조작</span><br>
<span style="color:#111827">a. set: reg |= MASK</span><br>
<span style="color:#111827">b. clear: reg &amp;= ~MASK</span><br>
<span style="color:#111827">c. toggle: reg ^= MASK</span><br>
<span style="color:#111827">d. check: (reg &amp; MASK) != 0U</span><br>
<span style="color:#111827">e. field 변경: (reg &amp; ~FIELD_MASK) | ((value &lt;&lt; SHIFT) &amp; FIELD_MASK)</span><br>
<span style="color:#dc2626">※ field 값은 먼저 mask해서 이웃 bit를 침범하지 않게 함</span><br>
<br>
<span style="color:#1d4ed8">예: 3-bit mode field</span><br>
<span style="color:#111827">#define MODE_SHIFT  4U</span><br>
<span style="color:#111827">#define MODE_MASK   (0x7U &lt;&lt; MODE_SHIFT)</span><br>
<span style="color:#111827">reg = (reg &amp; ~MODE_MASK) | ((mode &amp; 0x7U) &lt;&lt; MODE_SHIFT);</span><br>
<span style="color:#dc2626">※ 레지스터의 read-modify-write 자체는 동시성 안전을 보장하지 않음</span><br>

## 2페이지: 전처리기·inline·volatile

<span style="color:#1d4ed8">4. 전처리기와 macro</span><br>
<span style="color:#111827">a. #include, #define, #if는 compiler 전의 텍스트 처리</span><br>
<span style="color:#111827">b. macro는 함수 호출이 아니라 인수를 포함한 텍스트 치환</span><br>
<span style="color:#111827">c. 표현식 macro는 인수와 전체 식을 모두 괄호로 감쌈</span><br>
<span style="color:#111827">- #define SQR(x) ((x) * (x))</span><br>
<span style="color:#111827">d. 여러 문장 macro는 do { ... } while (0)으로 한 문장처럼 묶음</span><br>
<span style="color:#dc2626">※ SQR(i++)는 i++를 두 번 평가: 괄호만으로 side effect를 해결 못 함</span><br>
<br>
<span style="color:#1d4ed8">5. macro와 static inline</span><br>
<span style="color:#111827">a. static inline 함수는 타입 검사·함수 scope·인수 한 번 평가를 가짐</span><br>
<span style="color:#111827">b. inline은 실제 호출 제거를 보장하는 명령이 아니라 최적화 힌트</span><br>
<span style="color:#111827">c. 작은 헤더 유틸리티는 static inline이 안전한 선택</span><br>
<span style="color:#111827">d. macro는 조건부 컴파일, #, ##, __FILE__/__LINE__처럼 고유한 역할에 사용</span><br>
<span style="color:#dc2626">※ 성능은 inline이라는 단어가 아니라 build 결과와 profiler로 확인</span><br>
<br>
<span style="color:#1d4ed8">6. volatile의 역할</span><br>
<span style="color:#111827">a. 이 값은 코드 흐름 밖에서 바뀔 수 있으니 매 접근을 실제로 수행하라는 뜻</span><br>
<span style="color:#111827">b. MMIO register, ISR과 main이 공유하는 flag 등에 사용</span><br>
<span style="color:#111827">c. compiler의 읽기 캐싱·쓰기 제거·접근 합치기를 막는 목적</span><br>
<span style="color:#111827">d. volatile uint32_t *reg = (volatile uint32_t *)ADDR;</span><br>
<span style="color:#dc2626">※ volatile은 hardware delay, memory barrier, atomicity를 보장하지 않음</span><br>
<br>
<span style="color:#1d4ed8">7. const volatile MMIO</span><br>
<span style="color:#111827">a. const: 이 코드 경로가 쓰지 못하게 함</span><br>
<span style="color:#111827">b. volatile: 하드웨어 변화 때문에 매번 읽음</span><br>
<span style="color:#111827">c. 읽기 전용 status/data register에 const volatile 사용</span><br>
<span style="color:#dc2626">※ const volatile은 값이 안 바뀐다는 뜻이 아님: 하드웨어는 바꿀 수 있음</span><br>

## 3페이지: 구조체·padding·CMSIS

<span style="color:#1d4ed8">8. 구조체 layout과 alignment</span><br>
<span style="color:#111827">a. CPU/ABI는 int 같은 멤버를 특정 배수 주소에 두려 함</span><br>
<span style="color:#111827">b. 그래서 멤버 사이와 끝에 padding이 들어갈 수 있음</span><br>
<span style="color:#111827">c. sizeof(struct)는 멤버 크기 합보다 클 수 있음</span><br>
<span style="color:#111827">d. offsetof()로 target의 실제 offset을 확인</span><br>
<span style="color:#dc2626">※ 구조체 전체를 memcmp하거나 raw 통신으로 보내면 padding 값이 문제될 수 있음</span><br>
<br>
<span style="color:#1d4ed8">9. packed와 bit-field의 한계</span><br>
<span style="color:#111827">a. packed는 padding을 줄이지만 unaligned access로 성능 저하·fault 위험</span><br>
<span style="color:#111827">b. bit-field는 상태를 읽기 좋게 표현할 수 있음</span><br>
<span style="color:#111827">c. 하지만 bit 배치 방향, 저장 단위, padding, signedness가 구현 의존적</span><br>
<span style="color:#111827">d. 통신 packet과 register bit에는 bit-field보다 mask/shift를 우선</span><br>
<span style="color:#dc2626">※ 정확한 binary layout은 compiler가 아니라 protocol·datasheet가 기준</span><br>
<br>
<span style="color:#1d4ed8">10. CMSIS register 구조체</span><br>
<span style="color:#111827">a. peripheral base address를 register-block 구조체 포인터로 봄</span><br>
<span style="color:#111827">b. GPIOA-&gt;ODR은 base + ODR offset의 volatile word 접근</span><br>
<span style="color:#111827">c. 멤버 순서와 reserved field가 데이터시트 register map과 정확히 맞아야 함</span><br>
<span style="color:#111827">d. 직접 재작성보다 벤더 CMSIS device header를 사용</span><br>
<span style="color:#dc2626">※ 구조체는 register word offset용, 개별 bit는 vendor macro/mask로 조작</span><br>
<br>
<span style="color:#1d4ed8">11. RMW와 set/clear register</span><br>
<span style="color:#111827">a. reg |= mask는 읽기 → 수정 → 쓰기의 read-modify-write</span><br>
<span style="color:#111827">b. ISR/DMA/다른 코드가 사이에 값을 바꾸면 update가 유실될 수 있음</span><br>
<span style="color:#111827">c. MCU가 제공하면 BSRR, SET, CLR 같은 전용 alias register를 사용</span><br>
<span style="color:#dc2626">※ volatile ODR |= mask도 경쟁 조건을 막아 주지 않음</span><br>

## 4페이지: atomic·race condition·점검 순서

<span style="color:#1d4ed8">12. race condition</span><br>
<span style="color:#111827">a. 둘 이상의 실행 주체가 공유 데이터를 동시에 다뤄 결과가 실행 순서에 따라 달라지는 문제</span><br>
<span style="color:#111827">b. counter++는 read → add → write의 여러 단계라 중간에 끼어들 수 있음</span><br>
<span style="color:#111827">c. ISR/main, thread/thread, DMA와 CPU의 공유 상태에서 발생 가능</span><br>
<span style="color:#dc2626">※ volatile counter++도 원자적 연산이 아니므로 race condition 해결책이 아님</span><br>
<br>
<span style="color:#1d4ed8">13. C11 atomic과 critical section</span><br>
<span style="color:#111827">a. #include &lt;stdatomic.h&gt;, _Atomic uint32_t count;</span><br>
<span style="color:#111827">b. atomic_fetch_add(&amp;count, 1U)는 한 객체의 원자적 RMW를 표현</span><br>
<span style="color:#111827">c. 한 flag/카운터에는 atomic이 적합할 수 있음</span><br>
<span style="color:#111827">d. 여러 변수의 일관성·긴 작업은 mutex 또는 짧은 critical section으로 보호</span><br>
<span style="color:#111827">e. toolchain/target이 C11 atomic을 지원하는지, lock-free인지 확인</span><br>
<span style="color:#dc2626">※ ISR에서는 blocking mutex를 쓰지 않으며, critical section은 짧게 유지</span><br>
<br>
<span style="color:#1d4ed8">14. 레지스터 코드 점검 순서</span><br>
<span style="color:#111827">1) 데이터시트에서 register 주소, access 권한, bit 정의 확인</span><br>
<span style="color:#111827">2) uint32_t 등 폭이 맞는 unsigned 타입과 U suffix 사용</span><br>
<span style="color:#111827">3) mask/shift로 필요한 field만 변경</span><br>
<span style="color:#111827">4) volatile, const volatile을 access 성격에 맞게 사용</span><br>
<span style="color:#111827">5) RMW 경쟁 가능성 확인 후 BSRR/SET/CLR 또는 보호 구간 선택</span><br>
<span style="color:#dc2626">※ 동작 코드보다 access 권한·동시성·검증 방법을 함께 말해야 함</span><br>
<br>
<span style="color:#1d4ed8">Q. 꼬리질문</span><br>
<span style="color:#111827">- volatile이 atomic을 보장하지 않는 이유는?</span><br>
<span style="color:#111827">- bit-field보다 mask/shift가 안전한 경우는?</span><br>
<span style="color:#111827">- packed를 기본으로 쓰면 안 되는 이유는?</span><br>
<span style="color:#111827">- ODR |= mask 대신 BSRR을 쓰는 이유는?</span><br>
<span style="color:#111827">- atomic 하나로 여러 변수 상태를 보호할 수 없는 이유는?</span><br>

## 면접 30초 답변

<span style="color:#1d4ed8">임베디드 C에서 중요한 점</span><br>
<span style="color:#111827">임베디드 C에서는 레지스터와 통신 데이터의 폭과 bit 위치가 중요하므로 uint32_t 같은 고정폭 타입, unsigned mask, shift 연산을 사용합니다.</span><br>
<span style="color:#111827">하드웨어가 바꾸는 레지스터는 volatile로 매 접근을 유지하고, 읽기 전용 상태 레지스터는 const volatile로 표현합니다. 다만 volatile은 원자성을 보장하지 않습니다.</span><br>
<span style="color:#111827">구조체는 CMSIS처럼 register offset을 표현하는 데 쓰되, 정확한 bit layout은 mask/shift로 다룹니다.</span><br>
<span style="color:#dc2626">ISR이나 다른 실행 주체와 공유하는 값은 atomic, critical section, 전용 set/clear register 중 상황에 맞는 방법으로 보호합니다.</span><br>

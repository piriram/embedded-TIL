<span style="color:#1d4ed8">I. C언어 심화 2 — 임베디드 실전</span><br>
<br>
<span style="color:#1d4ed8">1. C 코드를 하드웨어 bit와 안전하게 연결하기</span><br>
<span style="color:#1d4ed8">1) 용어 설명</span><br>
<span style="color:#111827">① <strong>고정폭 타입</strong>(fixed-width integer): 저장할 bit 폭이 이름에 정해진 정수 타입</span><br>
<span style="color:#111827">② <strong>mask</strong>: 특정 bit 또는 field만 골라 읽고 바꾸기 위한 bit 패턴</span><br>
<span style="color:#111827">③ <strong>shift</strong>: bit를 원하는 위치로 옮겨 mask와 결합하는 연산</span><br>
<span style="color:#dc2626">! <strong>폭을 맞춘 뒤 → mask로 범위를 고르고 → shift로 위치를 맞춤</strong>이라고 먼저 잡기</span><br>
<br>
<span style="color:#1d4ed8">2) 고정폭 정수 타입</span><br>
<span style="color:#111827">① #include &lt;stdint.h&gt;의 uint8_t, int16_t, uint32_t 등</span><br>
<span style="color:#111827">② 타입 이름에 bit 폭과 signed/unsigned 의도가 드러남</span><br>
<span style="color:#111827">③ 레지스터, 통신 payload, 파일 형식처럼 폭이 중요한 곳에 우선</span><br>
<span style="color:#111827">④ size_t는 객체 크기·배열 인덱스에 맞는 unsigned 타입</span><br>
<span style="color:#dc2626">! <strong>int의 크기는 환경 의존적</strong>; 프로토콜/레지스터에는 int라고 가정하지 않음</span><br>
<br>
<span style="color:#1d4ed8">3) literal과 shift의 기본</span><br>
<span style="color:#111827">① 1U, 0x20U처럼 unsigned suffix를 써서 의도를 명확히 함</span><br>
<span style="color:#111827">② <strong>1U &lt;&lt; n</strong>은 n번 bit mask를 만드는 기본 표현</span><br>
<span style="color:#111827">③ shift 수는 음수이거나 타입 폭 이상이면 안 됨</span><br>
<span style="color:#111827">④ signed 값의 left shift와 overflow는 피하고 unsigned mask를 사용</span><br>
<span style="color:#dc2626">! bit 연산 전에 <strong>대상 레지스터의 폭과 bit 번호를 데이터시트로 확인</strong></span><br>
<br>
<span style="color:#1d4ed8">4) mask로 bit 조작</span><br>
<span style="color:#111827">① set: <strong>reg |= MASK</strong></span><br>
<span style="color:#111827">② clear: <strong>reg &amp;= ~MASK</strong></span><br>
<span style="color:#111827">③ toggle: <strong>reg ^= MASK</strong></span><br>
<span style="color:#111827">④ check: <strong>(reg &amp; MASK) != 0U</strong></span><br>
<span style="color:#111827">⑤ field 변경: <strong>(reg &amp; ~FIELD_MASK) | ((value &lt;&lt; SHIFT) &amp; FIELD_MASK)</strong></span><br>
<span style="color:#dc2626">! field 값은 먼저 mask해서 이웃 bit를 침범하지 않게 함</span><br>
<br>
<span style="color:#1d4ed8">ex) 3-bit mode field</span><br>
<span style="color:#111827">#define MODE_SHIFT  4U</span><br>
<span style="color:#111827">#define MODE_MASK   (0x7U &lt;&lt; MODE_SHIFT)</span><br>
<span style="color:#111827">reg = (reg &amp; ~MODE_MASK) | ((mode &amp; 0x7U) &lt;&lt; MODE_SHIFT);</span><br>
<span style="color:#dc2626">! <strong>read-modify-write 자체는 동시성 안전을 보장하지 않음</strong></span><br>
<br>
<span style="color:#1d4ed8">2. 전처리기와 접근 의미를 구분한다</span><br>
<span style="color:#1d4ed8">1) 전처리기와 macro</span><br>
<span style="color:#111827">① #include, #define, #if는 compiler 전의 텍스트 처리</span><br>
<span style="color:#111827">② <strong>macro는 함수 호출이 아니라 인수를 포함한 텍스트 치환</strong></span><br>
<span style="color:#111827">③ 표현식 macro는 인수와 전체 식을 모두 괄호로 감쌈</span><br>
<span style="color:#111827">ex) #define SQR(x) ((x) * (x))</span><br>
<span style="color:#111827">④ 여러 문장 macro는 do { ... } while (0)으로 한 문장처럼 묶음</span><br>
<span style="color:#dc2626">! <strong>SQR(i++)는 i++를 두 번 평가</strong>: 괄호만으로 side effect를 해결 못 함</span><br>
<br>
<span style="color:#1d4ed8">2) macro와 static inline</span><br>
<span style="color:#111827">① <strong>static inline 함수</strong>는 타입 검사·함수 scope·인수 한 번 평가를 가짐</span><br>
<span style="color:#111827">② inline은 실제 호출 제거를 보장하는 명령이 아니라 최적화 힌트</span><br>
<span style="color:#111827">③ 작은 헤더 유틸리티는 static inline이 안전한 선택</span><br>
<span style="color:#111827">④ macro는 조건부 컴파일, #, ##, __FILE__/__LINE__처럼 고유한 역할에 사용</span><br>
<span style="color:#dc2626">! 성능은 inline이라는 단어가 아니라 build 결과와 profiler로 확인</span><br>
<br>
<span style="color:#1d4ed8">3) volatile의 역할</span><br>
<span style="color:#111827">① <strong>volatile</strong>: 이 값은 코드 흐름 밖에서 바뀔 수 있으니 매 접근을 실제로 수행하라는 뜻</span><br>
<span style="color:#111827">② MMIO register, ISR과 main이 공유하는 flag 등에 사용</span><br>
<span style="color:#111827">③ compiler의 읽기 캐싱·쓰기 제거·접근 합치기를 막는 목적</span><br>
<span style="color:#111827">④ volatile uint32_t *reg = (volatile uint32_t *)ADDR;</span><br>
<span style="color:#111827">cf) MMIO(Memory-Mapped I/O) = 하드웨어 레지스터를 메모리 주소처럼 읽고 쓰는 방식</span><br>
<span style="color:#dc2626">! <strong>volatile은 hardware delay, memory barrier, atomicity를 보장하지 않음</strong></span><br>
<br>
<span style="color:#1d4ed8">4) const volatile MMIO</span><br>
<span style="color:#111827">① <strong>const</strong>: 이 코드 경로가 쓰지 못하게 함</span><br>
<span style="color:#111827">② <strong>volatile</strong>: 하드웨어 변화 때문에 매번 읽음</span><br>
<span style="color:#111827">③ 읽기 전용 status/data register에 const volatile 사용</span><br>
<span style="color:#dc2626">! <strong>const volatile은 값이 안 바뀐다는 뜻이 아님</strong>: 하드웨어는 바꿀 수 있음</span><br>
<br>
<span style="color:#1d4ed8">3. 구조체는 layout을, mask는 bit를 표현한다</span><br>
<span style="color:#1d4ed8">1) 용어 설명</span><br>
<span style="color:#111827">① <strong>alignment</strong>: CPU/ABI가 특정 타입을 배치할 때 요구하는 주소 경계</span><br>
<span style="color:#111827">② <strong>padding</strong>: alignment를 맞추려고 구조체 멤버 사이·끝에 넣는 빈 byte</span><br>
<span style="color:#111827">③ <strong>CMSIS</strong>: MCU 레지스터 block과 core 접근을 표준화한 벤더 device header 기반</span><br>
<span style="color:#dc2626">! <strong>구조체 member 위치는 register word offset용이고, 개별 bit는 mask/shift로 다룸</strong></span><br>
<br>
<span style="color:#1d4ed8">2) 구조체 layout과 alignment</span><br>
<span style="color:#111827">① CPU/ABI는 int 같은 멤버를 특정 배수 주소에 두려 함</span><br>
<span style="color:#111827">② 그래서 멤버 사이와 끝에 padding이 들어갈 수 있음</span><br>
<span style="color:#111827">③ sizeof(struct)는 멤버 크기 합보다 클 수 있음</span><br>
<span style="color:#111827">④ offsetof()로 target의 실제 offset을 확인</span><br>
<span style="color:#dc2626">! 구조체 전체를 memcmp하거나 raw 통신으로 보내면 padding 값이 문제될 수 있음</span><br>
<br>
<span style="color:#1d4ed8">3) packed와 bit-field의 한계</span><br>
<span style="color:#111827">① packed는 padding을 줄이지만 unaligned access로 성능 저하·fault 위험</span><br>
<span style="color:#111827">② bit-field는 상태를 읽기 좋게 표현할 수 있음</span><br>
<span style="color:#111827">③ 하지만 bit 배치 방향, 저장 단위, padding, signedness가 구현 의존적</span><br>
<span style="color:#111827">④ 통신 packet과 register bit에는 bit-field보다 mask/shift를 우선</span><br>
<span style="color:#dc2626">! <strong>정확한 binary layout은 compiler가 아니라 protocol·datasheet가 기준</strong></span><br>
<br>
<span style="color:#1d4ed8">4) CMSIS register 구조체</span><br>
<span style="color:#111827">① peripheral base address를 register-block 구조체 포인터로 봄</span><br>
<span style="color:#111827">② GPIOA-&gt;ODR은 base + ODR offset의 volatile word 접근</span><br>
<span style="color:#111827">③ 멤버 순서와 reserved field가 데이터시트 register map과 정확히 맞아야 함</span><br>
<span style="color:#111827">④ 직접 재작성보다 벤더 CMSIS device header를 사용</span><br>
<span style="color:#dc2626">! 구조체는 register word offset용, 개별 bit는 vendor macro/mask로 조작</span><br>
<br>
<span style="color:#1d4ed8">5) RMW와 set/clear register</span><br>
<span style="color:#111827">① <strong>reg |= mask</strong>는 읽기 → 수정 → 쓰기의 read-modify-write</span><br>
<span style="color:#111827">② ISR/DMA/다른 코드가 사이에 값을 바꾸면 update가 유실될 수 있음</span><br>
<span style="color:#111827">③ MCU가 제공하면 <strong>BSRR, SET, CLR 같은 전용 alias register</strong>를 사용</span><br>
<span style="color:#dc2626">! <strong>volatile ODR |= mask도 경쟁 조건을 막아 주지 않음</strong></span><br>
<br>
<span style="color:#1d4ed8">4. 공유 상태는 volatile만으로 안전해지지 않는다</span><br>
<span style="color:#1d4ed8">1) race condition</span><br>
<span style="color:#111827">① <strong>race condition</strong>: 둘 이상의 실행 주체가 공유 데이터를 동시에 다뤄 결과가 실행 순서에 따라 달라지는 문제</span><br>
<span style="color:#111827">② counter++는 read → add → write의 여러 단계라 중간에 끼어들 수 있음</span><br>
<span style="color:#111827">③ ISR/main, thread/thread, DMA와 CPU의 공유 상태에서 발생 가능</span><br>
<span style="color:#dc2626">! <strong>volatile counter++도 원자적 연산이 아니므로 race condition 해결책이 아님</strong></span><br>
<br>
<span style="color:#1d4ed8">2) C11 atomic과 critical section</span><br>
<span style="color:#111827">① #include &lt;stdatomic.h&gt;, _Atomic uint32_t count;</span><br>
<span style="color:#111827">② <strong>atomic_fetch_add(&amp;count, 1U)</strong>는 한 객체의 원자적 RMW를 표현</span><br>
<span style="color:#111827">③ 한 flag/카운터에는 atomic이 적합할 수 있음</span><br>
<span style="color:#111827">④ 여러 변수의 일관성·긴 작업은 mutex 또는 짧은 critical section으로 보호</span><br>
<span style="color:#111827">⑤ toolchain/target이 C11 atomic을 지원하는지, lock-free인지 확인</span><br>
<span style="color:#dc2626">! <strong>ISR에서는 blocking mutex를 쓰지 않으며, critical section은 짧게 유지</strong></span><br>
<br>
<span style="color:#1d4ed8">3) 레지스터 코드 점검 순서</span><br>
<span style="color:#111827">① 데이터시트에서 register 주소, access 권한, bit 정의 확인</span><br>
<span style="color:#111827">② uint32_t 등 폭이 맞는 unsigned 타입과 U suffix 사용</span><br>
<span style="color:#111827">③ mask/shift로 필요한 field만 변경</span><br>
<span style="color:#111827">④ volatile, const volatile을 access 성격에 맞게 사용</span><br>
<span style="color:#111827">⑤ RMW 경쟁 가능성 확인 후 BSRR/SET/CLR 또는 보호 구간 선택</span><br>
<span style="color:#dc2626">! 동작 코드보다 access 권한·동시성·검증 방법을 함께 말해야 함</span><br>
<br>
<span style="color:#1d4ed8">5. 핵심 3줄</span><br>
<span style="color:#111827">1) <strong>레지스터와 통신 데이터는 uint32_t 같은 고정폭 타입과 unsigned mask/shift로 폭과 bit 위치를 명확히 한다.</strong></span><br>
<span style="color:#111827">2) <strong>volatile은 하드웨어나 ISR이 바꾸는 값의 접근을 유지하지만, atomicity·memory barrier·race condition 해결을 보장하지 않는다.</strong></span><br>
<span style="color:#111827">3) <strong>register word offset은 CMSIS 구조체로 표현하고, RMW 경쟁은 BSRR/SET/CLR·atomic·짧은 보호 구간으로 상황에 맞게 다룬다.</strong></span><br>
<br>
<span style="color:#1d4ed8">Q. volatile이 atomic을 보장하지 않는 이유는?</span><br>
<span style="color:#111827">A. volatile은 compiler가 접근을 생략하거나 합치지 않게 할 뿐이며, counter++처럼 여러 단계인 read-modify-write를 하나의 원자적 동작으로 만들지 않는다.</span><br>
<span style="color:#1d4ed8">Q. bit-field보다 mask/shift가 안전한 경우는?</span><br>
<span style="color:#111827">A. 통신 packet과 register bit처럼 정확한 binary layout이 필요한 경우다. bit-field의 배치 방향·저장 단위·padding은 구현 의존적이다.</span><br>
<span style="color:#1d4ed8">Q. packed를 기본으로 쓰면 안 되는 이유는?</span><br>
<span style="color:#111827">A. padding은 줄지만 unaligned access로 성능 저하나 fault가 생길 수 있고, 정확한 layout은 protocol·datasheet 기준으로 검증해야 한다.</span><br>
<span style="color:#1d4ed8">Q. ODR |= mask 대신 BSRR을 쓰는 이유는?</span><br>
<span style="color:#111827">A. ODR |= mask는 읽기 → 수정 → 쓰기 사이에 다른 실행 주체의 갱신을 잃을 수 있지만, BSRR은 전용 set/clear 접근으로 그 RMW 경쟁을 피할 수 있다.</span><br>
<span style="color:#1d4ed8">Q. atomic 하나로 여러 변수 상태를 보호할 수 없는 이유는?</span><br>
<span style="color:#111827">A. atomic은 한 객체의 원자적 연산에는 적합하지만, 여러 변수의 일관성이나 긴 작업은 mutex 또는 짧은 critical section으로 함께 보호해야 한다.</span><br>
<br>
<span style="color:#1d4ed8">6. 30초 면접 답변</span><br>
<span style="color:#111827">임베디드 C에서는 레지스터와 통신 데이터의 폭과 bit 위치가 중요하므로 uint32_t 같은 고정폭 타입, unsigned mask, shift 연산을 사용합니다.</span><br>
<span style="color:#111827">하드웨어가 바꾸는 레지스터는 volatile로 매 접근을 유지하고, 읽기 전용 상태 레지스터는 const volatile로 표현합니다. 다만 volatile은 원자성을 보장하지 않습니다.</span><br>
<span style="color:#111827">구조체는 CMSIS처럼 register offset을 표현하는 데 쓰되, 정확한 bit layout은 mask/shift로 다룹니다.</span><br>
<span style="color:#dc2626">ISR이나 다른 실행 주체와 공유하는 값은 atomic, critical section, 전용 set/clear register 중 상황에 맞는 방법으로 보호합니다.</span><br>

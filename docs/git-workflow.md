# Git Workflow

이 repo의 커밋·브랜치·PR 운영 규칙. 면접관이 한국 채용 시장 관점에서 "검토 비용이 낮은" 저장소로 보이게 하기 위한 자체 가이드.

## 커밋 컨벤션

### 형식

```
Type: 한국어 설명
```

### Type 종류

- `Feat:` 새 기능 (LED blink, UART 초기화, I2C 드라이버)
- `Fix:` 버그 수정 (ADDR 클리어 누락, TRISE 미설정)
- `Refactor:` 동작 동일, 구조 개선
- `Docs:` README, 주석, 데이터시트 노트
- `Update:` 기존 기능 보강
- `Chore:` 빌드 설정, gitignore, CI

### 예시

```
Feat: USART1 초기화 + 폴링 송신
Fix: I2C ADDR 클리어 시퀀스 SR1 → SR2 순서로 수정
Docs: README에 빌드/플래시 절차 추가
Refactor: GPIO 설정을 함수로 분리
Chore: GitHub Actions arm-none-eabi-gcc 빌드 추가
```

### 분량·빈도 원칙

- 한 커밋 = 의미 단위. 보통 30~200 LOC
- 한 기능 = 1~3 커밋
- 하루 1~5개 커밋 정상 (30개+ = 부자연)
- 시간대 자연스럽게 (낮·밤·주말 다양 OK)
- typo·"깜빡함" 수정 커밋도 솔직히 남김 (사람 냄새)

### 금지

- `WIP`, `update`, `fix bug` 같은 의미 없는 메시지
- 이모지 도배 (`🎉 첫 커밋`)
- AI 라이브러리 자동 생성 메시지 그대로 (`Generated by ...`)
- `Co-Authored-By: Claude` 같은 라인 금지

## 브랜치 전략

### main 중심 단순 GitHub Flow

```
main
 ├── feat/<기능명>
 ├── fix/<버그>
 └── docs/<문서>
```

3주 단독 포트폴리오에 `develop` / `release` / `hotfix` 같은 과도한 Git Flow X.

### 예시 브랜치

- `feat/clock-gpio-init`
- `feat/uart-logging`
- `feat/i2c-register-mpu6050`
- `feat/can-tx`
- `fix/addr-clear-sequence`
- `docs/readme-demo`

## Pull Request

### PR 갯수 = 2~4개의 의미 있는 self-PR

3주 프로젝트 권장 PR 분리:
1. `feat/clock-gpio-init` — 클럭·GPIO·UART 초기 bring-up
2. `feat/i2c-register-mpu6050` — I2C 레지스터 직접 read (WHO_AM_I)
3. `feat/can-tx` — CAN 송신 + 메시지 ID 설계
4. `docs/readme-demo` — README 완성 + 검증 자료

### PR 본문 4섹션

`.github/PULL_REQUEST_TEMPLATE.md` 자동 적용:
- **목적**: 왜 필요한가
- **변경 사항**: 무엇을 바꿨나
- **검증**: UART 로그, 로직 분석기, 빌드 결과
- **참고 / 한계**: 데이터시트 인용, 다음 작업, 솔직한 한계

### Self-PR 포지셔닝

self-PR은 **"기능 단위 정리와 자기 리뷰 목적"**으로 정직하게.
"협업 경험 보여주려고"라고 포장하면 역효과.

## 작성자 일치 (잔디 안 심김 방지)

### 로컬 설정

```bash
git config user.name "Soram Kim"
git config user.email "judyischicken@gmail.com"   # GitHub 등록 이메일

# 또는 noreply
git config user.email "judymom@users.noreply.github.com"
```

### 원칙

- `user.email` = GitHub 계정 이메일 또는 `users.noreply.github.com` 주소
- 한 repo 안 author name 여러 개 흩어지면 신뢰 ↓
- GitHub 프로필 표시 이름과 git user.name 일치 권장

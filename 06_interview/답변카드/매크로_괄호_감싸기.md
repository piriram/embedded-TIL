# 매크로 괄호 감싸기 / 방어적 정의

## 30초 통합 답변

> 면접 직전 이것만 소리내어 읽는다. 입에 붙을 때까지.

매크로 괄호 감싸기는 **`#define` 매크로의 치환 결과가 주변 코드 문맥에 끼어들어 의미가 바뀌지 않도록 보호하는 방어적 정의 방식**입니다. 주로 연산자 우선순위, 결합 방향, 포인터 역참조, 산술식 확장 때문에 생기는 의도치 않은 해석을 막기 위해 사용하며, 내부적으로는 매크로 본문과 인자를 괄호로 감싸 치환 후에도 하나의 단위처럼 해석되게 합니다. 일반 변수나 함수와 비교하면 매크로는 타입 있는 문법 요소가 아니라 단순 텍스트 치환이라는 점이 가장 중요한 차이입니다. 실제로는 MMIO 레지스터 매크로, 비트 마스크, 수식 매크로에서 특히 중요합니다.

---

## 한 줄 정의

매크로 괄호 감싸기는 **매크로 치환 결과가 주변 문맥과 섞여 다른 의미로 해석되지 않게 하는 방어적 작성 규칙**이다.

핵심 특성은 **치환 결과를 하나의 문법 단위처럼 고정한다는 것**이다.

## 왜 필요한가

매크로는 컴파일 전 단순 텍스트 치환이기 때문에, 치환된 텍스트가 사용 위치의 연산자나 문맥과 섞일 수 있다.

예를 들어 괄호가 없는 매크로는 다음처럼 예상과 다르게 동작할 수 있다.

```c
#define DOUBLE(x) x + x

int a = 10 * DOUBLE(3);
```

치환 후:

```c
int a = 10 * 3 + 3;
```

결과는 `60`이 아니라 `33`이다.
사용자는 `10 * (3 + 3)`을 기대했지만, 실제로는 연산자 우선순위 때문에 `(10 * 3) + 3`으로 해석된다.

방어적으로 쓰면 다음과 같다.

```c
#define DOUBLE(x) ((x) + (x))

int a = 10 * DOUBLE(3);
```

치환 후:

```c
int a = 10 * ((3) + (3));
```

이제 의도대로 `60`이 된다.

## 동작 원리

C Preprocessor는 매크로 이름을 본문 텍스트로 치환할 뿐, 그 매크로가 "하나의 값", "하나의 식", "하나의 주소"인지 보장하지 않는다.

따라서 매크로 전체를 괄호로 감싸면, 치환된 뒤 주변 연산자보다 먼저 하나의 단위로 묶인다. 함수형 매크로에서는 인자도 각각 괄호로 감싸야 한다. 인자 자체가 `a + b` 같은 식일 수 있기 때문이다.

기본 원칙:

```c
#define MACRO(x) ((x) ...)
```

나쁜 예:

```c
#define SQUARE(x) x * x
```

방어적 정의:

```c
#define SQUARE(x) ((x) * (x))
```

사용 예:

```c
int y = SQUARE(a + b);
```

괄호가 없으면:

```c
int y = a + b * a + b;
```

괄호가 있으면:

```c
int y = ((a + b) * (a + b));
```

## 언제 쓰는가 / 언제 피하는가

- **쓰는 경우:** 값처럼 쓰이는 매크로, 주소 계산 매크로, 포인터 역참조 매크로, 비트 연산 매크로, 수식 매크로에서는 기본적으로 괄호를 감싼다.

```c
#define GPIO_PORTF_DATA  (*((unsigned int *)(GPIOF_BASE + 0x3FC)))
#define BIT(n)           (1U << (n))
#define MASK(a, b)       ((a) | (b))
```

- **피하는 경우:** 매크로가 의도적으로 문장 조각을 만들어야 하는 특수한 경우에는 무조건 전체 괄호를 감싸면 안 될 수 있다. 예를 들어 여러 문장을 포함하는 매크로는 보통 `do { ... } while (0)` 패턴을 쓴다.

```c
#define SET_AND_CLEAR(x) do { \
    set(x);                   \
    clear(x);                 \
} while (0)
```

또한 일반 계산 로직은 가능하면 `inline function`, `const`, `enum`을 우선 고려한다. 매크로는 타입 검사가 약하고 디버깅이 어렵다.

## 대표 예시

MMIO 레지스터 매크로:

```c
#define RCGCGPIO   (*((unsigned int *)0x400FE608))
```

여기서 괄호는 두 단계로 의미가 있다.

```c
(unsigned int *)0x400FE608
```

주소값 `0x400FE608`을 `unsigned int *` 포인터로 캐스팅한다.

```c
*((unsigned int *)0x400FE608)
```

그 포인터가 가리키는 메모리 위치를 역참조한다.

```c
(*((unsigned int *)0x400FE608))
```

전체 역참조 결과를 하나의 단위로 묶는다.

이렇게 정의하면 다음처럼 쓸 수 있다.

```c
RCGCGPIO = 0x20;
```

치환 후:

```c
(*((unsigned int *)0x400FE608)) = 0x20;
```

괄호 덕분에 왼쪽 전체가 "해당 주소의 메모리 객체"라는 하나의 lvalue로 안정적으로 해석된다.

## 비교 / 대안

| 비교 대상 | 핵심 차이 |
|----------|-----------|
| 괄호 없는 매크로 | 주변 연산자와 섞여 우선순위 문제를 일으킬 수 있다. |
| 괄호 있는 매크로 | 치환 결과가 하나의 단위로 묶여 문맥 변화에 강하다. |
| `inline function` | 타입 검사를 받을 수 있고 인자 평가도 함수 규칙을 따른다. 단, 전처리 텍스트 치환은 아니다. |
| `const` / `enum` | 단순 상수에는 매크로보다 안전할 수 있다. 하지만 MMIO 주소 역참조처럼 코드 조각 자체를 만들 때는 매크로가 쓰인다. |

## 꼬리질문 예상

- **Q:** 매크로는 왜 괄호를 많이 쓰나요?
  **A:** 매크로는 단순 텍스트 치환이라 사용 위치의 연산자와 섞일 수 있다. 괄호로 감싸면 치환 결과가 하나의 단위처럼 해석되어 의미 변화가 줄어든다.

- **Q:** 매크로 전체만 괄호로 감싸면 충분한가요?
  **A:** 함수형 매크로는 전체뿐 아니라 인자도 각각 괄호로 감싸야 한다. 인자 자체가 `a + b` 같은 복합식일 수 있기 때문이다.

- **Q:** 모든 매크로를 괄호로 감싸면 되나요?
  **A:** 값이나 표현식처럼 쓰이는 매크로는 보통 그렇다. 하지만 여러 문장을 생성하는 매크로는 괄호가 아니라 `do { ... } while (0)` 패턴을 쓰는 경우가 많다.

- **Q:** 괄호를 감싸면 매크로의 부작용 문제가 사라지나요?
  **A:** 아니다. 괄호는 우선순위 문제를 줄일 뿐이다. `SQUARE(i++)`처럼 인자가 여러 번 평가되는 문제는 여전히 남는다.

## 자주 하는 오해

- **오해:** 괄호는 보기 좋게 하려고 넣는 것이다.
  - **정확히는:** 괄호는 매크로 치환 결과가 주변 문맥에 끼어들어 의도와 다르게 해석되는 것을 막기 위한 방어 장치다.

- **오해:** 매크로 전체만 괄호로 감싸면 항상 안전하다.
  - **정확히는:** 함수형 매크로에서는 인자도 각각 괄호로 감싸야 한다. 그래도 인자 중복 평가 같은 매크로 고유의 위험은 남는다.

- **오해:** 괄호를 잘 치면 매크로는 함수처럼 안전해진다.
  - **정확히는:** 아니다. 매크로는 여전히 타입 검사를 받지 않고, 인자가 여러 번 평가될 수 있으며, 디버깅 시 실제 이름이 사라질 수 있다.

## 자주 놓치는 정확 표현

| 모호한 말 | 정확한 용어 |
|----------|-------------|
| 매크로를 안전하게 만든다 | 연산자 우선순위와 문맥 결합 문제를 줄인다 |
| 괄호로 실행 순서를 정한다 | 괄호로 치환 결과의 구문적 결합 방식을 고정한다 |
| 매크로 값 | 매크로 치환 결과 |
| 매크로가 계산된다 | 전처리 단계에서 텍스트가 치환되고, 계산은 컴파일러/런타임 문맥에서 처리된다 |
| 괄호 치면 완전히 안전하다 | 우선순위 문제는 줄지만 중복 평가 문제는 남는다 |

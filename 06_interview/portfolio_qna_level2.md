## 1. 폴링(Polling)과 인터럽트(Interrupt)

### Q1-1. 센서 데이터를 읽어올 때 폴링 방식과 인터럽트 방식을 각각 어떻게 활용하셨으며, 그 이유는 무엇인가요?
* **Tip:** 단순 폴링의 한계(CPU 점유)를 언급하고, 왜 특정 이벤트에 인터럽트를 적용했는지 실무적인 관점에서 설명하세요.
> **[모범 예시]** 
> "초기 구현에서는 `while(1)` 루프 안에서 센서 상태를 계속 확인하는 폴링 방식을 사용했습니다. 하지만 시스템이 커지면서 디스플레이 출력 등 다른 작업이 지연되는 문제가 발생했습니다. 이를 해결하기 위해 특정 시간마다 트리거되는 타이머 인터럽트(또는 외부 EXTI)를 적용하여 CPU의 불필요한 대기 시간을 줄이고 효율성을 높였습니다."

### Q1-2. 인터럽트 서비스 루틴(ISR)을 작성할 때 가장 중요하게 생각한(주의한) 점은 무엇인가요?
* **Tip:** ISR은 최대한 짧고 간결하게 작성해야 한다는 임베디드 기본 원칙을 묻는 질문입니다.
> **[모범 예시]** 
> "ISR 내부는 최대한 짧고 빠르게 실행되도록 설계했습니다. ISR 안에서 무거운 연산이나 긴 `delay()` 함수, `printf` 같은 블로킹 함수를 사용하면 다른 중요한 인터럽트 처리가 지연될 수 있기 때문입니다. 따라서 ISR에서는 플래그 변수만 세팅하고 바로 빠져나온 뒤, 실제 데이터 처리 연산은 메인 루프(혹은 RTOS Task)에서 플래그를 확인하여 비동기적으로 처리하도록 구현했습니다."

## 2. 통신 프로토콜 세부 구현 (I2C, SPI, UART)

### Q2-1. I2C 통신을 구현할 때 Pull-up 저항을 사용하는 이유와 통신 속도 설정 시 고려했던 점은 무엇인가요?
* **Tip:** 하드웨어 인터페이스의 원리를 정확히 이해하고 있는지 확인하는 질문입니다. Open-drain 특성을 언급하면 매우 좋습니다.
> **[모범 예시]** 
> "I2C 버스는 하드웨어적으로 Open-drain(또는 Open-collector) 구조를 가지기 때문에 MCU 스스로 High 신호를 강제로 구동할 수 없습니다. 따라서 통신 라인(SDA, SCL)에 반드시 외부(또는 내부) Pull-up 저항을 연결하여 기본 상태를 High로 유지해야 합니다. 통신 속도는 케이블 길이와 기생 커패시턴스를 고려하여 안정적이면서도 요구 성능을 만족하는 400kHz(Fast Mode)로 설정했습니다."

### Q2-2. SPI 통신의 4가지 모드(Mode 0~3)에 대해 설명해 보시고, 본인의 디바이스는 어떤 모드로 동작했나요?
* **Tip:** CPOL(Clock Polarity)와 CPHA(Clock Phase)의 개념을 묻는 질문입니다. 
> **[모범 예시]** 
> "SPI 모드는 클럭의 기본 유휴 상태(High/Low)를 결정하는 CPOL과, 데이터를 어느 엣지(Rising/Falling)에서 샘플링할지 결정하는 CPHA의 조합으로 총 4가지가 존재합니다. 제가 제어한 모듈은 데이터시트상 유휴 상태에서 클럭이 Low이고(CPOL=0), 첫 번째 Rising 엣지에서 데이터를 읽는(CPHA=0) 'SPI Mode 0'을 요구했기 때문에 MCU의 통신 설정도 이에 맞춰 일치시켰습니다."

## 3. DMA(Direct Memory Access) 활용

### Q3-1. 프로젝트에서 DMA를 사용하셨다면, 왜 사용했고 어떤 이점을 얻었나요?
* **Tip:** CPU 병목 현상 해소라는 DMA의 존재 의의를 구체적인 사례로 설명하세요. (만약 안 썼다면, '도입한다면 어디에 적용하고 싶은지' 적으셔도 좋습니다.)
> **[모범 예시]** 
> "초기에는 폴링 방식으로 SPI를 통해 디스플레이 프레임 버퍼를 전송했는데, 전송이 끝날 때까지 CPU가 루프 안에 갇혀 있어 센서 수집 주기가 밀렸습니다. 이를 해결하기 위해 SRAM에서 SPI 데이터 레지스터로 데이터를 바로 밀어넣는 Memory-to-Peripheral 방식의 DMA를 적용했습니다. 덕분에 전송 중에도 CPU는 다른 연산을 수행할 수 있어 백그라운드 처리가 가능해졌고 전체 응답성이 향상되었습니다."

## 4. RTOS 환경에서의 동기화 및 통신 (해당 시)

### Q4-1. 여러 Task(혹은 메인 루프와 인터럽트)에서 하나의 리소스(예: 전역 변수, I2C 버스)를 공유할 때 데이터 충돌을 어떻게 방지했나요?
* **Tip:** Mutex나 Semaphore, 혹은 인터럽트 비활성화 등을 통해 임계 구역(Critical Section)을 보호한 경험을 묻습니다.
> **[모범 예시]** 
> "여러 모듈에서 동시에 UART로 `printf`를 호출하면 시리얼 출력이 섞여 글자가 깨지는 현상이 있었습니다. 이를 막기 위해 UART 전송 함수를 감싸는 래퍼(Wrapper) 함수를 만들고, 내부에 Mutex를 적용했습니다. 한 모듈이 Mutex를 획득하여 출력하는 동안에는 다른 모듈이 대기 상태에 들어가도록 하여 상호 배제(Mutual Exclusion)를 보장했습니다."
>
> **내 답변:** 
>

### Q4-2. Task 간(또는 모듈 간)에 데이터를 전달할 때는 어떤 방식을 사용하셨나요?
* **Tip:** 전역 변수 공유의 위험성을 언급하고, 메세지 큐(Message Queue) 구조나 버퍼 체계의 장점을 설명하면 베스트입니다.
> **[모범 예시]** 
> "처음에는 `extern` 키워드로 전역 변수를 공유하여 데이터를 넘겼지만, 구조가 커지면서 데이터 무결성을 보장하기 어렵고 모듈 간 결합도가 지나치게 높아졌습니다. 이를 개선하기 위해 Message Queue (또는 Ring Buffer) 자료구조를 도입했습니다. 센서 수집부가 데이터를 큐에 Push하고, 처리부가 큐에서 Pop하는 생산자-소비자 패턴을 구축하여 비동기적이고 안전하게 데이터를 전달했습니다."

## 5. 포인터 및 메모리 관리 (C 언어 역량)

### Q5-1. 코드 모듈화 과정에서 C 언어의 포인터와 구조체(Struct)를 어떻게 활용하셨나요?
* **Tip:** 임베디드 C 프로그래밍의 핵심인 객체지향적 접근(구조체를 이용한 상태 관리, 함수 포인터를 통한 콜백 등) 경험을 묻습니다.
> **[모범 예시]** 
> "장치의 설정값이나 상태 정보를 여러 개의 낱개 변수로 분산시켜 관리하면 코드가 지저분해집니다. 그래서 장치의 ID, 현재 상태, 핀 번호 등을 하나로 묶은 `Device_HandleTypeDef`라는 핸들 구조체를 정의했습니다. 각종 제어 함수에 인자를 넘길 때는 복사 오버헤드를 막고 원본 데이터를 조작하기 위해 이 구조체의 포인터를 매개변수로 전달하는 방식을 취했습니다. 이를 통해 하나의 드라이버 코드로 동일한 센서 여러 개를 제어할 수 있는 확장성을 확보했습니다."

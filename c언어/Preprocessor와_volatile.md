# C Preprocessor와 volatile 키워드

**원본 강의:** [#5 Preprocessor and the "volatile" keyword in C (YouTube)](https://www.youtube.com/watch?v=5MzilJ2-MGY) — Miro Samek, Embedded Systems Programming Course

이전 강의(Lesson 4)에서 만든 LED 깜빡임 프로그램은 동작은 하지만 **읽기 매우 어렵다**. 레지스터 주소가 전부 cryptic한 16진수 숫자로 박혀 있고 주석도 없다. 이 강의에서는 두 가지 도구로 그 문제를 해결한다.

1. **C Preprocessor** — 숫자에 의미 있는 이름을 붙이는 매크로 메커니즘
2. **volatile 키워드** — 컴파일러 최적화로부터 IO 레지스터와 delay loop를 지키는 타입 한정자

---

## 1. C Preprocessor와 `#define` 매크로

### 매크로 정의 문법

`#`(pound sign)으로 시작하는 줄에 `#define`, 매크로 이름, 그리고 그 이름이 치환될 코드 조각을 차례로 쓴다.

```c
#define RCGCGPIO   (*((unsigned int *)0x400FE608))
```

데이터시트에서 이 레지스터를 "Run Mode Clock Gating Control register for GPIO"라고 부르므로 매크로 이름을 `RCGCGPIO`로 지었다. 정의한 뒤로는 원래 숫자 표현 대신 매크로 이름을 코드에 그대로 쓸 수 있다.

### 동작 원리 — 컴파일 전 단일 텍스트 치환

C Preprocessor는 이름 그대로 **컴파일 이전의 별개 단계**다. 개념적으로 다음 일을 한다.

- `#`로 시작하는 모든 줄을 컴파일러가 보기 전에 제거한다.
- 코드에서 **실제로 사용된** 매크로 이름만 치환 텍스트로 바꾼다.
- 그 결과 **컴파일러는 매크로 이름 자체를 절대 보지 못한다**. 치환된 문자 시퀀스만 본다.

따라서 정의만 해두고 어디서도 쓰지 않은 매크로는 컴파일에 아무 영향이 없다. 아무 텍스트로 정의해도 사용만 안 하면 빌드는 통과한다.

> **주의**
> 매크로는 C 언어의 완성된 문법 요소일 필요가 없다. 예를 들어 매크로 `FOO`가 포인터 캐스트 표현식의 일부분만 담고 있어도, 그것을 사용한 자리에 치환된 결과가 문맥상 말이 되기만 하면 컴파일러는 통과시킨다. 컴파일러 입장에서는 사람이 쓴 텍스트와 매크로가 치환된 텍스트를 구별할 방법이 없다.

### 매크로는 항상 괄호로 감싸라

위 성질의 따름정리: 매크로가 어떤 문맥에 끼어들지 모르므로, **의도하지 않은 의미 변화가 일어나지 않도록 방어적으로 정의**해야 한다.

```c
#define RCGCGPIO   (*((unsigned int *)0x400FE608))
```

전체를 괄호 `( ... )`로 둘러싼 이유가 그것이다. 이렇게 두면 어떤 문맥에 들어가도 항상 "포인터를 역참조한 값"이라는 한 단위로 해석된다.

### 매크로 안에서 매크로 사용 — Base + Offset 패턴

매크로를 다른 매크로의 정의에 다시 쓸 수 있다. 데이터시트가 알려주는 GPIO Port F의 **base address**를 한 번만 정의하고, 각 레지스터는 그 base에서의 **offset**으로 표현한다.

```c
#define GPIOF_BASE    0x40025000

#define GPIO_PORTF_DIR    (*((unsigned int *)(GPIOF_BASE + 0x400)))
#define GPIO_PORTF_DEN    (*((unsigned int *)(GPIOF_BASE + 0x51C)))
#define GPIO_PORTF_DATA   (*((unsigned int *)(GPIOF_BASE + 0x3FC)))
```

- `0x400` — Pin Direction register offset
- `0x51C` — Digital Enable register offset
- `0x3FC` — Data register offset

데이터시트 그대로의 base+offset 구조를 코드에 그대로 옮긴 셈이다.

### 컴파일 타임 상수 folding — 런타임 비용 0

"base에 offset을 더하는 연산이 매번 CPU에서 실행되는 것 아닌가?" 하는 걱정이 자연스럽게 든다. 하지만 디버거에서 한 줄씩 step해보면, `GPIO_PORTF_DATA`에 접근하는 자리에 어셈블리는 다음과 같이 생성되어 있다.

```asm
ldr r0, =0x400253FC    ; 더하기 없이 완성된 주소를 R0에 직접 로드
```

컴파일러가 **컴파일 타임에 계산 가능한 상수를 미리 접어 넣는다** (constant folding). 가독성을 얻으면서 성능 손실은 0이다.

> 강사 코멘트: CPU 입장에서 "외부 세계와 대화한다"는 행위는 결국 **특정 주소에 특정 값을 쓰는** `str`(store) 명령 한 번으로 환원된다. MMIO의 본질이 이 한 줄에 다 있다.

## 2. 주석 — 두 가지 스타일

C99는 주석 두 형식을 모두 지원한다.

```c
/* 전통적 C 스타일 — 여러 줄 가능, */로 종료 */
// C++ 스타일 — 줄 끝까지
```

- 주석은 사람을 위한 것이며 컴파일러는 완전히 무시한다.
- 모든 주석은 컴파일 전에 **공백 하나로 치환**된다.
- 공백을 합법적으로 놓을 수 있는 모든 자리에 주석을 둘 수 있다 — 매크로 정의 안에서도 가능.

## 3. 벤더 제공 헤더 파일 — 매크로를 직접 안 만들어도 된다

지금까지의 매크로를 매번 직접 작성할 필요는 없다. **MCU 벤더(여기서는 Texas Instruments)가 이미 모든 레지스터 매크로를 헤더 파일로 제공**한다.

### 헤더 파일 추가와 포함

Stellaris Launchpad에 탑재된 칩 이름이 `LM4F120H5QR`이므로 헤더 파일명도 `lm4f120h5qr.h`다. 프로젝트에 파일을 추가한 뒤 `#include`로 가져온다.

```c
#include "lm4f120h5qr.h"
```

- `#` + `include` + 파일명을 **큰따옴표**로 묶는다.
- 확장자 `.h`는 "header file" — `.c` 파일에 포함되도록 설계된 파일이라는 뜻.

헤더를 포함하면, 직접 정의했던 모든 매크로를 헤더가 제공하는 동등한 이름들로 교체할 수 있다. 데이터시트의 레지스터 이름을 그대로 따르므로 식별이 쉽다 (`GPIO_PORTF_DATA_R`, `GPIO_PORTF_DIR_R`, `GPIO_PORTF_DEN_R` 등). 이름만으로 헷갈리면 주소값을 확인해서 동일한지 검증할 수 있다.

### 헤더 파일 매크로 vs 직접 만든 매크로 — `unsigned long`과 `volatile`

헤더 파일의 매크로 한 줄을 가져와 직접 만든 것과 나란히 두면 두 가지 차이가 보인다.

```c
// 직접 작성:
#define MY_REG   (*((unsigned int          *)0x40025000))

// 헤더 파일:
#define HW_REG   (*((volatile unsigned long *)0x40025000))
```

1. **`unsigned int` vs `unsigned long`**
   - ARM 같은 **32비트 머신에서는 `int`와 `long`이 모두 32비트**이므로 두 타입은 실질적으로 동등하다.
   - 타입 차이의 일반론은 별도 강의에서 다룬다.

2. **`volatile` 한정자가 추가됨**
   - 이게 진짜 차이다. 그리고 이 강의의 핵심 주제다.

## 4. `volatile` 키워드 — 컴파일러에게 "최적화하지 말라" 알리기

### 정의

`volatile`은 **포인터가 가리키는 객체가 프로그램 명령과 무관하게 자발적으로 바뀔 수 있다**고 컴파일러에 알리는 타입 한정자다.

> 어떤 객체를 `volatile`로 선언한다는 것은: "이 객체는 프로그램의 어떤 문장도 변경하지 않는 것처럼 보여도 값이 바뀔 수 있다"고 컴파일러에 선언하는 것이다.

### IO 레지스터에 필수인 이유

Launchpad 보드의 `GPIO_PORTF` 레지스터에는 사용자 스위치 두 개의 비트가 연결되어 있다. 사용자가 스위치를 누르거나 떼면 이 비트가 바뀌는데, 이는 **프로그램의 어떤 명령으로도 일어나지 않는 변화**다. 따라서 `GPIO_PORTF`를 비롯한 **대부분의 IO 레지스터는 본질적으로 volatile**이다.

`volatile`이 없으면 컴파일러는 다음과 같은 최적화를 합법적으로 수행할 수 있다.

1. 객체의 값을 CPU 레지스터로 한 번 읽어 들인다.
2. 한동안 레지스터에서만 작업한다.
3. 마지막에 그 레지스터 값을 다시 메모리(객체)에 쓴다.

`volatile`로 표시되면 컴파일러는 **이런 최적화를 못 한다**. 소스 코드가 "이 객체를 읽어라/써라"고 말할 때마다 컴파일러는 **반드시 그대로 메모리 접근을 발생시켜야 한다**.

### 일반 변수에서도 유용 — delay loop 사례

`volatile`은 IO 레지스터 전용이 아니다. 일반 변수에서도 컴파일러 최적화를 막을 때 유용하다. 대표적인 예가 **busy-wait delay loop**다.

```c
unsigned int counter;   // volatile 없음

// LED ON
for (counter = 0; counter < 1000000; ++counter) { }
// LED OFF
for (counter = 0; counter < 1000000; ++counter) { }
```

컴파일러의 시선으로 보면, 이 두 루프는 **계산에 아무런 기여도 하지 않는다**. `counter`의 최종 값은 곧 덮어쓰이거나 어디에서도 쓰이지 않는다. 따라서 컴파일러는 두 루프를 **합법적으로 통째로 제거**할 수 있다.

### 실제로 확인하는 방법 — 최적화 레벨 올리기

IAR 툴체인 기준: Project Options → C/C++ Compiler → Optimizations 탭 → **High** 선택 → 빌드 후 보드에서 실행.

결과: **LED가 깜빡이지 않고 켜진 채로 멈춘다**. single step으로 확인하면 LED ON/OFF 명령은 여전히 그 자리에 있지만, **사이에 있던 두 delay loop는 사라졌다**.

### 해결책 — `counter`를 volatile로 만든다

```c
unsigned int volatile counter;
```

이제 컴파일러는 루프 안의 모든 `counter` 읽기·쓰기를 실제 메모리 접근으로 유지해야 하며 루프를 제거할 수 없다. 보드에서 다시 실행하면 LED가 정상적으로 깜빡이고, single step으로 보면 delay loop도 그대로 살아 있다.

### `volatile` 위치 — 타입 앞 vs 뒤

```c
volatile unsigned int counter;   // 타입 앞 — 헤더 파일 매크로가 쓰는 스타일
unsigned int volatile counter;   // 타입 뒤 — 강사 추천
```

문법적으로 둘 다 합법이며 의미도 같다. 강사는 **타입 뒤에 두는 쪽을 추천**한다.

> **주의**
> volatile은 "정확성"을 위한 도구이지 성능 최적화 도구가 아니다. 자발적 변경이 가능한 객체(IO 레지스터, 인터럽트 핸들러가 갱신하는 변수, 멀티스레드 공유 변수 일부, busy-wait counter 등)에만 정확히 붙여야 한다. 남발하면 컴파일러가 본래 가능한 최적화까지 못 하게 된다.

## 5. 정리 — 이 강의에서 얻은 것

- `#define` 매크로로 cryptic한 숫자를 의미 있는 이름으로 추상화하면서도 **런타임 성능 손실 없이** 가독성을 얻는다.
- 매크로는 정의 시점에 **괄호로 감싸 문맥 변화로부터 보호**한다.
- **벤더가 제공하는 헤더 파일**(예: `lm4f120h5qr.h`)을 `#include`하면 직접 매크로를 만들 필요가 없다.
- 헤더 파일의 매크로는 `volatile`을 사용한다. **IO 레지스터는 프로그램 명령 없이도 값이 바뀌므로**, 컴파일러가 캐시·재사용·제거 같은 최적화를 못 하도록 막아야 한다.
- `volatile`은 **delay loop 같은 일반 변수**에도 필요할 수 있다. 그렇지 않으면 최적화 레벨을 올렸을 때 루프 자체가 제거된다.
- 이 두 도구를 알고 나면 **어떤 최적화 레벨에서도 정확하게 동작하는 프로그램**을 쓸 수 있다.

> 다음 강의 예고: bitwise OR / AND 연산자로 composite LED의 다른 색을 깜빡이는 법과 GPIO 레지스터의 더 고급 기능을 배운다.

## 면접 답변 (30초 분량)

> `/easy-quiz` 실행 시 이 섹션이 정답 카드로 사용됩니다.

- **한 줄 정의:** `volatile`은 "이 객체는 프로그램 명령과 무관하게 자발적으로 값이 바뀔 수 있다"고 컴파일러에 알리는 타입 한정자다.
- **왜 필요:** IO 레지스터는 외부 신호(스위치, 인터럽트, 하드웨어 이벤트)로 값이 바뀌고, busy-wait delay loop의 카운터는 컴파일러 입장에서 "쓸모없어" 보인다. `volatile`이 없으면 컴파일러는 값을 CPU 레지스터에 캐싱하거나 루프 자체를 제거하는 최적화를 하고, 결과적으로 프로그램이 잘못 동작한다.
- **동작:** `volatile`이 붙은 객체는 소스 코드가 읽기/쓰기를 요구할 때마다 컴파일러가 **반드시 실제 메모리 접근 명령을 생성**해야 한다. 캐시·재배치·제거 같은 최적화가 금지된다.
- **비교:** 일반 변수는 컴파일러가 자유롭게 최적화할 수 있다. C Preprocessor의 `#define`은 컴파일 이전 텍스트 치환으로 가독성을 주지만 런타임 동작에는 관여하지 않는 반면, `volatile`은 컴파일러가 만드는 **실제 기계어 코드에 직접 영향**을 준다.
- **30초 통합 답변:**
  > `volatile`은 컴파일러에게 "이 객체는 프로그램 명령 없이도 값이 바뀔 수 있다"고 알리는 C 타입 한정자입니다. GPIO 같은 IO 레지스터는 스위치 입력으로 값이 바뀌고, delay 카운터는 컴파일러가 보기에 쓸모없는 루프라 통째로 제거될 수 있는데, `volatile`을 붙이면 컴파일러가 매번 실제 메모리 접근 명령을 생성해야 해서 캐싱이나 루프 제거 같은 최적화가 금지됩니다. MCU 벤더가 제공하는 헤더 파일의 레지스터 매크로가 전부 `volatile`로 정의되어 있는 이유이기도 합니다.

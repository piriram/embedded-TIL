# Memory Management

**주제:** RTOS에서 static memory, stack, heap이 어떻게 쓰이는지, FreeRTOS가 task와 kernel object를 heap에 할당하는 방식, stack overflow와 memory leak을 피하는 방법.

## 1. RTOS에서 Memory Management가 중요한 이유

RTOS 코드를 작성할 때는 data가 memory 어디에 저장되는지 이해해야 한다. 특히 embedded system은 RAM이 제한적이기 때문에 stack overflow나 memory leak이 발생하면 processor reset, undefined behavior, memory overwrite 같은 문제가 곧바로 나타날 수 있다.

일반 C program에서도 memory layout은 중요하지만, RTOS에서는 task마다 stack이 따로 생기고 task control block(TCB), queue, semaphore 같은 kernel object도 memory를 사용한다. 따라서 task 설계 자체가 RAM 사용량에 직접 영향을 준다.

---

## 2. Static Memory와 Static Allocation

Compiler는 compile이 끝난 시점에 global variable과 static variable에 필요한 memory 크기를 알 수 있다. Program이 시작되면 이 변수들을 위한 memory 영역이 미리 할당된다. 강의에서는 이 영역을 **static memory**라고 설명한다.

Global variable이나 `static` variable은 이 static memory 영역에 저장된다. 이 방식은 **static allocation**이다.

Static allocation의 중요한 특징은 variable이 program 전체 실행 시간 동안 존재한다는 점이다. Function call이 끝나도 사라지지 않으며, 이 memory 영역은 다른 용도로 재사용되지 않는다.

- **Global variable:** file scope 또는 program 전체에서 접근 가능한 변수
- **Static local variable:** function 안에 선언되지만 lifetime은 program 전체인 변수
- **Static allocation:** compile/link 단계에서 크기가 결정되고 program 시작 시 고정적으로 확보되는 memory allocation

---

## 3. Stack과 Automatic Allocation

Function 안에서 선언한 local variable은 보통 stack에 저장된다. Stack은 **last in, first out(LIFO)** 구조다. Nested function call이 일어날 때마다 local variable, argument, local pointer 같은 값이 stack에 push되고, function이 return하면 해당 function frame이 pop된다.

이 방식은 **automatic allocation**이다. Function이 호출될 때 자동으로 memory가 할당되고, function이 return하면 자동으로 해제된다.

Stack은 program 실행 중 필요한 만큼 free memory에서 자라날 수 있다. 예를 들어 recursive function call이 계속 이어지면 stack 사용량이 빠르게 늘어난다.

다만 compiler와 architecture에 따라 exact layout은 달라질 수 있다. 어떤 system에서는 static section이 위쪽에 있을 수 있고, stack이 아래쪽에 있을 수도 있다. Stack, heap, static 영역의 실제 배치는 processor architecture와 compiler, linker script에 따라 달라지므로 정확한 구조는 datasheet나 linker map을 확인해야 한다.

> **주의**
> Stack memory는 자동으로 관리되는 것처럼 보이지만 무한하지 않다. Recursive call, 큰 local array, 깊은 function call chain은 embedded system에서 stack overflow의 흔한 원인이 된다.

---

## 4. Heap과 Dynamic Allocation

Heap은 program 실행 중 동적으로 memory를 할당할 때 쓰이는 영역이다. C에서는 보통 `malloc`으로 필요한 크기의 memory를 요청하고, 사용이 끝나면 `free`로 반환한다.

이 방식은 **dynamic allocation**이다. Programmer가 명시적으로 "이만큼 memory를 새로 확보해 달라"고 요청한다는 점이 stack과 다르다.

C와 C++에서는 동적으로 할당한 memory를 사용 후 직접 해제해야 한다. Function 끝에서 `free`를 잊으면 heap에 할당된 memory가 계속 남는다. 이런 상황을 **memory leak**이라고 한다.

Memory leak이 반복되면 heap이 계속 줄어든다. Heap과 stack이 서로를 향해 자라는 구조라면 둘이 충돌해 서로의 memory를 덮어쓸 수도 있다. `malloc`은 memory를 할당할 수 없을 때 `NULL`을 반환해야 하지만, microcontroller 환경에서는 error를 던지고 reset되는 형태로 나타날 수도 있다.

## 5. FreeRTOS가 Task Memory를 할당하는 방식

FreeRTOS에서 새 task를 만들면 heap에서 memory 일부가 할당된다. 이 memory는 크게 두 부분으로 나뉜다.

첫 번째는 **Task Control Block(TCB)**이다. TCB는 task에 필요한 핵심 정보를 담는 struct다. 예를 들어 task stack의 위치, task priority level 같은 정보를 저장한다.

두 번째는 해당 task 전용 **stack**이다. 우리가 `xTaskCreate` 또는 `xTaskCreatePinnedToCore`를 호출할 때 지정하는 stack size는 이 task stack으로 사용할 heap memory 크기다.

Task마다 TCB와 stack이 새로 필요하다. 따라서 task를 많이 만들수록 heap 사용량이 늘어난다. 이후 queue, semaphore 같은 kernel object를 만들 때도 heap memory가 사용된다.

> **이미지 필요**
> Heap 안에 task별 TCB와 stack이 배치되고, queue/semaphore 같은 kernel object도 heap에 생기는 구조
> - 출처: 강의 02:37~03:44 구간
> - 대체안: heap 영역을 블록으로 나누어 TCB, stack, queue, semaphore를 표시한 다이어그램

## 6. Static Task Allocation

FreeRTOS의 newer version에는 task와 kernel object를 static memory에 할당하는 방법도 있다. Critical application에서는 dynamic allocation 자체를 금지하거나 최소화하는 coding standard를 쓰기도 한다.

예를 들어 medical device나 satellite 같은 system에서는 memory leak이 치명적일 수 있다. 이때 static allocation을 사용하면 runtime heap allocation 실패나 leak 위험을 줄일 수 있다.

FreeRTOS에서 static allocation을 사용하려면 `configSUPPORT_STATIC_ALLOCATION` parameter를 `1`로 정의해야 한다.

강의 시점 기준으로는 ESP-IDF가 이 설정을 기본으로 켜 두지 않아 ESP32 Arduino/ESP-IDF 환경에서 static task를 바로 사용할 수 없다고 설명한다.

> **예외**
> Static allocation은 memory leak 위험을 줄일 수 있지만, 필요한 memory를 compile/link 단계에서 충분히 계산해야 한다. Runtime flexibility는 줄어든다.

## 7. Heap Fragmentation과 FreeRTOS Heap Schemes

Dynamic allocation을 수행하면 program은 heap에서 요청한 크기를 담을 수 있는 contiguous block을 찾는다. Heap을 계속 할당하고 해제하다 보면 free block이 여기저기 흩어지는 **fragmentation**이 생길 수 있다.

Fragmentation이 심하면 전체 free memory는 남아 있어도, 요청한 크기의 연속된 block이 없어 allocation에 실패할 수 있다. 또한 heap이 stack 방향으로 더 빠르게 자라는 것처럼 보일 수 있다.

FreeRTOS는 build system에 포함할 수 있는 여러 heap allocation scheme을 제공한다. FreeRTOS source를 직접 포함하는 환경에서는 이 중 하나의 source file을 선택해야 한다.

- **heap_1:** memory free를 허용하지 않는다. Static allocation support 이전에는 heap 일부를 static memory처럼 쓰고 싶을 때 사용했다.
- **heap_2:** 현재는 `heap_4`에 비해 obsolete로 간주된다.
- **heap_3:** 일반 C `malloc`과 `free`를 감싸서 thread-safe하게 사용할 수 있게 한다.
- **heap_4:** fragmented heap 영역을 합쳐 coalescing할 수 있어 fragmentation을 줄인다. 강사는 가장 자주 보는 scheme이라고 설명한다.
- **heap_5:** non-contiguous heap section들을 하나의 allocation block처럼 사용할 수 있게 하는 더 advanced한 scheme이다.

일반 C의 `malloc`과 `free`는 thread-safe하지 않고, 실행 시간이 compile time에 결정되지 않는다. RTOS에서는 thread safety와 deterministic timing을 고려해야 하므로 heap scheme 선택이 중요하다.

Critical application에서 coding standard가 dynamic allocation을 허용하지 않는다면 `heap_1` 또는 static allocation을 선택할 수 있다.

ESP32는 여러 종류의 RAM을 가지고 있어서 vanilla FreeRTOS보다 heap allocation scheme이 더 복잡하다. 강의에서는 ESP32-specific heap allocation은 깊게 다루지 않고 ESP-IDF documentation을 참고하라고 안내한다.

## 8. Task Stack Overflow와 Stack Canary

강의의 첫 실습은 task stack이 부족할 때 어떤 일이 발생하는지 보여준다.

Bare-bones 예제에서 하나의 task만 만들고, 그 task 안에서 integer array를 만든 뒤 값을 출력한다. `int` 100개 배열은 보통 400 bytes를 사용한다. 그런데 task stack을 1KB로 잡고 그중 약 **768 bytes**가 overhead로 필요하다면 local array를 담을 여유가 부족하다.

이 상태로 실행하면 output이 몇 번 보이다가 processor가 reset될 수 있다. 이는 task에 할당한 stack buffer를 overflow했다는 신호일 수 있다.

강의에서 언급한 **stack canary watchpoint**는 stack 끝부분의 몇 byte에 known value를 넣어 두고, 이 값이 바뀌었는지 주기적으로 확인하는 보호 기법이다. Canary 값이 바뀌었다는 것은 stack이 할당된 경계를 넘어 침범했다는 뜻이다. 이 경우 error가 발생하고 processor가 reset된다.

해결 방법은 task에 충분한 stack size를 주는 것이다. 예제에서는 overhead 768 bytes와 local variable 크기를 고려하면 약 **1200 bytes**가 필요하고, safety margin을 두어 **1500 bytes**로 늘리면 정상 실행된다.

> **주의**
> Stack canary error catching behavior를 바꿀 수는 있지만, 강의에서는 당분간 변경하지 말라고 권장한다. Stack overflow를 조용히 지나가게 만들면 memory corruption을 더 찾기 어려워진다.

## 9. Stack High Watermark와 Heap Size 확인

FreeRTOS API `uxTaskGetStackHighWaterMark`를 사용하면 task stack에 얼마나 여유가 남았는지 확인할 수 있다.

이 값은 byte가 아니라 **word 단위**로 보고된다. 32-bit system에서는 word 하나가 4 bytes이므로, 사용 가능한 byte 수를 보려면 반환값에 4를 곱해야 한다.

High watermark가 0에 가까워지면 stack overflow가 임박했다는 뜻이며, stack canary error와 reset이 발생할 수 있다.

전체 heap 여유는 `xPortGetFreeHeapSize`로 확인할 수 있다. Stack high watermark와 달리 이 함수는 available heap size를 **bytes** 단위로 반환한다.

- `uxTaskGetStackHighWaterMark`: task stack 여유 확인, word 단위
- `xPortGetFreeHeapSize`: 전체 free heap 확인, byte 단위

## 10. `pvPortMalloc`과 `vPortFree`

Vanilla FreeRTOS에서 `heap_3` scheme을 사용하지 않는다면 일반 `malloc` 대신 `pvPortMalloc`을 사용하는 편이 좋다. 일반 `malloc`은 thread-safe하지 않기 때문이다.

ESP-IDF에서는 일반 `malloc`도 사용할 수 있지만, 강의에서는 vanilla FreeRTOS에 가깝게 설명하기 위해 `pvPortMalloc`을 사용한다.

Dynamic allocation을 할 때는 반드시 allocation 실패를 확인해야 한다. `malloc`이나 `pvPortMalloc`은 heap memory가 부족하면 `NULL`을 반환해야 한다. 따라서 반환값이 `NULL`인지 검사하고, 실패했다면 error를 출력하거나 error code를 반환하는 흐름이 필요하다.

사용이 끝난 memory는 `free`가 아니라 FreeRTOS의 `vPortFree`로 반환한다. 그래야 RTOS heap scheme과 thread safety 조건에 맞게 memory를 해제할 수 있다.

강의 예제에서는 heap size를 출력한 뒤 `pvPortMalloc`으로 memory를 할당한다. `vPortFree`를 호출하지 않으면 loop를 반복할수록 free heap이 줄어들고, 결국 heap이 거의 0이 되어 ESP32가 reset되거나 allocation failure message가 출력된다.

`vPortFree`를 추가하면 allocated heap은 loop 한 번 동안만 사용되고, 다음 iteration 전에 정상적으로 반환된다.

## 11. 실습 Challenge: Dynamic Heap 기반 Serial Echo

강의의 challenge는 두 task로 간단한 serial echo program을 만드는 것이다.

Task A는 serial monitor input을 듣는다. Newline character를 만나면 그 시점까지 입력된 문자열을 저장한다. 이때 문자열 길이에 정확히 맞는 heap memory를 새로 할당해야 한다.

Task B는 새 message가 준비되었다는 알림을 받으면 해당 message를 serial terminal에 출력하고, 출력이 끝난 뒤 heap memory를 free한다.

이 challenge의 핵심은 두 가지다.

첫 번째는 heap allocation lifecycle이다. 문자열을 담기 위해 필요한 만큼만 `pvPortMalloc`하고, Task B가 사용을 끝낸 뒤 반드시 `vPortFree`해야 한다.

두 번째는 task 간 notification이다. Part 4에서는 아직 queue를 자세히 다루지 않았지만, "message ready" 상태를 Task B에 알려야 한다. 다음 강의에서 queue를 다루는 이유가 바로 이런 inter-task communication 문제 때문이다.

# Multicore Systems

**주제:** ESP32 dual-core 환경에서 FreeRTOS task를 core에 pinning하거나 no affinity로 실행하는 방식, AMP와 SMP의 차이, cache와 interrupt determinism, multicore critical section 설계.
**원본 강의:** [Introduction to RTOS Part 12 - Multicore Systems | Digi-Key Electronics (YouTube)](https://www.youtube.com/watch?v=LPSHUcH5aQc)

## 1. 왜 Multicore RTOS를 쓰는가

여러 core를 가진 microcontroller는 점점 흔해지고 있다. Multicore MCU를 사용하면 task를 병렬화할 수 있고, machine learning, Wi-Fi stack, Bluetooth stack처럼 계산량이나 response deadline이 있는 작업을 분리하기 좋다.

ESP32 계열에서 흔히 만나는 chip은 두 개의 core를 가진다. 이를 이용하면 한 core에서는 communication protocol task를 돌리고, 다른 core에서는 user application task를 돌리는 식으로 system을 구성할 수 있다.

다만 RTOS에서 multicore를 쓰는 것은 어떤 면에서는 단순하지만, 어떤 면에서는 determinism과 synchronization을 훨씬 복잡하게 만든다. Task가 어느 core에서 실행되는지, interrupt가 어느 core에서 발생하는지, cache miss가 timing에 어떤 영향을 주는지까지 고려해야 한다.

---

## 2. AMP와 SMP

Multicore processing을 이해하려면 먼저 **AMP**와 **SMP**를 구분해야 한다.

**AMP(Asymmetric Multiprocessing)**는 여러 processor 또는 core가 서로 통신하지만, 그중 하나가 system을 주도하는 구조다. 한 core가 operating system을 실행하고, 다른 core들에게 task나 job을 보낸다. Secondary core도 task를 받기 위해 자체 OS를 가질 수 있지만, 핵심은 하나의 core가 task distribution을 담당한다는 점이다.

**SMP(Symmetric Multiprocessing)**는 각 core 또는 processor가 동등하게 취급되고 같은 operating system을 실행하는 구조다. Core들은 shared task list에 접근하고, 각 core의 scheduler가 그 list에서 실행할 task를 가져간다.

AMP는 서로 다른 architecture의 core나 별도 processor, 심지어 separate computer까지 사용할 수 있다. 반면 SMP는 shared memory와 I/O bus를 긴밀하게 공유해야 하므로 보통 같은 architecture의 core를 사용한다.

## 3. ESP32 Dual-Core 구조

ESP32에는 두 core가 있다.

- **PRO core:** CPU0, protocol core
- **APP core:** CPU1, application core

두 core는 같은 Xtensa LX6 architecture이며, shared bus를 통해 memory와 peripheral에 접근한다. PRO core는 Wi-Fi, Bluetooth 같은 communication protocol task를 실행하도록 의도되어 있고, APP core는 user program을 실행하도록 의도되어 있다.

Wi-Fi나 Bluetooth를 사용한다면 이 model을 유지하는 것이 좋다. Networking protocol deadline을 놓치면 data loss가 발생할 수 있기 때문이다. Protocol stack은 core 0에 두고, user application은 core 1에서 실행하는 식의 분리가 안전하다.

ESP32의 cache 구조도 determinism에 영향을 준다. ESP32에서는 shared instruction RAM의 첫 64KB가 cache로 사용되며, 앞 32KB는 core 0 cache, 뒤 32KB는 core 1 cache로 나뉜다. Task가 core를 바꾸면 이전 core의 cache에 있던 working data를 그대로 사용할 수 없고, main memory fetch와 cache update가 필요해진다.

## 4. ESP-IDF FreeRTOS의 Multicore Scheduling

Vanilla FreeRTOS는 multicore execution을 지원하지 않는다. ESP32에서 설명하는 multicore behavior는 ESP-IDF port of FreeRTOS의 동작이다. 다른 RTOS나 다른 MCU의 multicore support는 다를 수 있으므로 반드시 해당 chip과 RTOS documentation을 확인해야 한다.

ESP-IDF에서는 각 core가 독립적인 scheduler와 tick timer를 가진다. 따라서 core 0의 task와 core 1의 task가 정확히 같은 시점에 실행된다고 가정할 수 없다.

Task Control Block(TCB), stack, code는 shared memory에 있으므로 이론적으로 어느 core든 task를 실행할 수 있다. ESP-IDF에서는 task 생성 시 core에 pinning할 수도 있고, scheduler가 shared ready list에서 선택하게 둘 수도 있다.

Task를 특정 core에 pinning하면 그 task는 해당 core에서만 실행된다. 예를 들어 task A를 core 0에 pinning하면 task A는 core 1에서 실행되지 않는다.

반대로 `tskNO_AFFINITY`를 지정하면 task가 어느 core에서든 실행될 수 있다. 각 core scheduler는 ready state에 있는 highest priority task를 찾아 실행한다.

## 5. Pinning과 No Affinity Demo

강의 예제는 priority가 다른 두 task를 사용한다.

- Task L: low priority, priority 1
- Task H: high priority, priority 2

두 task는 200 milliseconds마다 task name과 현재 실행 중인 core를 serial terminal에 출력한다. 강의에서는 일부러 좋지 않은 delay를 사용한다. 단순 `for` loop로 processor를 hogging해서 task가 scheduler에 yield하지 않는 상황을 보여주기 위해서다.

두 task를 모두 core 0에 pinning하면 high priority task H가 core 0을 계속 점유하고 task L은 실행 기회를 얻지 못한다. 또한 core 0에는 scheduler가 몇 초 동안 호출되지 않으면 trigger되는 task watchdog timer가 있어 processor가 reset된다. 이 watchdog은 wireless communication task가 loop에 갇히는 상황을 막기 위한 장치이며, core 1에는 기본적으로 같은 watchdog이 설정되어 있지 않다.

두 task를 서로 다른 core에 pinning하거나 `tskNO_AFFINITY`를 사용하면 task L과 task H가 각각 다른 core에서 주기적으로 실행될 수 있다. 다만 no affinity에서는 어느 core가 어떤 task를 실행할지 바뀔 수 있다.

## 6. Shared Ready List와 Determinism 문제

FreeRTOS는 ready state의 task list를 유지한다. 이 list는 priority level별 linked list를 담은 array 구조로 볼 수 있다.

ESP-IDF에서는 이 ready list가 core들 사이에 공유된다. 각 core scheduler가 호출되면 이 shared list를 보고 어떤 task를 실행할지 결정한다. 각 task의 TCB에는 task가 core 0에서 실행될 수 있는지, core 1에서 실행될 수 있는지, 또는 no affinity인지 나타내는 field가 있다.

Scheduler는 자기 core와 task affinity field가 맞거나 no affinity인 task를 실행할 수 있다. Priority list마다 shared index variable도 있어 scheduler가 task를 선택할 때 갱신된다.

Pinned task와 unpinned task를 섞으면 scheduler가 일부 task를 skip하는 상황이 생길 수 있다. 기술적으로는 deterministic하더라도, 실제 event timing과 instruction execution timing을 사람이 계산하기는 매우 어려워진다.

---

## 7. Cache Miss와 Core Migration

Task를 특정 core에 pinning하면 그 task는 해당 core의 cache를 활용할 수 있다. 자주 사용하는 working data가 cache에 남아 있어 memory access가 빨라질 수 있다.

하지만 no affinity task가 한 번은 core 0에서 실행되고 다음에는 core 1에서 실행된다면, 이전 core cache에 있던 working data를 새 core가 바로 사용할 수 없다. 새 core는 main memory에서 data를 다시 가져오고 cache를 다시 채워야 한다.

이런 cache miss는 execution timing 예측을 어렵게 만든다. 특히 real-time application에서는 단순 평균 성능보다 worst-case timing과 predictability가 중요하므로, task migration이 determinism을 해칠 수 있다.

---

## 8. Multicore Interrupts

일부 architecture에서는 interrupt가 core들 사이에 공유될 수 있다. 하지만 ESP32에서는 각 core가 32개의 interrupt set을 가진다.

Code에서 pin level change, DMA buffer full 같은 external event를 특정 core의 interrupt에 연결할 수 있다. Interrupt가 trigger되면 해당 core의 processing이 멈추고, 그 core에서 ISR이 실행된다.

No affinity task를 사용하면 interrupt 발생 시 어떤 task가 멈췄는지 추적하기 어려워진다. Scheduler가 task를 임의 core에서 실행하게 두기 때문이다.

또한 ESP32의 각 core에는 watchdog timer 같은 core-specific internal peripheral이 있다. 이런 peripheral은 자기 core의 interrupt만 trigger할 수 있고 다른 core의 interrupt를 직접 trigger하지 못한다.

> **주의**
> Multicore interrupt behavior는 MCU마다 다르다. ESP32에서 core별 interrupt set을 가진다고 해서 다른 multicore MCU도 같은 방식이라고 가정하면 안 된다.

## 9. Task를 Core에 Pinning할지 결정하는 기준

Task를 no affinity로 두면 사용이 쉽고 CPU utilization을 높이기 좋다. Ready task가 있으면 idle core가 가져가 실행할 수 있으므로 load balancing도 OS가 처리한다. Smartphone이나 desktop의 일반 multithreaded program에서는 보통 이런 방식이 자연스럽다.

하지만 embedded RTOS에서는 pinning이 더 적합한 경우가 많다.

Pinning의 장점은 다음과 같다.

- 어떤 core에서 interrupt가 발생하고 ISR이 실행되는지 추적하기 쉽다.
- Task가 core를 이동하지 않아 cache miss를 줄일 수 있다.
- Core별 workload를 직접 설계해 throughput을 높일 수 있다.
- 어떤 core가 어떤 task를 실행하는지 명확해져 timing determinism이 좋아진다.

단점도 있다. Automatic load balancing을 잃고, optimal placement와 scheduling을 직접 고민해야 한다. 하지만 medical equipment나 space mission처럼 정확한 execution timing이 중요한 RTOS application에서는 이 control과 determinism이 더 중요할 수 있다.

ESP32도 이미 Wi-Fi와 Bluetooth task를 core 0에 pinning하는 방식으로 이런 분리를 사용한다.

## 10. Kernel Object는 Core 간에도 동작한다

ESP32처럼 shared memory를 가진 multicore system에서는 queue, mutex, semaphore 같은 FreeRTOS kernel object를 core 간 synchronization에도 사용할 수 있다.

강의의 간단한 demo에서는 task 0이 core 0에서 실행되고 task 1이 core 1에서 실행된다. Task 0은 500 milliseconds마다 shared binary semaphore를 give한다. Task 1은 semaphore를 take하면 LED를 toggle한다.

결과적으로 core 0이 core 1에게 LED toggle message를 보내는 복잡한 blinky program이 된다. 핵심은 core가 다르더라도 shared memory와 kernel object를 통해 synchronization이 가능하다는 점이다.

## 11. Multicore Critical Section과 Spin Lock

Vanilla FreeRTOS에서는 `taskENTER_CRITICAL`과 `taskEXIT_CRITICAL`로 critical section을 표시할 수 있다. 이는 mutex보다 훨씬 강한 제어다. Critical section 안에서는 scheduler가 실행되지 않고, 일정 priority 이하의 interrupt도 비활성화된다.

ESP-IDF에서는 두 core를 고려해야 하므로 critical section에 들어갈 때 **spin lock**을 제공해야 한다. Spin lock은 global variable lock처럼 동작한다. Mutex와 비슷해 보이지만, 이미 lock이 잡혀 있을 때 다른 core는 blocked state로 들어가는 것이 아니라 while loop를 돌며 기다린다. 이 대기 동작을 spinning이라고 한다.

강의 demo에서는 core 1 task가 critical section 안에서 pin 13을 200 milliseconds 동안 켠다. 동시에 core 0 task는 pin 12를 30 milliseconds마다 toggle한다. Core가 다르기 때문에 core 1에서 scheduler를 멈췄다고 해서 core 0 task까지 그대로 멈추지는 않는다.

그러나 같은 spin lock을 core 0에서도 사용하면 core 1이 critical section 안에 있을 때 core 0은 spinning하며 아무 일도 하지 못한다.

---

## 12. 긴 Critical Section이 Tick Timing을 망가뜨리는 이유

강의에서 200 milliseconds짜리 긴 critical section을 사용하면 예상과 다른 timing이 나타난다. Core 1의 timing이 크게 깨지고, `vTaskDelay` 기반 idle 구간도 예상대로 나오지 않는다.

이유는 ESP-IDF가 critical section 동안 scheduler가 멈춰 놓친 tick을 보정하려고 하기 때문이다. 내부 counter variable은 `vTaskDelay`가 task를 blocked state에서 언제 꺼낼지 판단하는 데 쓰인다. ESP-IDF는 tick timer가 호출되었어야 할 횟수를 계산해 counter를 fast-forward한다.

이 보정은 1~2 tick 정도를 잃었을 때는 도움이 될 수 있다. 하지만 critical section이 너무 길면 timing behavior를 크게 왜곡할 수 있다.

강의에서 hog delay를 1 millisecond로 줄이면 pin 13은 1ms 동안만 켜지고, pin 12는 task 1 idle time 동안 정상적으로 toggle된다.

> **주의**
> Critical section은 가능하면 피하고, 피할 수 없다면 매우 짧게 유지해야 한다. Long critical section은 multicore system에서 scheduler, interrupt, tick compensation, spin lock behavior를 복잡하게 만들어 timing을 예측하기 어렵게 한다.

## 13. 실습 Challenge: Dual-Core ADC Average Program

마지막 challenge는 이전 hardware interrupt project를 ESP32 dual-core 구조로 바꾸는 것이다.

요구사항은 다음과 같다.

- ISR과 sample batch average를 계산하는 task A는 core 0에서 실행한다.
- Serial terminal character echo를 담당하는 task B는 core 1에서 실행한다.
- Serial terminal에 `avg`를 입력하면 가장 최근에 계산한 ADC batch average를 출력한다.
- 기존 single-core version처럼 serial character echo와 average query가 정상 동작해야 한다.

Kernel object를 사용해 data 전달과 synchronization을 이미 잘 해 두었다면, dual-core support를 위해 바꿔야 할 코드는 많지 않다. Task 생성 시 core pinning 인자를 조정하고, ISR과 task 배치를 명확히 하면 된다.

# 컴퓨터는 어떻게 숫자를 세는가

**원본 강의:** [#1 How computers count? (YouTube)](https://www.youtube.com/watch?v=gQOv8o5lS2k)

이 강의는 "Modern Embedded Systems Programming" 코스의 1강이다. 첫 C 프로젝트를 만들어 변수 하나를 1씩 증가시키면서, 그 과정을 디버거로 들여다본다. 표면적으로는 "숫자 세기"지만, 실제로는 변수가 메모리·레지스터에 어떻게 올라가는지, machine instruction이 무엇인지, 컴퓨터가 16진법과 2의 보수로 숫자를 다루는 방식까지 머신 레벨로 내려가 확인하는 강의다. 이 노트만 읽어도 강의를 따로 볼 필요 없도록 절차·숫자·원리를 모두 담았다.

## 2. 컴파일 — 컴파일러는 내 친구다

생성된 코드가 정말 올바른(valid) C 코드인지 검증하려면 **컴파일**한다. 컴파일은 코드를 **컴파일러(compiler)**라는 프로그램에 통과시키는 작업이다.

- `Project → Make`를 선택한다. 단축키는 **F7**이며, 이 단축키는 앞으로 아주 자주 쓴다.
- 처음 빌드하면 툴이 워크스페이스 이름을 묻는다. 일반적으로 `workspace`라고 입력하고 엔터.
- 빌드가 **0 errors, 0 warnings**로 끝나면 첫 합법적인(legal) C 프로그램이 완성된 것이다.

코드 포맷팅(줄바꿈, 들여쓰기 4칸)은 컴파일러 입장에서는 아무 상관이 없다 — 코드를 한 줄로 길게 늘여 써도 컴파일러는 똑같이 받아들인다. 하지만 포맷팅은 그 코드를 읽고 유지보수해야 하는 **사람**에게는 큰 차이를 만든다.

물론 코드에 하는 모든 일이 합법적인 것은 아니다. 일부러 잘못된(illegal) 무언가를 타이핑하고 F7을 누르면, 이번엔 컴파일러가 **에러를 보고**한다. 에러 리포트를 더블클릭하면 툴셋이 코드의 문제 지점으로 바로 데려다준다. 문제를 고친 뒤에는 F7을 다시 눌러 컴파일러에게 또 검사받는 것이 좋은 습관이다.

> 강사의 메시지: **컴파일러는 내 어깨너머로 늘 지켜봐 주는 최고의 친구다.** F7을 자주 눌러 컴파일러에게 도와줄 기회를 주기만 하면 된다.

## 3. 변수 정의와 증가시키기

이제 컴퓨터가 어떻게 세는지 보여줄 `counter` 변수를 정의한다.

**변수(variable)는 숫자 같은 값을 저장하기 위한 컴퓨터 메모리상의 한 위치**다. C에서는 변수를 사용하기 전에 반드시 먼저 정의해야 한다. 정의는 **타입 → 이름 → (선택적으로) 초기값** 순서로 적는다.

```c
int main() {
    int counter;      /* 타입 int, 이름 counter — 변수 정의 */

    ++counter;        /* pre-increment 연산자: counter를 현재 값에서 1 증가 */
    ++counter;
    ++counter;
    /* ... 컴퓨터가 세는 모습을 보려고 여러 번 더 증가 ... */

    return 0;
}
```

변수를 정의하고 바로 F7로 검사하면 에러는 없지만 경고(warning)가 하나 뜬다 — **"변수 counter가 선언되었으나 한 번도 참조되지 않았다(declared but never referenced)"**. 맞는 말이다. 그래서 다음 단계로 넘어가 값을 증가시킨다.

값을 1 증가시키는 C의 특별한 연산자가 **`++`**이며, 이 형태를 **pre-increment**라 부른다. 코드를 작성할 때마다 F7로 여전히 컴파일되는지 확인한다.

## 4. 시뮬레이터로 실행하고 디버거 뷰 열기

프로그램을 실행하기 전에, 프로젝트가 **시뮬레이터(simulator)**용으로 구성됐는지 확인한다.

- 화면 상단에 Simulator 메뉴가 있으면 시뮬레이터 구성이다.
- 확실히 하려면 `Project → Options`의 Debugger 카테고리에서 Simulator가 선택돼 있는지 본다.

실행 방법은 두 가지 — `Project → Download and Debug` 메뉴, 또는 툴바 버튼이다. 실행하면 IAR이 **디버거 모드**로 전환된다.

디버거에서 다음 4개 뷰가 보이도록 한다. 이 뷰들이 시뮬레이션되는 **ARM Cortex-M4 프로세서** 내부를 들여다보는 창이다.

- **Disassembly** — 컴파일러가 만든 machine instruction
- **Memory** — 메모리 내용
- **Register** — CPU 레지스터
- **Locals** — 지역 변수

## 5. machine instruction과 메모리 — 명령어도 그냥 숫자다

**Disassembly 뷰**는 컴파일러가 우리 프로그램으로부터 생성한 **machine instruction(기계 명령어)**을 보여준다. 프로세서는 강조 표시된 명령어, 즉 `main` 함수의 시작 지점에 멈춰 있다.

여기서 핵심 통찰: **machine instruction도 컴퓨터 안의 다른 모든 것과 마찬가지로 그냥 숫자다.**

- 명령어 오른쪽의 기호는 **instruction mnemonic(명령어 니모닉)**이라 하며, 가독성을 높이려고 **디버거가 덧붙인 것**이다. 명령어 자체가 아니다.
- 명령어 왼쪽의 숫자 열은 명령어의 **메모리 주소(memory address)**다. 메모리 주소는 **메모리의 바이트마다 부여된 숫자**일 뿐이다.

이 점을 확인하려고 **Memory 뷰**를 본다. 메모리는 **0부터 순차적으로 번호가 매겨진 바이트들의 거대한 표**로 생각할 수 있다. 이 순차 번호가 바로 주소이며, Memory 뷰 왼쪽 가장자리의 숫자 열에 표시된다.

메모리에서 machine instruction을 더 잘 알아보려면 뷰 단위를 **2바이트 단위**로 바꾼다. 대부분의 ARM Cortex 명령어가 메모리에서 **2바이트**를 차지하기 때문이다. 그러면 명령어가 쉽게 눈에 들어온다 — 예를 들어 주소 40에는 Disassembly 뷰에서 본 것과 같은 숫자가 있고, 주소 42부터 50까지의 명령어도 마찬가지다. 즉 Disassembly가 보여주는 명령어와 Memory가 보여주는 숫자가 같다 — 명령어는 정말로 메모리 속 숫자다.

## 6. 한 줄씩 실행하기와 PC register

코드를 한 줄(C line)씩 실행하려면 코드 뷰 안을 클릭하고 **Step Into** 버튼을 누른다.

- 처음 Step Into → 현재 명령어가 1 전진하고, `counter` 변수 값이 0으로 바뀐다. 동시에 **PC 레지스터** 값이 42로 바뀐다.
- **PC는 program counter(프로그램 카운터)**의 약자다. **명령어를 세기 때문에** 이런 이름이 붙었다.
- 다시 Step Into → 다음 명령어 실행 → 이번엔 `counter` 값이 1로 증가한다.
- Locals 뷰는 `counter` 변수가 **R1 레지스터**에 들어 있다고 알려준다. Register 뷰를 보면 실제로 R1 값이 1이다.

## 7. CPU 레지스터 — R0부터 R15까지

레지스터(register)란 무엇인가? 간단한 계산기를 써 봤다면 이미 감이 있다. **마이크로프로세서의 레지스터는 계산기의 메모리 레지스터와 매우 비슷하다.** 계산기에서 메모리 레지스터에 값을 더하고(add), 불러오고(recall), 지울(clear) 수 있는 것처럼 말이다.

- ARM Cortex-M 프로세서에는 그런 레지스터가 **16개** 있고, **R0부터 R15**까지 이름이 붙어 있다.
- **R15는 PC(program counter)의 다른 이름**이다.
- 모든 레지스터는 **32비트 숫자**를 담을 수 있다.

레지스터가 중요한 이유: **machine instruction이 레지스터를 직접, 보통 단 한 클럭 사이클(one clock cycle)만에 조작할 수 있다.** 앞서 본 두 가지 예가 바로 레지스터를 조작하는 명령어다 — R1에 0을 옮기는 것(`counter = 0`), 그리고 R1에 1을 더하는 것(`++counter`).

코드를 계속 한 줄씩 실행하며 `counter` 변수가 증가하는 것을 지켜본다. 모든 게 예상대로 동작하는 듯하지만, **counter가 10에 도달하면 흥미로운 일**이 생긴다.

## 8. 진법 — 10진법, 2진법, 16진법

`counter`는 R1 레지스터에 들어 있는데, 값이 10이 되자 **Locals 뷰와 Register 뷰가 서로 안 맞는 것처럼 보인다** — R1이 값 `a`를 보여주기 때문이다.

이유: **Locals 뷰는 counter를 10진법(decimal)으로 보여준다.** 사람들이 10진법을 채택한 건 손가락이 10개라서다. 하지만 강사의 농담대로 "C 프로그래머는 일하다 보면 손가락이 16개로 자란다" — 프로그래머는 **16진법(hexadecimal)**으로 일하는 게 훨씬 자연스럽다고 느낀다. 16진법이 모든 컴퓨터의 바탕인 **2진법(binary)에 완벽하게 대응**되기 때문이다.

10진법·2진법·16진법의 대응 관계는 이렇다.

| 10진법 | 2진법 (4비트) | 16진법 |
|--------|---------------|--------|
| 0  | 0000 | 0 |
| 1  | 0001 | 1 |
| 2  | 0010 | 2 |
| 3  | 0011 | 3 |
| 4  | 0100 | 4 |
| 5  | 0101 | 5 |
| 6  | 0110 | 6 |
| 7  | 0111 | 7 |
| 8  | 1000 | 8 |
| 9  | 1001 | 9 |
| 10 | 1010 | a |
| 11 | 1011 | b |
| 12 | 1100 | c |
| 13 | 1101 | d |
| 14 | 1110 | e |
| 15 | 1111 | f |

핵심 용어와 규칙:

- **하나의 16진수 자리(hex digit)는 4비트 묶음을 표현하며, 이 4비트 묶음을 nibble(니블)이라 부른다.** 16진법은 한 자리로 0~15를 모두 표현하지만, 10진법은 9를 넘는 수에 두 자리가 필요하다.
- 16진수 앞에 붙는 이상해 보이는 **`0x` 접두사는 C 언어가 16진수를 표기하는 약속(convention)**이다. (예: `0xA`)
- 32비트 문자열을 16진수로 인코딩할 때는, 비트를 8개씩 4묶음으로 나누고 이 8비트 묶음을 **byte(바이트)**라 한다. **각 바이트는 4비트 nibble 2개로 이루어진다.** nibble은 위 표대로 16진수 한 자리에 곧바로 대응된다.
- 인코딩 예: nibble `1010` → 16진수 `a`, nibble `0101` → 16진수 `5`. 따라서 1바이트 `10100101`은 `0xA5`다. 같은 방식으로 32비트 문자열 전체를 8자리 16진수로 옮길 수 있다.

그래서 디버거 뷰 대부분이 `0x` 접두사가 붙은 16진수를 보여주는 것이며, 이제 그 뷰들이 훨씬 이해된다.

## 9. signed integer 오버플로우와 2의 보수

`counter`를 계속 증가시키기 전에, 숫자가 아주 커지면 무슨 일이 생기는지 미리 실험해 본다(치팅). 디버거에서는 변수를 클릭해 새 값을 직접 타이핑할 수 있어서 쉽다.

- `counter`에 **`0x7FFFFFFF`**를 입력하고 엔터. 10진법으로는 큰 양수다.
- 프로그램이 `counter`를 1 증가시키게 하면 — **이상한 일이 일어난다.** counter가 10진법으로 **거대한 음수**가 된다. R1 레지스터로는 **`0x80000000`**이다.

이유: `counter`는 `int`(정수)로 선언됐고, **C에서 `int`는 signed number(부호 있는 수)** 라서 양수와 음수를 모두 담을 수 있다. 그리고 컴퓨터는 음수를 **2의 보수 표현(two's complement representation)**이라는 다소 독특한 방식으로 나타낸다.

2의 보수의 동작을 원형 그래프로 설명하면 — 그래프의 모든 화살표는 "1 증가"를 뜻한다.

> **이미지 필요**
> 2의 보수 순환 다이어그램: 32비트 정수 값이 원형으로 배치되어 `0x7FFFFFFF`(최대 양수) → `0x80000000`(최소 음수) → `0xFFFFFFFF`(-1) → `0x0` 순으로 1씩 증가하며 순환하는 그림.
> - 출처: 강의 13:30 부근 circular graph
> - 대체안: 강의 해당 구간 스크린샷 캡처, `cs/임베디드수업/images/1_twos_complement_circle.png`로 저장

순환 원리:

1. 작은 양수에서는 모든 게 예상대로 동작한다 — **최상위 비트(MSB)를 제외한 모든 비트가 채워질 때까지**. 이 값 `0x7FFFFFFF`가 32비트 signed integer가 표현할 수 있는 **가장 큰 양수**다.
2. 이 수를 1 증가시키면 **MSB로 오버플로우**되고, 그 순간 수는 음수가 된다. 사실상 32비트로 표현 가능한 **가장 작은 음수** `0x80000000`이 된다.
3. 거기서 계속 증가시키면 값은 점점 **덜 음수**가 되다가, 모든 비트가 채워지면 **-1**(`0xFFFFFFFF`)에 도달한다.
4. -1을 1 증가시키면 다시 **0**이 되고, 이 순환이 반복된다.

디버그 세션에서 이를 확인하려면 `counter`를 -1로 설정하고 R1 레지스터 내용을 본 뒤, 1 증가시켜 counter를 다시 0으로 만들어 순환을 닫는다. 확인이 끝나면 X 버튼으로 디버거를 종료한다.

> **숙제(강사 제시):** unsigned integer가 어떻게 세는지 공부할 것. `counter` 변수의 타입을 **`unsigned int`**로 바꾸고 다시 컴파일한 뒤, 이번 세션과 똑같이 디버거를 실행해 관찰한다. (signed와 달리 unsigned는 음수 구간 없이 0 ~ 최대값을 순환한다.)

## 10. LaunchPad 보드에서 직접 실행하기

마지막으로, 시뮬레이터가 아닌 실제 LaunchPad 보드에서 코드를 돌려본다.

1. `Project → Options` 메뉴를 연다.
2. **Debugger 카테고리**의 드롭다운 목록에서 **TI Stellaris** 옵션을 선택한다.
3. **Download 탭**으로 가서 **`Use flash loader`** 옵션과 **`Verify download`** 옵션을 체크한다.
4. OK를 누른다.
5. 제공된 USB 케이블로 LaunchPad 보드를 컴퓨터에 연결한다. 보드를 처음 연결하는 경우, USB 디버거용 USB 드라이버 설치에 1~2분 정도 기다린다.

보드에는 LED를 깜빡이는 데모 프로그램이 미리 적재돼 있다. 이제 우리 코드를 보드의 **flash 메모리**에 다운로드하고, 시뮬레이터에서 했던 것과 **똑같은 방식으로** 디버깅할 수 있다.

이게 가능한 이유: 보드의 USB 디버거와 마이크로컨트롤러 자체가 이 기능을 제공하는 **특별한 회로(special circuitry)**를 갖추고 있기 때문이다.

> **주의**
> 우리 프로그램은 마이크로컨트롤러 안에 **영구적으로 프로그래밍된 채로 남는다.** 따라서 보드는 이제 숫자를 세긴 하지만 LED를 더 이상 깜빡이지 않는다(데모 프로그램을 덮어썼으므로). 다시 깜빡이게 만드는 법은 이후 강의에서 다룬다.

다음 강의에서는 명령어의 반복을 **loop(루프)**로 대체하는 법, 그리고 코드의 **제어 흐름(control flow)**을 바꾸는 여러 방법을 다룬다.

## 면접 답변 (30초 분량)

> `/easy-quiz` 실행 시 이 섹션이 정답 카드로 사용됩니다.

주제: **2의 보수(two's complement)와 signed integer 오버플로우**

- **한 줄 정의:** 2의 보수는 컴퓨터가 음수를 표현하는 방식으로, 정해진 비트 폭 안에서 값이 원형으로 순환하는 표현법이다.
- **왜 필요:** 음수를 위한 별도 부호 비트 처리 없이, 덧셈 회로 하나로 양수·음수 연산을 동일하게 처리하기 위해서다. 그래서 machine instruction의 "1 더하기"가 양수든 음수든 똑같이 동작한다.
- **동작:** 32비트 signed `int`에서 가장 큰 양수는 `0x7FFFFFFF`다. 여기에 1을 더하면 최상위 비트(MSB)로 오버플로우되어 가장 작은 음수 `0x80000000`이 된다. 계속 더하면 값이 점점 덜 음수가 되어 `0xFFFFFFFF`에서 -1이 되고, 다시 1을 더하면 0으로 돌아와 순환이 반복된다.
- **비교:** `int`(signed)는 음수 구간을 갖고 `0x7FFFFFFF`에서 음수로 뒤집히지만, `unsigned int`는 음수 없이 0 ~ `0xFFFFFFFF`를 순환하며 최대값 다음이 0이 된다. 같은 비트 패턴이라도 타입에 따라 해석이 달라진다.
- **30초 통합 답변:**
  > 2의 보수는 컴퓨터가 음수를 표현하는 방식으로, 정해진 비트 폭 안에서 값이 원형으로 순환하는 게 핵심입니다. 음수용 부호 처리를 따로 두지 않고 하나의 덧셈 회로로 양수·음수 연산을 똑같이 처리하려고 이렇게 합니다. 32비트 signed int에서 가장 큰 양수는 0x7FFFFFFF인데, 여기에 1을 더하면 최상위 비트로 오버플로우되면서 가장 작은 음수인 0x80000000으로 뒤집힙니다. 계속 더하면 점점 덜 음수가 되다가 0xFFFFFFFF에서 -1이 되고, 다시 1을 더하면 0으로 돌아와 순환이 반복됩니다. unsigned int는 같은 비트라도 음수 구간 없이 0부터 최대값까지만 순환한다는 점이 다릅니다. 결국 메모리의 비트 패턴 자체에는 부호가 없고, 타입이 그 패턴을 어떻게 해석할지를 결정하는 것입니다.

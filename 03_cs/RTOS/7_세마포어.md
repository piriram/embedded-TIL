# Semaphore

**주제:** Semaphore의 count 기반 동작, mutex와의 차이, producer-consumer synchronization, binary semaphore와 counting semaphore의 실제 사용법.
**원본 강의:** [Introduction to RTOS Part 7 - Semaphore | Digi-Key Electronics (YouTube)](https://www.youtube.com/watch?v=5JcMtbA9QEE)

## 1. Semaphore를 Mutex의 일반화로만 보면 안 되는 이유

많은 자료에서는 semaphore를 mutex의 generalization이라고 설명한다. Mutex는 critical section에 한 task만 들어가게 하지만, semaphore는 count를 1보다 크게 둘 수 있으므로 여러 task가 동시에 critical section에 들어가게 할 수 있다는 뜻이다.

이 설명은 technically true다. 하지만 강의에서는 실제로는 여러 thread가 같은 critical section에 동시에 들어가야 하는 경우가 드물다고 설명한다. 오히려 semaphore는 shared resource 자체를 보호하는 lock이라기보다, 어떤 resource가 준비되었음을 다른 task에 알리는 **signaling mechanism**으로 쓰는 편이 더 적합하다.

Coffee shop analogy로 보면 mutex는 shared restroom 하나를 열고 잠그는 key와 비슷하다. Semaphore를 이 비유로 확장하면 여러 restroom과 어느 문에도 맞는 key bucket처럼 보인다. 그러나 이 비유는 곧 한계에 부딪힌다. Key를 하나 얻었다고 해도 어떤 restroom이 이미 사용 중인지 알 수 없고, 결국 각 restroom을 보호하는 별도 mutex가 필요하기 때문이다.

> **주의**
> Semaphore를 "여러 task가 동시에 critical section에 들어가게 하는 mutex"로만 이해하면 shared resource 보호를 잘못 설계하기 쉽다. 개별 shared resource 접근이 atomic하지 않다면 semaphore와 별개로 mutex가 필요하다.

## 2. Counting Semaphore의 기본 동작

Semaphore는 lock과 비슷하지만 값이 0 또는 1에만 머물지 않는다. 우리가 설정한 positive number까지 count할 수 있다.

예를 들어 critical section에 동시에 최대 세 task만 접근하게 하고 싶다면, semaphore의 initial value와 maximum value를 3으로 설정할 수 있다.

동작 흐름은 다음과 같다.

1. Task A가 shared resource를 사용하기 전에 semaphore를 확인한다.
2. Semaphore count가 0보다 크면 task A는 semaphore를 take한다.
3. Take 동작은 count를 1 감소시킨다.
4. Task A는 critical section에 들어간다.
5. Task B와 task C도 같은 방식으로 semaphore를 take하고 들어간다.
6. Count가 0이 되면 네 번째 task D는 semaphore를 take할 수 없다.
7. Task D는 blocked state에서 기다리거나, block하지 않고 나중에 다시 확인할 수 있다.
8. 어떤 task가 critical section 작업을 끝내고 semaphore give를 호출하면 count가 1 증가한다.
9. Task D는 다시 semaphore를 take하고 critical section에 들어갈 수 있다.

Semaphore take에서 count를 확인하고 decrement하는 동작은 **atomic operation**이어야 한다. 중간에 다른 task가 끼어들면 둘 이상의 task가 같은 count를 보고 잘못 진입할 수 있기 때문이다.

FreeRTOS에서는 보통 `xSemaphoreTake`와 `xSemaphoreGive`라는 표현을 쓴다. POSIX semaphore에서는 `wait`와 `post` 같은 용어를 쓴다. OS마다 vocabulary가 다르므로 documentation을 확인해야 한다.

## 3. Semaphore의 실용적 용도: Producer-Consumer Synchronization

Semaphore는 producer-consumer design에서 자주 쓰인다.

Producer task는 shared resource에 data를 추가한다. Consumer task는 shared resource에서 data를 읽고 제거한다. 여기서 shared resource는 buffer나 linked list처럼 여러 item을 담을 수 있는 구조일 수 있다.

Producer가 buffer에 item을 하나 추가하면 semaphore give를 호출한다. 이는 "소비할 item이 하나 생겼다"는 signal이다. Consumer는 item을 읽기 전에 semaphore take를 호출한다. Count가 0보다 크면 consumer는 item을 읽고 제거할 수 있으며, take 동작으로 count가 1 줄어든다.

Count가 0이면 consumer는 소비할 item이 없다는 뜻이므로 block된다. 반대로 semaphore maximum value를 buffer capacity에 맞추면 producer가 buffer를 무한히 키우지 못하도록 제한할 수도 있다.

> **이미지 필요**
> Producer가 buffer에 item을 넣고 semaphore give로 count를 올리며, consumer가 semaphore take로 count를 내리고 item을 소비하는 흐름
> - 출처: 강의 03:37~05:11 구간
> - 대체안: producer-consumer buffer와 filled count semaphore 다이어그램

## 4. Semaphore와 Mutex를 함께 써야 하는 경우

Producer-consumer 구조에서도 shared resource 접근이 atomic하지 않다면 semaphore만으로는 충분하지 않다.

예를 들어 circular buffer에 여러 producer가 값을 쓰고 여러 consumer가 값을 읽는다고 하자. Semaphore는 filled slot 수나 empty slot 수를 count할 수 있지만, buffer 배열, read index, write index를 수정하는 순간은 여전히 critical section이다.

이런 경우에는 다음처럼 역할을 나눈다.

- **Semaphore:** 읽을 item이 있는지, 빈 slot이 있는지 같은 상태를 task 사이에 signal한다.
- **Mutex:** buffer index와 data structure 자체를 수정하는 critical section을 보호한다.

강의 challenge도 이 구조를 요구한다. Five producer tasks와 two consumer tasks가 shared circular buffer를 사용하며, 이를 보호하려면 mutex 1개와 counting semaphore 2개가 필요하다.

## 5. Queue와 비교

Semaphore로 producer-consumer synchronization을 구현할 수 있지만, 이 구조는 queue와 매우 비슷하다.

FreeRTOS queue는 data 전달과 synchronization을 함께 제공한다. Producer는 queue에 item을 넣고, consumer는 queue에서 item을 꺼낸다. Queue가 full이면 producer가 기다리고, queue가 empty이면 consumer가 기다릴 수 있다.

강의에서는 semaphore가 program에 불필요한 complexity를 더하고 debugging을 어렵게 만들 수 있다고 설명한다. Queue로 해결할 수 있는 문제라면 queue를 먼저 고려하는 편이 좋다.

> **주의**
> Semaphore가 가능하다고 해서 항상 좋은 선택은 아니다. Task 사이에 data item을 전달하는 문제라면 queue가 더 단순하고 안전할 수 있다.

## 6. Mutex와 Semaphore의 핵심 차이

Mutex와 semaphore는 구현이 비슷해 보일 수 있지만 사용 목적은 다르다.

Mutex는 **ownership**을 가진다. 어떤 task가 mutex를 take하면 그 task가 critical section 또는 shared resource의 lock을 소유한다. 작업이 끝나면 같은 task가 mutex를 release한다. 다른 task는 그동안 mutex를 얻을 수 없다.

Semaphore는 ownership을 전제로 하지 않는다. 보통 한 task가 semaphore를 give하고, 다른 task가 semaphore를 take한다. 즉 semaphore는 "resource가 준비되었다", "item이 생겼다", "event가 발생했다"는 signal을 전달하는 데 적합하다.

또 하나의 차이는 **priority inheritance**다. FreeRTOS 같은 구현에서는 mutex에는 priority inheritance가 포함될 수 있지만 semaphore에는 포함되지 않는다. Priority inheritance는 mutex lock을 가진 낮은 priority task의 priority를 임시로 올려, 높은 priority task가 오래 막히는 priority inversion 문제를 완화한다.

Binary semaphore는 0 또는 1까지만 count하는 semaphore다. 겉보기에는 mutex와 비슷하지만, ownership과 priority inheritance 관점에서 mutex와 같지 않다.

## 7. ISR에서는 Binary Semaphore가 유용하다

Semaphore, 특히 binary semaphore는 interrupt service routine(ISR)에서 유용하다. ISR에서 어떤 data가 준비되었음을 task에 알리고 싶을 때 semaphore를 give할 수 있다.

반대로 ISR에서 mutex를 사용하는 것은 좋지 않다. Mutex를 take하려다 resource가 풀릴 때까지 기다리면 ISR이 block될 수 있기 때문이다. ISR은 가능한 짧고 빠르게 끝나야 한다.

> **주의**
> ISR 안에서는 block될 수 있는 동작을 피해야 한다. Data ready event를 task에 알리는 목적이라면 mutex가 아니라 binary semaphore나 ISR-safe notification mechanism을 사용해야 한다.

## 8. Binary Semaphore로 Task Parameter Copy를 기다리기

이전 강의에서는 task 생성 중 stack memory에 있는 parameter를 task가 읽을 때까지 setup function을 기다리게 하려고 mutex를 사용했다. 강의에서는 이것이 mutex의 좋은 사용은 아니며, binary semaphore가 더 적합하다고 설명한다.

Binary semaphore는 초기값이 0이다. 따라서 task 생성 전에 미리 take할 필요가 없다.

흐름은 다음과 같다.

1. Setup에서 binary semaphore를 만든다.
2. Task를 생성하며 parameter pointer를 넘긴다.
3. Task는 parameter 내용을 local variable로 복사한다.
4. Task가 `xSemaphoreGive`를 호출해 "parameter를 복사했다"고 signal한다.
5. Setup은 `xSemaphoreTake`로 기다리다가 signal을 받으면 다음 단계로 진행한다.

이 방식은 mutex보다 의미가 명확하다. Mutex는 ownership과 shared resource 보호를 표현하지만, binary semaphore는 event completion을 표현한다.

다만 FreeRTOS documentation은 여전히 stack memory를 이런 방식으로 task parameter에 넘기는 것을 권장하지 않는다고 한다. 예제에서는 동작하지만 production code에서는 더 안전한 parameter lifetime 설계를 고려해야 한다.

## 9. Counting Semaphore Demo

강의의 counting semaphore demo는 다섯 task가 parameter copy를 끝낼 때까지 setup function이 기다리는 구조다.

Base code는 다섯 task를 만들고, 모두 같은 task function을 실행한다. 각 task는 parameter로 받은 message struct를 local message struct로 복사한 뒤, `body`와 `length` member를 출력한다.

Setup에서는 task 수와 같은 maximum value 5, initial value 0을 가진 counting semaphore를 만든다. 그런 다음 `for` loop로 unique task name을 만들고 task를 생성한다. 각 task는 struct를 local variable로 복사한 뒤 semaphore를 increment하고, 내용을 출력하고, 1초 기다린 다음 자신을 delete한다.

Setup은 `xSemaphoreTake`를 다섯 번 호출하는 loop를 돌며 모든 task가 parameter copy를 완료할 때까지 기다린다. Semaphore count가 다시 0이 되면 다섯 task 모두 stack memory에 있던 struct를 local copy로 옮겼다는 뜻이고, setup function은 안전하게 return할 수 있다.

실행하면 argument가 다섯 번 출력된다. 하지만 serial port를 shared resource로 보호하지 않았기 때문에 output이 서로 겹칠 수 있다. Bonus challenge는 `Serial.print` statements를 critical section으로 보고 mutex로 보호하는 것이다.

## 10. 실습 Challenge: Circular Buffer 보호

최종 challenge는 five producer tasks와 two consumer tasks가 shared circular buffer를 사용하는 program을 완성하는 것이다.

Producer task는 자기 task number를 parameter에서 복사한 뒤, 그 번호를 circular buffer에 세 번 쓴다. 따라서 올바르게 구현하면 terminal에는 0, 1, 2, 3, 4가 각각 세 번씩 출력되어야 한다. 출력 순서는 정해져 있지 않다.

Consumer task는 buffer에서 값을 읽어 출력한다. Starting code에는 protection이 없기 때문에 serial output이 겹치고, consumer task를 멈추는 조건도 없어 program이 계속 실행된다.

해결에는 다음 synchronization object가 필요하다.

- **Mutex 1개:** circular buffer의 shared data와 index 보호
- **Counting semaphore 1개:** filled slot 수 count
- **Counting semaphore 1개:** empty slot 수 count

Producer는 empty slot semaphore를 take한 뒤 mutex로 buffer 접근을 보호하고, write가 끝나면 filled slot semaphore를 give한다. Consumer는 filled slot semaphore를 take한 뒤 mutex로 buffer 접근을 보호하고, read가 끝나면 empty slot semaphore를 give한다.

강의는 먼저 semaphore로 풀고, 그다음 queue로 다시 풀어보라고 권한다. Queue를 사용하면 같은 문제를 더 적은 코드와 낮은 complexity로 해결할 수 있는지 비교할 수 있다.

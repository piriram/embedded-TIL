# 인터럽트의 개념과 동작 원리 — Interrupts Part 1

**원본 강의:** [#16 Interrupts Part-1: What are interrupts, and how they work (YouTube)](https://www.youtube.com/watch?v=jP1JymlHUtc)

이 강의는 "Modern Embedded Systems Programming" 코스의 16강이다. 앞 강의에서 준비한 vector table과 `SysTick_Handler()`를 실제로 사용해, CPU를 붙잡고 있던 busy-wait polling을 0.5초 주기의 SysTick interrupt로 교체한다. 단순히 코드를 바꾸는 데서 끝나지 않고, interrupt가 왜 하드웨어를 필요로 하는지, 비동기 신호가 언제 프로그램을 선점하는지, Cortex-M의 interrupt entry와 `PRIMASK`가 어떤 역할을 하는지까지 설명한다.

---

## 1. Polling의 문제와 interrupt가 필요한 이유

기존 blinky 프로그램은 다음 순서로 동작했다.

1. 하드웨어를 초기화한다.
2. 빨간 LED를 켠다.
3. `delay()`가 50만 회를 세는 동안 기다린다.
4. 빨간 LED를 끈다.
5. 다시 `delay()`로 50만 회를 기다린다.
6. 이 과정을 `while (1)`에서 반복한다.

이 `delay()`는 기다리는 동안 CPU가 iteration counter가 0이 되었는지만 계속 확인한다. 어떤 조건이 만족됐는지 프로그램이 반복해서 확인하는 방식을 **polling**이라 하고, 그중에서도 아무 유용한 작업 없이 반복문만 도는 방식을 **busy-wait polling**이라 한다.

Polling 자체가 항상 나쁜 것은 아니며 더 영리한 polling 방식도 있다. 그러나 0.5초처럼 긴 시간을 busy-wait으로 보내면 CPU 전체를 점유하여 다른 작업을 할 수 없게 만든다.

> 밤새 시계를 보면서 매 tick을 세어 아침에 일어나는 대신, 우리는 알람을 맞춰 놓고 그동안 잠을 잔다. Interrupt는 프로세서가 사용하는 알람과 같다.

Interrupt는 timeout뿐 아니라 다음과 같은 사건에도 사용할 수 있다.

- 사용자가 버튼을 눌렀을 때
- 통신 interface로 데이터가 도착했을 때
- ADC(Analog-to-Digital Conversion)가 끝났을 때
- Timer의 설정 시간이 만료됐을 때

즉, CPU가 사건을 계속 확인하는 대신 하드웨어가 사건 발생을 CPU에 알리고, CPU는 그때만 대응 코드를 실행한다.

---

## 2. Interrupt에는 하드웨어와 소프트웨어가 모두 필요하다

현실의 알람이 동작하려면 두 종류의 장치가 필요하다.

- 정해진 시각에 소리를 내는 알람 시계
- 그 소리를 감지할 귀와 신경계

MCU의 interrupt도 구조가 같다.

- **Interrupt source:** Timer, GPIO, UART, ADC 같은 peripheral이 조건을 감지하고 interrupt request를 발생시킨다.
- **CPU interrupt hardware:** CPU가 interrupt 신호를 감지하고 현재 실행 흐름을 중단한 뒤 handler로 진입한다.
- **Software configuration:** Peripheral의 조건·주기와 interrupt enable을 설정하고, vector table에 handler를 연결하며, CPU의 interrupt mask를 허용 상태로 만든다.
- **Interrupt handler(ISR):** 사건 발생 시 실행할 짧은 대응 코드를 작성한다.

> **주의**
> Software만 작성한다고 interrupt가 만들어지는 것은 아니다. 사건을 감지하고 CPU에 알리는 peripheral과, 그 신호를 받아 실행 흐름을 전환하는 CPU 내부 하드웨어가 반드시 필요하다.

## 3. 이번 강의의 interrupt source — SysTick

TivaC MCU에는 interrupt를 발생시킬 수 있는 장치가 여러 개 있다. 이번 강의에서는 ARM Cortex-M 코어에 포함된 **SysTick(System Timer)**을 사용한다.

SysTick은 CPU clock으로 동작하는 하드웨어 peripheral이며, 강의에서 다루는 핵심 register는 세 개다.

| Datasheet 이름 | CMSIS 이름 | 역할 |
| --- | --- | --- |
| `STCTRL` | `SysTick->CTRL` | clock source, interrupt enable, counter enable 설정 |
| `STRELOAD` | `SysTick->LOAD` | down-counter가 다시 시작할 reload 값 설정 |
| `STCURRENT` | `SysTick->VAL` | 현재 counter 값. 이 MCU에서는 write 시 값과 무관하게 clear |

`SysTick->VAL`은 **24-bit down-counter**다. CPU clock cycle마다 1씩 감소하고, 0에 도달하면 CPU에 interrupt를 발생시킬 수 있다. 이후 `SysTick->LOAD`의 값이 자동으로 다시 적재되고 감소를 반복하므로, 별도의 software delay 없이 일정한 주기의 interrupt를 계속 만들 수 있다.

```text
SysTick->LOAD 값 적재
        ↓ CPU clock마다 1 감소
... → 2 → 1 → 0
              ├─ interrupt request 발생
              └─ LOAD 값 자동 재적재 → 다시 감소
```

`SysTick->LOAD`를 바꾸면 두 interrupt 사이의 시간도 바뀐다.

> **이미지 필요**
> `LOAD`에서 `VAL`로 reload되고, 0에서 interrupt를 발생시킨 뒤 다시 시작하는 SysTick down-counter 구조
> - 출처: TivaC datasheet의 SysTick 설명 및 강의 04:02~05:20
> - 대체안: 강의 04:26~04:59 화면을 캡처하거나 직접 흐름도 작성

## 4. CPU가 interrupt를 감지하고 선점하는 과정

강의의 개념 모델에서 CPU 내부 interrupt hardware는 **각 instruction이 끝날 때 interrupt line의 상태를 확인**한다.

- Interrupt line이 low라면 pipeline의 다음 instruction을 계속 실행한다.
- Interrupt line이 high라면 일반적인 다음 instruction 대신 **Interrupt Entry** 동작을 수행한다.
- 그 결과 현재 프로그램의 정상 흐름이 중단되고 interrupt handler로 제어가 넘어간다.

현재 실행 중인 흐름을 중단하고 더 긴급한 처리로 제어권을 가져오는 것을 **preemption(선점)**이라 한다.

```text
일반 코드 실행
instruction A → instruction B → instruction C → ...
                                  ↑
                       interrupt request 감지
                                  ↓
                         Interrupt Entry
                                  ↓
                         SysTick_Handler()
                                  ↓
                      중단했던 일반 코드로 복귀
```

강의에서는 Cortex-M의 Interrupt Entry가 최소 **12 clock cycles** 걸린다고 설명한다. `MOV`, `ADD` 같은 단순 instruction이 1 cycle에 실행될 수 있는 것과 비교하면 interrupt 진입은 상대적으로 긴 CPU 동작이다.

> **주의**
> Interrupt가 발생했다고 해서 실행 중인 instruction의 중간을 잘라 handler로 이동하는 것은 아니다. Interrupt 신호는 instruction 도중 언제든 바뀔 수 있지만, CPU는 instruction 경계에서 이를 받아들여 진입 절차를 수행한다.

## 5. Interrupt가 asynchronous하다는 의미

CPU instruction은 CPU clock에 맞춰 엄격하게 실행되지만, interrupt source의 사건은 일반 프로그램의 실행 순서와 맞춰 발생하지 않는다. 버튼 입력이나 통신 데이터 도착 같은 사건은 현재 어느 C 문장을 실행 중인지와 관계없이 생길 수 있다.

Interrupt line도 보통 instruction 실행과 동기화되어 있지 않아서 instruction의 중간 시점에 상태가 바뀔 수 있다. 이런 의미에서 interrupt는 실행 중인 프로그램에 대해 **asynchronous(비동기적)**라고 말한다.

여기서 두 시점을 구분해야 한다.

- **사건 발생 시점:** 프로그램 흐름과 무관하며 비동기적이다.
- **CPU가 받아들이는 시점:** 현재 instruction을 마친 뒤 interrupt entry를 시작한다.

따라서 handler가 정확히 어느 일반 코드 instruction 사이에 끼어들지는 실행할 때마다 달라질 수 있다. 이후 race condition, 공유 데이터, critical section을 이해할 때 이 특성이 중요해진다.

## 6. 실습 프로젝트와 polling 코드를 handler 형태로 준비하기

실습은 이전 `lesson15` 프로젝트를 복사해 디렉터리 이름을 `lesson16`으로 바꾸는 것부터 시작한다. 코스에 중간부터 참여했다면 [state-machine.com/quickstart](https://state-machine.com/quickstart)에서 이전 프로젝트를 받을 수 있다. `lesson16` 디렉터리의 workspace 파일을 열어 IAR toolset에서 작업하며, IAR 환경이 없다면 코스의 `lesson0` 설정을 먼저 참고한다.

그동안의 실험 코드를 정리해 기본 blinky 상태로 되돌린다. `main()`은 hardware를 초기화한 뒤 `while (1)` 안에서 빨간 LED를 켜고 끄며, 각각의 상태 뒤에서 `delay()`로 50만 iteration을 busy-wait한다. 이번에는 빨간 LED만 관찰할 수 있도록 파란 LED를 켜는 코드는 comment out한다.

새 방식을 적용하기 전에 기존 polling 코드부터 단순화한다. LED를 켜고 delay한 다음 끄고 다시 delay하는 대신, 매 delay 직전에 LED 상태를 한 번씩 **toggle**하면 delay를 하나만 사용할 수 있다.

```c
while (1) {
    /* LED_RED bit가 0이면 1로, 1이면 0으로 toggle */
    LED_DATA ^= LED_RED;
    delay(500000U);
}
```

위 코드는 강의 화면의 GPIO register 접근식을 핵심 동작만 보이도록 줄여 쓴 것이다. `LED_DATA`는 실제 프로젝트에서 빨간 LED data register에 해당하는 expression으로 바꿔 읽어야 한다.

Toggle에는 C의 bitwise exclusive-OR인 XOR와 복합 대입 연산자 `^=`를 사용한다.

| 기존 `LED_RED` bit | XOR mask | 결과 |
| ---: | ---: | ---: |
| 0 | 1 | 1 |
| 1 | 1 | 0 |

이렇게 바꾸면 `delay()`를 제외한 loop body가 곧 handler가 해야 할 일과 같아진다. `F7`로 error 없이 build되는지 확인한 뒤 XOR 연산에 breakpoint를 걸면, breakpoint를 지날 때마다 LED가 toggle된다. 프로그램을 free-run하면 LED가 약 1초마다 한 번 깜빡인다. 이 polling 동작을 먼저 검증하고 나서 같은 toggle 코드를 handler로 옮긴다.

> LED 상태는 0.5초마다 toggle된다. ON 0.5초와 OFF 0.5초가 합쳐져 완전한 한 번의 깜빡임 주기는 약 1초다.

## 7. 0.5초 주기의 SysTick 값 계산

TivaC의 기본 CPU clock은 보드의 16 MHz crystal oscillator에서 오며, 이는 초당 16,000,000 clock cycles를 뜻한다.

```c
#define BSP_TICKS_PER_SEC 16000000U
```

0.5초마다 interrupt를 발생시키려면 필요한 cycle 수는 다음과 같다.

```text
16,000,000 cycles/s × 0.5 s = 8,000,000 cycles
```

SysTick은 0까지 포함하여 세므로 `LOAD`에는 1을 뺀 값을 기록한다.

```text
SysTick->LOAD = 8,000,000 - 1
              = 7,999,999
              = 0x7A11FF
```

즉 reload 이후 `7,999,999, 7,999,998, ... , 1, 0`의 총 8,000,000개 count를 거친다. 1을 빼지 않으면 한 clock을 더 세게 된다.

SysTick counter의 최대 폭은 24-bit이므로 값이 범위 안에 드는지도 확인해야 한다.

```text
24-bit 최대값 = 0xFFFFFF = 16,777,215
필요한 LOAD 값 = 0x7A11FF = 7,999,999
```

`0x7A11FF`는 세 byte 안에 들어가므로 24-bit 범위를 넘지 않는다.

> **주의**
> Timeout을 계산할 때는 CPU clock, counter bit 폭, 0 포함 여부를 함께 확인해야 한다. Clock 설정이 달라지면 같은 `LOAD` 값도 다른 시간이 된다.

## 8. SysTick register 설정

SysTick register는 `tm4c_cmsis.h`가 포함하는 CMSIS header `core_cm4.h`에 이미 memory-mapped 구조로 정의되어 있다. Datasheet와 CMSIS의 이름은 다르지만 역할을 대응시켜 사용할 수 있다.

```c
SysTick->LOAD = (BSP_TICKS_PER_SEC / 2U) - 1U;
SysTick->VAL  = 0U;
SysTick->CTRL = (1U << 2) | (1U << 1) | (1U << 0);
```

`SysTick->CTRL`에서 켜는 bit는 다음과 같다.

| Bit | 설정 | 의미 |
| ---: | --- | --- |
| 2 | Clock Source | CPU clock을 SysTick clock source로 사용 |
| 1 | Interrupt Enable | counter가 0일 때 interrupt 발생 허용 |
| 0 | Counter Enable | SysTick counter 시작 |

`SysTick->VAL`은 강의의 대상 MCU에서 clear-on-write register이므로 어떤 값을 쓰든 clear된다. 의도를 분명히 하기 위해 `0U`를 쓴다.

설정이 끝나면 SysTick hardware가 CPU와 독립적으로 시간을 세고, 0.5초마다 interrupt request를 보낸다.

## 9. SysTick_Handler에는 무엇을 넣는가

이전 강의에서 vector table에 `SysTick_Handler`를 설치했고 `bsp.c`에 빈 handler body를 만들어 두었다. 이제 handler에는 polling loop에서 검증했던 LED toggle 한 줄만 넣는다.

```c
void SysTick_Handler(void) {
    LED_DATA ^= LED_RED;
}
```

여기서도 `LED_DATA`는 register 접근의 의미를 보여주기 위한 축약 표기다. 핵심은 `bsp.c`의 기존 빈 `SysTick_Handler()` body에서 빨간 LED bit에 XOR를 적용한다는 점이다.

기존 polling에서는 toggle 뒤의 `delay()`가 다음 toggle까지의 시간을 만들었다. Interrupt 방식에서는 SysTick peripheral이 CPU 밖에서 그 시간을 세므로 handler 안에 delay가 필요 없다.

```text
Polling 방식:   LED toggle → CPU가 delay를 세며 대기 → LED toggle
Interrupt 방식: LED toggle → CPU는 다른 코드 실행 → SysTick interrupt → LED toggle
```

`LED_RED`와 CPU clock frequency가 `main.c`에만 정의되어 있으면 `bsp.c`의 handler가 사용할 수 없다. 이런 board-specific definition은 `bsp.h`로 옮기고 `main.c`와 `bsp.c` 양쪽에서 include한다. Busy-wait가 없어졌으므로 기존 `delay.h`를 `bsp.h`로 정리하고 `delay.c`와 `delay()` 호출도 프로젝트에서 제거한다.

> **주의**
> ISR은 사건에 대한 최소한의 처리만 하고 짧게 끝내는 것이 기본이다. 이 예제에서는 LED bit toggle만 수행하며, 긴 busy-wait를 handler 안으로 옮기지 않는다.

## 10. 빈 `while (1)`이 여전히 필요한 이유

LED toggle을 handler로 옮기면 `main()`의 무한 loop에는 당장 실행할 코드가 없어진다. 그래도 loop 자체를 삭제해서는 안 된다.

```c
int main(void) {
    /* hardware와 SysTick 설정 */
    __enable_interrupt();

    while (1) {
        /* 현재는 할 일이 없지만 CPU가 머물 실행 흐름 */
    }
}
```

CPU는 interrupt 사이에도 계속 어떤 instruction인가를 실행해야 한다. 현재 예제에서는 빈 `while (1)`을 반복하고, SysTick interrupt가 오면 handler로 선점된다. 이후에는 이 loop에서 유용한 background work를 하거나, 다음 interrupt까지 CPU를 sleep 상태로 둘 수 있다.

> Empty loop는 interrupt를 발생시키는 것이 아니다. SysTick hardware가 interrupt를 만들며, loop는 그 사이에 main context가 머무는 장소일 뿐이다.

## 11. `PRIMASK`와 CPU interrupt 활성화

Peripheral에서 interrupt를 enable하는 것만으로는 충분하지 않다. ARM Cortex-M CPU에는 configurable interrupt가 CPU에 도달하지 못하도록 막을 수 있는 **`PRIMASK`**라는 special-purpose mask bit가 있다.

- `PRIMASK = 1`: mask 가능한 interrupt를 차단한다.
- `PRIMASK = 0`: mask 가능한 interrupt를 CPU가 받아들일 수 있다.

강의에서는 IAR intrinsic인 다음 함수를 호출해 `PRIMASK`를 clear하고 CPU interrupt를 허용한다.

```c
__enable_interrupt();
```

따라서 interrupt가 실제로 실행되기 위한 조건은 다음처럼 정리할 수 있다.

1. SysTick의 counter와 clock source가 설정되어야 한다.
2. SysTick 자체의 interrupt enable bit가 켜져야 한다.
3. CPU의 `PRIMASK`가 clear되어 interrupt를 받아들일 수 있어야 한다.
4. Vector table이 올바른 `SysTick_Handler`를 가리켜야 한다.
5. Handler 함수가 실제 대응 코드를 가져야 한다.

## 12. 완성된 동작과 디버깅 관찰

완성한 프로그램을 실행하면 다음 현상을 확인할 수 있다.

- 빨간 LED 상태가 0.5초마다 toggle된다.
- 따라서 LED의 전체 ON/OFF 주기는 약 1초다.
- 실행 중 break하면 CPU는 대부분 빈 `while (1)` 안에 있다.
- `SysTick_Handler`에 breakpoint를 두면 0.5초 간격으로 handler에 진입한다.
- Handler가 끝나면 CPU는 중단했던 main loop로 돌아간다.

전체 구조를 요약하면 다음과 같다.

```text
초기화
  ├─ SysTick LOAD/VAL/CTRL 설정
  ├─ vector table의 SysTick_Handler 사용
  └─ PRIMASK clear
        ↓
main의 빈 while (1) 실행
        ↓ 0.5초 경과
SysTick interrupt request
        ↓
CPU가 현재 instruction 완료 후 preemption
        ↓
SysTick_Handler에서 LED toggle
        ↓
main의 중단 지점으로 복귀
```

이 방식은 CPU가 0.5초를 직접 세지 않으므로 polling보다 효율적이다. 지금은 main loop가 비어 있지만, 앞으로 그 시간에 다른 작업을 실행하거나 저전력 sleep을 사용할 수 있다.

## 13. 핵심 비교 — Polling과 interrupt

| 구분 | Busy-wait polling | Interrupt |
| --- | --- | --- |
| 사건 확인 주체 | CPU가 반복해서 조건 확인 | Peripheral이 사건을 감지해 CPU에 알림 |
| 대기 중 CPU | 반복문에 묶임 | 다른 작업 또는 sleep 가능 |
| 응답 흐름 | 프로그램이 확인 지점에 도달해야 함 | 사건이 현재 흐름을 선점 |
| 시간 생성 | CPU instruction 반복 | Hardware timer가 자율적으로 count |
| 코드 위치 | `while` loop 안 | ISR / interrupt handler |
| 주의점 | CPU 시간 낭비 | 비동기성, ISR 길이, 공유 데이터 관리 필요 |

Interrupt가 polling을 무조건 없애는 만능 해법은 아니다. 다만 긴 시간 동안 CPU가 같은 조건만 확인해야 하는 상황에서는, 사건 감지를 hardware에 맡겨 CPU 시간을 되돌려준다는 큰 장점이 있다.

## 면접 답변 (30초 분량)

> `/easy-quiz` 실행 시 이 섹션이 정답 카드로 사용됩니다.

- **한 줄 정의:** Interrupt는 peripheral 등의 사건이 발생했을 때 CPU의 현재 실행 흐름을 선점하여 미리 등록된 handler를 실행하게 하는 하드웨어·소프트웨어 메커니즘이다.
- **왜 필요:** Busy-wait polling은 CPU가 조건을 계속 확인하느라 다른 일을 하지 못한다. Interrupt를 사용하면 hardware가 사건을 감지하는 동안 CPU는 다른 작업을 하거나 sleep할 수 있다.
- **동작:** Peripheral이 interrupt request를 발생시키면 CPU는 현재 instruction을 마친 뒤 interrupt entry를 수행하고 vector table에 연결된 ISR로 이동한다. ISR을 마치면 중단했던 코드로 복귀한다.
- **비교:** Polling은 CPU가 사건을 반복 확인하지만, interrupt는 사건이 비동기적으로 CPU에 알려져 기존 실행 흐름을 선점한다.
- **30초 통합 답변:**
  > Interrupt는 timer나 GPIO 같은 peripheral에서 사건이 발생했을 때 CPU의 현재 실행 흐름을 선점하고 미리 등록된 handler를 실행하는 메커니즘입니다. Busy-wait polling은 CPU가 조건을 계속 확인하느라 다른 일을 못 하지만, interrupt를 쓰면 hardware가 사건을 감지하는 동안 CPU는 다른 작업을 하거나 sleep할 수 있습니다. 사건이 발생하면 CPU는 현재 instruction을 마친 뒤 interrupt entry를 수행하고 vector table에 연결된 ISR로 이동하며, 처리가 끝나면 중단했던 코드로 복귀합니다. 따라서 polling과 달리 사건 발생이 실행 중인 프로그램에 비동기적이라는 점과 ISR을 짧게 작성해야 한다는 점이 중요합니다.
